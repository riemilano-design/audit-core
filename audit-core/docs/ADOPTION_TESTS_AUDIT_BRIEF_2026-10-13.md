# 採用条件の試験 patch の独立監査 ― 対象と判定基準(**実行の前に固定**)

人間の判定 D-017 の 3。**司令塔の再実行は独立監査と呼ばない。** 確かめるのは **patch の差分・変異ごとの証跡・復元後のハッシュ・既存 13 失敗との一致**。
監査席は**実装しない・直さない・封じた予測や採用条件や期待値を書き換えない・採用判断をしない**。判定は GO / REVISE / HUMAN のどれか。

**人間の指定(最重要)**: **12 変異を検知できたことは、検査対象の実装が概念的に正しいことの証明ではない。** 示されたのは「定められた変更の一部を試験が検出できる」という**試験側の能力**だけである。
席は、**この patch の試験が実際に何を守り、何を守っていないか**を分けて報告する。

## 2 監査項目(番号順)

### 2-1 patch の差分

- (3) の sha256 を確かめ、`git apply --check` → 当てる。**(3) が `recipes.py`・`core/`・`vocabulary.py`・`extract.py`・`tests/golden/`・`core_expectation_*.json`・`mutations.json`・既存の試験ファイルを 1 行も触っていないこと**を、patch の本文と適用後の sha の両方で確かめる。
- 試験 3 本を**読む**。次を答える。
  - **封 `EXTRACTION_SEAL_V2` §2.1 の表が `test_extraction_v2.py` から動いていないこと**(司令塔は「封じた表と境界の追加を混ぜない」ために別ファイルにしたと報告している)。
  - `test_extraction_v2_boundary.py` の **7 行の期待値が、封 §2 の規則の字から導けるか**(実装の出力を写しただけではないか)。**1 行ずつ、封のどの字から導いたかを書く。** 導けない行があれば REVISE。
  - `TR2AllThreeCallSitesStop` が **`ambiguous_count` の値を固定していないこと**(T-R6 が未決なので「立っていること」だけを見る、と司令塔は報告している)。値を固定していれば、未決の仕様を実装に合わせて決めたことになるので REVISE。
  - 合成した fact・context が、**本物の経路(`I.facts_for` / `ctx_ok` / `_collapse_candidates`)を実際に通っているか**。通っていなければ「試験が届いていない」ので REVISE。

### 2-2 変異ごとの証跡(**席が自分で当てて測る**)

- 12 本の変異(`test_adoption_mutation_gate.py` の `_MUTATIONS`)を**自分で**当て、**基準・変異・陰性対照・復元の 4 段階**を測る。
- **検知の判定は 4 つを別々に見る**(司令塔の基準。席はこれを使うか、より厳しいものを使ってよい。緩めない):
  1. `Ran N tests` の組が**ちょうど 1 組**で N が基準と同じ。2. `errors` が 0。3. 落ちた試験の**名前**が期待を含む。4. 終了コードが 0 でない。
  **`grep -c "^FAIL:"` のような行数の合算を使わない。**
- **復元後のハッシュ**が基準と一致することを、12 本とも自分で確かめる。
- **黙る変異を探す。** 司令塔が挙げていない変異を**自分で 3 本以上**作り、**先に予測を書いてから**測る。黙ったものは報告する(どの欠陥が守られていないかの証拠になる)。
- 司令塔が「実装の途中で自分の誤りを 3 件捕まえた」と報告した点(**同じ字数の置換で pyc が古いまま使われる**・**復元を逆向きの置換でやると別の場所に当たる**・**M-E1f の期待に構造的に検知できない試験名が入っていた**)を、**自分で再現**する。とくに **pycache を捨てない実行では変異が隠れるか**を確かめる。

### 2-3 既存 13 失敗との一致

- `unittest` と `pytest` を走らせ、**最終プロセスの終了コードと最終の `Ran`/`FAILED` の行**を記録する。**入れ子の出力と最終の結果を区別する。**
- pytest の落ちた **13 本の名前**が、統合測定のときと**同じ集合**であることを `diff` で確かめる。**新規の落ちが 0** であること。
- 試験の総数が **499 → 522**(unittest)・**595 → 618**(pytest)であること。増えた 23 本が (3) の 23 本と一致すること。
- **Golden 差が 29 件(1B 18・5F 11)で、統合測定の出力と同一**であること。**Golden の一致を正しい束縛の証明として扱わない。**

### 2-4 この試験が守っていないもの(**席が自分で列挙する**)

人間の指定により、**試験側の能力と実装の正しさを分ける**。次を答える。

- **概念の正しさを守る試験は 0 本か。** `N268`・`N272`(判定不能)・概念が違う 10 行・貸借対照表と CF の区別について、**この patch の試験が 1 つでも赤くなる入力があるか**。無ければ「0 本」と、その 0 を作りうる自分の絞り込みを同じ文に書く。
- **実文を読む試験が 0 本か**(合成だけか)。T-E3 の担当範囲と重なっていないか。
- **既存の `test_mutations.py` の飽和**(2 本の patch を重ねた木ではどの変異も「赤」に見える)が**直っていないこと**を確かめる。`mutations.json` が 1 行も変わっていないこと。
- **main では何も守られていないこと**を確かめる(main に `_representative`・`_assign_period_form` が存在しないこと。main に (3) だけを当てたらどうなるかを**測って**報告する)。

- **T-R3・T-E3・T-E4・T-R6 は実装されていない。** 席はこれらを実装しない・期待値を決めない。**`ambiguous_count` の 4 案(`ADOPTION_TESTS_RESULT` §6-3)のどれも選ばない。**
- 未使用 2 書類(`S100Z39P`・`S100Z4N9`)は**開かない**。

## 3 判定の基準(**先に固定**)

| 判定 | 条件 |
|---|---|
| **GO** | 2-1 の差分が報告どおり(`recipes.py` 0 行)、2-2 の 12 本が席自身の測定で検知でき復元ハッシュが一致、2-3 の数と名前が一致、2-4 が証拠つきで列挙されている |
| **REVISE** | 試験が封の字から導けない期待値を持つ / 未決の仕様(`ambiguous_count` の値・T-R3/T-E3/T-E4 の期待値)を実装に合わせて固定している / 本物の経路を通っていない / 席の測定で検知できない変異を司令塔が「検知」と報告している / patch が報告外のファイルを触っている |
| **HUMAN** | 封の字が 2 通りに読める点 / `ambiguous_count` の意味 / 試験の名前や数の不一致 / 再現不能 |

**GO が意味しないこと**: **main 採用の承認ではない。** **実装が概念的に正しいことの証明でもない**(人間の判定 D-017)。採用条件の全体は未達(T-R3・T-R6・T-E3・T-E4)。

## 4 席の規約

- 作業は `git worktree add --detach` の使い捨て木だけ。**共有の作業木を書き換える git(stash/reset/checkout --/clean/restore/add/commit/merge)を使わない。リポジトリのファイルを編集しない。** 終わったら `git worktree remove --force`。
- API キーを使わない・`.env` を読まない・EDINET を呼ばない(`fetch_material.py` を実行しない)。`scripts/playtest/out/` に書かない。
- 材料の zip は main の `audit-core/fixtures/xbrl/ai_prose_instance_2026-10-09.zip`(git 管理外)。worktree では `AC_ZIP` に絶対の道を渡す。
- **数の横に測った木と入口を書く。** 0 件は自分の絞り込みを同じ文に書く。**司令塔の数を写さず、自分で測った数を書く。**
- 報告の形: 判定 → 2-1〜2-4 の結果を番号順に(数・入力・出力)→ **この試験が守っていないもの**(別の節)→ 席が見つけたが範囲外の問題。
