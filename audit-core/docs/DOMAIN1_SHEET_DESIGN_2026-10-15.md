# 新領域① 表計算・会計データの照合 ― 設計案(2026-10-15)

人間の決定(2026-10-15): 「**新領域①へ進み**、A は『原因特定済み・修正未採用』として残します。」
領域の定義(人間、2026-10-14):

> **何を検証するか**: AI が作成した集計・報告と、元の表計算データや会計数値が一致しているか。
> 売上集計と明細の一致 / 複数シート間の数値の整合性 / 報告書に記載された数値の出典 /
> **合計・小計・期間・対象範囲の取り違え**
> XBRL で扱っている「**数値そのものが正しくても、対象や期間が違う**」という問題を、
> 別のデータ形式に展開する領域です。

人間の条件(2026-10-14): 「**公開された実データ**を根拠にし、**報告文は独立した LLM** に作らせる」
「**単純な数値一致ではなく、対象・期間・単位・集計範囲の取り違えを検出できるか**を中心に設計する」
「XBRL や議事録での成功が、そのまま他領域での成功を保証するわけではありません。」

**この文書は設計案である。合格線はまだ 1 つも書かない**(データを見る前に閾値を決めない)。
**実装もまだ無い。**

## 1. この領域で最初に決めるべきこと ― 一致の**優先関係**

人間の教訓(2026-10-15、欠陥 A を止めた直後):

> 単に許容帯を広げるのではなく、**既に完全一致している根拠を、より緩い一致で置き換えない設計**が必要だ。

XBRL では、この優先関係を**実装の後に**気づいた。表計算では**実装の前に仕様として書く**。
表計算は XBRL より危険である: **同じ値のセルが大量に在る**ので、値が一致しただけの接続が簡単に作れる
(「値が一致する参照がちょうど 1 件」でも同定ではない ― XBRL で踏んだ型)。

したがって Adapter の仕様の第 1 条は次の形にする(**案。人間の承認を要する**):

| 順位 | 一致の種類 | 条件 |
|---|---|---|
| 1 | **見出しで同定したセル**が完全一致 | 行見出し(対象)・列見出し(期間)・単位行が主張と合う |
| 2 | **見出しで同定した範囲の式**が一致 | 合計・小計の範囲が主張の集計範囲と合う |
| 3 | 丸めの帯の中で一致(桁は**書かれた桁**) | 1・2 が無いときだけ |
| ― | **値が一致するだけのセル** | **結ばない**(`POINTER_NOT_FOUND` か `UNVERIFIABLE`) |

**下位の一致が上位の一致を置き換えることを禁じる**(これが欠陥 A で起きたこと)。

## 2. 証拠・主張・ポインタ

| | 中身 |
|---|---|
| **証拠(Evidence)** | 1 冊のブック。セル = (シート名, 番地, 値, 表示形式, 式)、および**見出しの構造**(行見出し・列見出し・単位行) |
| **主張(Claim)** | 報告文の 1 文に出る 1 つの数と、その**対象・期間・単位・集計範囲** |
| **ポインタ(Pointer)** | `sheet:<シート名>!<番地>` / 範囲 `sheet:<シート名>!<範囲>` / `formula:sum(<範囲>)` / `formula:a-b` |
| **状態** | Core の 4 状態をそのまま(`GROUNDED` / `VALUE_MISMATCH` / `POINTER_NOT_FOUND` / `UNVERIFIABLE`) |

Core(`core/py/audit_core/`)は変更しない前提で始める。
**変更が要ると分かったら、それ自体を記録する**(README の「証明済みの範囲」の行を書き換える判断は人間)。

## 3. 中心に置く 4 つの取り違え(**この 4 つを検出できるかが領域の合否**)

| 軸 | 表計算での具体 | XBRL での対応物 |
|---|---|---|
| **対象** | 行見出しが違う(「売上高」と「売上総利益」) | 要素の取り違え(欠陥 C) |
| **期間** | 列見出しが違う(当月 / 累計 / 前年同月) | context の取り違え |
| **単位** | 単位行が違う(円 / 千円 / 百万円 / %) | `UNIT_SCALE`・書かれた桁 |
| **集計範囲** | 小計を合計として使う・部門の部分集合・除外行・二重計上 | member(セグメント)の取り違え(欠陥 B) |

## 4. 正解をどう作るか(2 つを**分けて**測る)

XBRL で効いた 2 つの道具を両方使う。**1 回の測定で混ぜない。**

### (i) 正しい報告での接続 ― 盲検のラベル

独立した LLM に報告文を書かせ、**engine の出力を見せずに** 2 席に
「この数はブックのどのセル(または範囲)を指すか」を答えさせる。
XBRL の弱点を最初から直す: **席のモデル・指示文・並びを変える**
(前回は同じ条件の 2 席が 68 行すべてで一致し、独立の証拠としては弱かった)。

### (ii) 誤りを通す率 ― 1 件ずつ注入する

正しい報告に、**4 つの軸のどれか 1 つだけ**を壊した版を作る
(対象をずらす / 期間をずらす / 単位を変える / 範囲を小計に差し替える)。
**1 回の検証で 1 件だけ変える**(複数混ぜると互いの結果を汚す ― 実測で踏んだ型)。
測るのは **誤りを通した件数 / 注入した件数**。人間の原則: 「**誤りを通す率を直接測り 0 を目指す**」。

**(i) と (ii) は分母が違うので、率を並べて比べない。**

## 5. データ(**公開実データ**。取得は人間の承認を得てから一度だけ)

選定の条件:

1. **公開・再配布条件が明記**されている(政府標準利用規約など)。
2. **多シートで、合計と内訳の関係が在る**(集計範囲の取り違えを作れる)。
3. **単位行が在る**(千円・百万円の混在)。
4. **期間の列が複数**在る(当月・累計・前年同月)。

候補(**人間が選ぶ**):

| | 材料 | 向き | 懸念 |
|---|---|---|---|
| (a) | 地方自治体の**歳入歳出決算**の Excel | 小計・合計・部門の階層が濃い。利用条件が明快 | 書式が自治体ごとに違う |
| (b) | **e-Stat** の統計表 Excel(毎月勤労統計・家計調査など) | 期間列・単位行が揃っている | 「AI の報告」を作る題材としては単調 |
| (c) | 上場企業の**決算補足資料**の Excel(IR) | XBRL と地続き。単位は百万円混在 | 再配布条件が材料ごとに違う |

**規律は XBRL と同じにする**: 生ファイルは repo に置かない(`~/.cache/audit-core/sheet/`)、
sha256 を `fixtures/sheet/manifest.json` に記録、取得は 1 回、取得の記録を commit してから測る。

## 6. 工程(**合格線はこの順で、M-3 まで書かない**)

| 段 | 中身 | 終わりの判定 |
|---|---|---|
| **M-1** | 証拠の読み取り(セル・見出し・単位・式)。主張はまだ扱わない | 凍結した 1 冊で、読み取り結果が fixture と一致。**数は読めたかどうかだけ** |

## 9. 読み取りの依存(**測った事実と、決めていないこと**)

測った事実:

- **既存の `adapters/` と `core/py` は外部依存ゼロ**(標準ライブラリだけ。`grep` で確認)。
  XBRL Adapter は ZIP の XML を `zipfile` + `xml.etree` で自分で読んでいる。
- この環境には **openpyxl 3.1.5 が在る**(`xlrd` も在る。`pandas` は無い)。

決めていないこと(**人間の判断を要する。売却先が保守する前提で効く**):

| 案 | 中身 | 利点 | 懸念 |
|---|---|---|---|
| (A) **標準ライブラリだけ**で読む | `zipfile` + `xml.etree` で `xl/worksheets/*.xml` を読む | 依存ゼロの規律を保てる。XBRL と同じ作り | 共有文字列・共有数式・結合セル・表示形式を自分で扱う |
| (B) **openpyxl に依存**する | `openpyxl` で値(`data_only=True`)と式(`data_only=False`)を 2 回読む | 実装が短い | `adapters/` に初の外部依存。版の差が結果に効きうる |

**どちらでも「式と値の両方」を取る必要がある**(値だけでは集計範囲の取り違えを検出できない)。
**(B) を採るなら、版を字で留めて、版が変わったら赤くなる門を置く。**
