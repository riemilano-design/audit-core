# D-1 計画と予測(封印) ― 原文 → Claim の境界を独立した層として切り出す

2026-10-07。人間の決定により GO。**次の実装目標は「誤り検出実験を作る」ではなく
「原文 → Claim の境界を独立した検証可能な層として切り出す」である。**

この文書は実装の前に封じる。**封じた予測は書き換えない。** 訂正は日付つきの追記か結果の文書で行う。
規則・範囲・上限・正規化を、予測を当てるために動かさない。外れは外れのまま残す。

## 1. 目的(言い換えに注意)

分解層の切り出しは、GROUNDED の穴を **閉じない**。
穴を **測れる場所に移す**。この区別を以後の文書で崩さない。

- 閉じる = 「指した行が正しいこと」を機械が保証する。D-1 はこれをしない。
- 測れるようにする = 原文のどの部分が、どの Claim になったかを明示し、
  原文 → Claim 化 → Evidence Binding → Core 検証 の **どこで壊れたかを分離できる**ようにする。

## 2. いまの構造(2026-10-07 に実測)

直近 run の Core 出力 `audit-core/fixtures/shogi/s8_real_run_core.json` より:

```
provenance.at = "observations[0]"
tally.by_state  = {GROUNDED: 58, UNVERIFIABLE: 17}
tally.by_form   = {aggregate: 49, direct_value: 26}
tally.by_reason = {"no_packet_ref(H-9 out of scope)": 17}
対象外 17 件は全件 pointers = []
席ごと: claude 15/57 = 26.3% / gpt 2/18 = 11.1%
```

つまり **席(LLM)が構造を直接出しており、文 → Claim の分解の段が存在しない。**
席は「何を主張したか」「何を根拠としたか」「どう構造化したか」を同時に決めている。
Core がどれだけ厳密でも、その前段の誤りは観測できない。

期待値 `audit-core/fixtures/xbrl/core_expectation_1B_v2.json` は
`source = core_expectation_1B.json + c1g_first_run_1B_P6.json` ― **自分の run から作った回帰の土台**であり、
誤りを混ぜた独立の正解集合ではない。したがって「false pass 0」は
「通していない」と「測っていない」を区別しない。この穴は D-1 では閉じない(D-2 以降)。

## 3. 目標の構造

```
LLM(席)        → 原文だけを出す
Claim Decomposer → Claim + 原文 span
Evidence Binding → evidence_pointer
Core             → 決定的な検証
```

鎖は次の形で、各段が次の段へ渡すものを schema で固定する。

```
original_text → span → claim_id → form → modifiers → evidence_pointer
```

**分解器の目的は「正しい Claim を作ること」ではない。**
「この原文のどの部分が、どの Claim として構造化されたか」を明示することである。
正しさの判定は Core が行い、分解の正しさは独立に測る。

## 4. D-1 の範囲(ここまでやる / ここから先はやらない)

D-1 は **LLM を 1 回も呼ばない。費用 0 円。**

やる:
- (a) 分解層の契約(schema)を 1 本新設する。鎖の 6 項目を必須にする。
- (b) span が原文に実在することを機械で確かめる門を作る(部分一致で通さない)。
- (c) **人が書いた原文 + 人が書いた正解の span/Claim**(手書きの正解集合)を作る。
      実装担当ではない席が作る。
- (d) 被覆の測定: 原文のうち **数が書いてあるのに Claim にならなかった文**を数える。
- (e) 萎縮の基準値を記録に固定する(下表)。

やらない:
- 席の指示文を変えること(原文だけ出させる変更は D-2)
- 実 run(費用が出るものは全部 D-2 以降)
- 誤りの混入(D-3 以降。誤り一覧の封印は実行者と別の者が行う)
- Core の変更(必要になったら **止めて人間に上げる**)

## 5. 設計判断

1. **席は原文だけを出す。** 席が原文と構造を両方出すと、分解層は単独で動かず独立に測れない。
2. **分解層の最初の試験は LLM も実データも使わない。** 手書きの原文と手書きの正解で測る。
   これが無いと分解器の出力を何と比べるのかが無く、「false pass 0」と同じ穴が分解層に再発する。
3. **被覆を測る。** 原文 → Claim の向きだけでは、数が書いてあるのに Claim にならなかった文を見逃す。
   それは検証されずに顧客へ届く主張である。
4. **同値異行・期間違い・単位違い・母集団違いは 4 つの検出器ではなく 1 つの規則。**
   いずれも「主語と修飾が、値を取った行に束縛されていない」。直しは
   「参照した行の定義的な欄を、Claim の主語・期間・単位・母集団と突き合わせる」の 1 つ。
   これは ①(定義値と数値 Claim の分離)で見つけた形の一般化である。
   **これが Core の比較の変更を要求するなら止めて人間に上げる。**
5. **既存の span 機構を使う。** `verifiedSpans` / `isFullyCoveredBySpan`
   (`scripts/playtest/lib/hypothesis.ts`)は部分的な重なりを通さない設計で、同じ規律を分解層に使う。

## 6. 萎縮を検出する指標(基準値を固定する)

| 指標 | 見るもの | 2026-10-07 の基準値 |
|---|---|---|
| Claim 総数 | そもそも主張が減っていないか | **75** |
| form 分布 | 構成が変わっていないか | **aggregate 49 / direct_value 26** |
| Binding Rate | 原文が Claim として拾われた割合 | D-1 で新設(いまは測れない) |
| 被覆されない数字入りの文 | 検証されずに届く主張 | D-1 で新設(いまは測れない) |
| UNVERIFIABLE | 対象外の割合 | **17 / 75 = 22.7%**(全件 `no_packet_ref`) |
| Detection Rate | 混入誤りを止めた割合 | D-3 以降 |
| False Pass Rate | 誤りを通した割合 | D-3 以降 |
| False Stop Rate | 正しいものを止めた割合 | D-3 以降 |

**検証率だけを見ない。** 難しい Claim(差分・合計・比較)を出さなくなることで
検証可能率が上がる「逃避による改善」が起きうる。
aggregate 49 / direct_value 26 はその検出の基準である。

## 7. 実験全体の順番(D-1 はこのうち ①〜② だけ)

```
① 分解層の設計                        ← D-1
② 手書きの正解集合で分解層を独立に測る  ← D-1
③ Claim Binding を固定
④ 実データで正常系を通す
⑤ 分解層の独立監査
⑥ 誤り一覧を第三者側で封印(実行者と別の者)
⑦ 原文に誤りを混入
⑧ 分解 → ⑨ Evidence Binding → ⑩ Core 検証
⑪ Detection / False Pass / False Stop を測定
```

⑥を④より先に封じる。**誤り一覧の sha256 を公開してから**正常系を通す。
そうしないと正常系を誤り集合に合わせて調整できてしまう。

## 8. 予測(封印。実装の前に書いた。外れは外れのまま残す)

v3 の規則に従い、**件数ではなく識別子の集合**で予測する(交わり / 予測のみ / 実測のみ)。
手で数えた数は書かない。数は門の出力行から読む。

| # | 欄 | 予測 |
|---|---|---|
| D1-1 | 新設する schema ファイル | `claim-decomposition.v0.1.schema.json` **1 本だけ** |
| D1-2 | 既存 schema の変更 | **0 本**(席の契約は D-2 まで触らない) |

| D1-4 | 設計判断 4 が Core の変更を要求するか | **要求しない**(Claim を複数に割って表現できる)。要求した場合は止めて人間へ |
| D1-5 | 手書きの正解集合の誤り | 実装担当以外が作るため、**最初の照合で不一致が 1 件以上出る**(0 件なら作成者が実装を見ている疑い) |

### 予測の独立性

D1-3 と D1-4 は従属する(4 が要求すれば 3 が崩れる)。**従属として明記し、別々の当たり外れとして数えない。**
D1-8 と D1-9 は独立(Golden は記録の面、試験は振る舞い)。
D1-5 と D1-7 は独立(前者は作成者の独立性、後者は材料の難しさ)。

## 9. 人間へ上げる予定の点

- 席の契約を「原文だけ」に変える判断(D-2)。これは席の出力の形を変えるので、
  現在の `seat-output.v0.1` を使う全工程に波及する。
- 設計判断 4 が Core の変更を要求した場合。
- 誤り一覧を誰が封じるか(実行者と別の者であることが条件)。

## 10. この計画が前提にしている外部の指摘

2026-10-07 の評価者の指摘のうち、採用したもの:
- GROUNDED は「Pointer 先の値と Claim の値が一致した」以上を意味しない。
- Claim の段階で誤りを混ぜると未検証の分解層を迂回し、検出率は構造上ほぼ 100% になる。
- 誤り一覧は作成者以外が作る。誤停止率には人が正しいと確認した集合を別に用意する。
- 検証率だけを上げると「逃避による改善」が起きる。Claim 総数と form 分布を同時に見る。

採用しなかったものは無い。

## 11. 追記(2026-10-07、封印後)― 正解集合が戻って出た 2 つの決定

封じた §8 は書き換えない。以下は §4〜§5 の補足であり、予測の訂正ではない。

**決-1. form の語彙は `docs/CLAIM_CONTRACT_SPEC_v0.2.md` の 4 語に従う。**
司令塔が実装担当へ渡した仕様に `direct_value | aggregate` の 2 語しか書かなかったのは**司令塔の誤り**。
正解集合は正本どおり 4 語で書かれている(実測: aggregate 5 / derived_value 3 / direct_value 1 = 9 件)。
schema の enum は正本に合わせる。**正解集合を仕様に合わせて書き換えない。**

**決-2. D-1 の照合では `subject` を字面一致で比べない。**
正解集合の `subject` は packet のパスではなく、人が文を読んで取った日本語の主語句である。
これは**正しい**。主語を packet のどの行に結ぶかは次の段(Evidence Binding)の仕事であり、
分解層の仕事ではない。D-1 の照合で比べるのは次の 5 つ:

| 比べるもの | 理由 |
|---|---|
| `span` | 原文のどこが Claim になったか(この層の本体) |
| `form` | 構造化の種類 |
| `value` | 数そのもの |
| `modifiers`(period / unit / population) | 文中にしか無い修飾を拾えたか |
| `expected_uncovered_number_sentences` | 被覆されなかった数字入りの文(萎縮の検出) |

`subject` は記録するが照合しない。**したがって D-1 では「同値異行」は検出できない。**
これは §1 の原則どおりで、D-1 は穴を閉じず、穴を測れる場所に移すだけである。
同値異行の検出は Evidence Binding の段(D-3 以降)で扱う。

**正解集合が意図的に仕込んだもの(作成者の報告より、司令塔が記録する)**
- `population` を 3 件(c5・c6・c7)意図的に `null` にした。文に母集団が無いため人は補わない。
  分解器が推測で「20 局」を補えばここで食い違う。これは §5-4 の検出対象を先取りした材料である。
- c9 の「3 回以上」の `3` を claim ではなく `population` の絞り込みに畳んだ。
  分解器が別の claim に切り出すか畳むかで差が出る。**どちらが正しいかは決めていない**(差が出ること自体が観測対象)。
- `evidence_pointer` は 9 件すべて `null`。人は packet を見ていないため指せない。
  **この正解集合は evidence_pointer を一切試験していない。**

**正解集合の sha256**: `6839f642a4ddbeb101b0b48ed7bacfccb83cc713a5d947397130bd1b285f07fe`
(`scripts/playtest/fixtures/decomposition/gold_01.json`、447 文字・18 行の原文、claim 9 件、uncovered 3 件)
