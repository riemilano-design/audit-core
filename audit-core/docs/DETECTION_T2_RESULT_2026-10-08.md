### 1-2. 検出率 ― 2 つ並べる

**検出 = 混ぜた後の Claim が GROUNDED ではない**(VALUE_MISMATCH / POINTER_NOT_FOUND / UNVERIFIABLE のどれでも検出)。
**その位置に Claim が 1 件も作られなかった場合は「止めなかった」**(人間の決定による定義)。

| | 検出 k | 分母 n | 値 | 両側 95% | 片側 95% 下限 |
|---|---|---|---|---|---|
| **条件付き**(混ぜる前に辿れていた主張に限る) | 30 | 30 | **100%** | **88.4 – 100%** | **90.5%** |
| **定義どおり**(拾われなかった現場も分母) | 30 | 30 (= 30 + ① 0) | **100%** | **88.4 – 100%** | **90.5%** |

**幅の方法: Clopper-Pearson(正確法、二項 CDF の二分探索)。**
両側は α=0.05 を 0.025 ずつ両裾に分け、片側下限は α=0.05 を下裾に全部使う。
検算: 片側 `0.05**(1/30) = 0.9049661471446958`、両側 `0.025**(1/30) = 0.8842966917779722`。
司令塔・実装担当・独立監査の 3 者が別々に計算して一致した。

**2 つの値が同じになったのは、①(拾われなかった現場)が 0 件だったからである。定義が同じになったのではない。**
①>0 のとき定義どおりの率だけが下がることは、合成入力の試験で固定してある
(混入 10・検出 10・① 5 → 条件付き 10/10 = 100%、**定義どおり 10/15 = 66.7%**、両側下限 0.6915 → 0.3838)。

| 族 | 混入 | VALUE_MISMATCH | POINTER_NOT_FOUND | 検出 | 止めなかった |

## 2. この数の読み方 ― 型 2 は易しい型である

**100% は「Core が強い」ことの証拠として読んではいけない。** 封に先に書いた読み方をそのまま採る:

> 高く出た場合 = **単位のずれは、桁が 1000 倍変わるので、値を照合すれば必ず止まる。これは易しい型である。**

理由はコードで決まっている(封の D-0、予測に数えない): `adapters/xbrl/recipes.py:201-203` は
`V.UNIT_SCALE`(`百万円 1e6・千円 1e3・億円 1e8・兆円 1e12・円 1`)を掛け、許容は
`max(0.5*10^-decimals, 0.5*claim_scale)`(`vocabulary.py:115-127`)である。
**金額の族の中で単位をずらせば 1000 倍以上ずれるので、束縛されている Claim なら必ず VALUE_MISMATCH になる。**

**この封で測れた本当の値は、率ではなく次の 3 つである。**

1. **① = 0** ― 抽出器は、単位を持つ量の数を 1 つも取りこぼしていない(§3-1。ただし構造的)。
2. **③ = 47/175(27%)** ― **型 2 の現場の 4 分の 1 以上が、誤りを混ぜる前からすでに辿れていない。**
   混ぜる余地がそこに無い。これは誤停止の側の数(`DETECTION_BASELINE_XBRL_2026-10-08.md`)と地続きである。
3. **② = 68/175(39%)** ― **同じ数字が書類の中で 2 回以上出ると、どの出現の主張かを機械で決められない。**

**率よりこの 3 つのほうが買い手に意味がある。**

## 3. 限界(測っていないこと・測れなかったこと)

### 3-1. ① = 0 は構造的である。予測の当たりに数えない

実測した前提(3 書類すべて):

| 確かめたこと | `S100Z4Q1` | `S100Z4B6` | `S100YMFV` |
|---|---|---|---|
| 型 2 の現場が Adapter の `iter_numbers` の部分集合でない件数 | 0 | 0 | 0 |
| 現場のうち除外(`EXCLUDE_AFTER`/`EXCLUDE_CONTEXT`)が発火した件数 | 0 | 0 | 0 |
| **書類全体での**除外の発火回数 | **0** | **0** | **0** |

**部分集合であり、除外が一度も発火しないので、① = 0 は構造的に決まる。外れようがない欄なので当たりに数えない。**

### 3-2. ② の 68 件は「区別できない」件数である

正確な形は **「107 件(175 − 68)については確実に ① ではない。68 件については区別できない」**。
②は「同じ数字 + 単位を持つ主張が 2 件以上ある」ことしか言えないので、
**その特定の 1 回の出現が主張になったかは、数字の一致だけでは言い切れない。**
68 件は全部、位置(文字オフセット)と前後 40 字つきで出力に残してある。

### 3-3. 残った 107 件には偏りがある

測ったのは「書類の中で数字 + 単位が 1 回だけ出る数」だけである。
**何度も言及される数 ― 重要だから繰り返し書かれている数 ― が体系的に除外されている。**
②の 68 件の実例: `35億円`(`S100Z4B6`)は本文の 718 字目と 6,937 字目に**同じ文がそのまま繰り返されて**いた。

### 3-4. 「止めなかった」の側は、実物では一度も観測されていない

**族ごとの「止めなかった」は 3 書類とも 0 件である。** つまり
**「検出率 100%」は反証例が 1 件も出なかったということであり、0 の上限が 0 だという証拠ではない。**
不確実性は Clopper-Pearson の片側下限 **90.5%** で読む。
`detected=False` の集計が正しく動くことは**合成入力の試験でのみ**確かめてある
(混入 10・未検出 3 → 検出 7・止めなかった 3、族別に money 2・ratio 1 へ割れる)。

### 3-5. 除外の 2 つの枝は、実物では検証できていない

`EXCLUDE_AFTER` / `EXCLUDE_CONTEXT` が 3 書類で 1 回も発火しないため、
**計器がこの 2 つを Adapter と同じように扱っているかは、字面の比較と合成入力の試験だけで確かめている。**
窓のリテラル(`s[b:b+3]`・`s[max(0,a-12):b+4]`)が Adapter と計器の 2 か所に重複して書かれているので、
**将来 `extract.py` 側だけ変わっても実データでは気づけない。**

**`after` 窓を 3→4 に広げる変異は真の等価変異である** ―
`EXCLUDE_AFTER` は `^(年|月|日|期|頁|ページ|四半期|号|条|項|回目)` で `^` 固定の `.match()`、
**最長の選択肢が 3 文字**(`ページ`・`四半期`)なので、3 文字以上に広げても真偽が変わらない。
振る舞いで留められないので、**前提(選択肢が全部 3 文字以下)を検査する試験で代替した。**
将来 4 文字以上の語が増えたらその試験が赤くなる。窓を縮める方向(3→2・`a-12`→`a-11`・`b+4`→`b+3`)は全部赤になる。

### 3-6. チェックイン済みの試験に無い退化値

空の混入配列・`drawn=0` かつ ①>0 の 2 つは、**試験としては入っていない**(独立監査が手で関数を呼んで
例外なく妥当な値を返すことを確認した)。`test_broken_implementation_*` 2 本は本物のモジュールを
書き換える形ではなく、壊れた実装を試験ファイル内で再現して比べる形である。
**本物のモジュールへの変異当ては、実装担当と独立監査がそれぞれ別に行い、どちらも狙った試験が狙った理由で赤になった。**

### 3-7. 将棋側は測っていない

**冊子の Claim を Core へ渡す経路が存在しない。** 根拠: `audit-core/adapters/shogi/recipes.py:128` の
`build_recipes(seat_envelopes, packet)` は**席の封筒(仮説の出力)**を入力に取り、分解器の Claim を取らない。
繋ぐのは別の段である。したがって**この文書の数は有価証券報告書の経路だけの数**であり、
将棋の経路(AI が書いた冊子 + AI の分解器 + Core)の数と**同じ表に並べてはいけない。**

### 3-8. 型 1・型 3・型 5 はこの封では測っていない

人間の事前の決定(3 回目の差し戻しの帰結)により、**参照一覧に頼らない型だけで実 run に進んだ** ―
`t2_sites` だけが参照一覧を使わない。型 5 は「道具の不備で未測定」として凍結
([INJECTION_TOOL_AUDIT3_RESULT_2026-10-08.md](INJECTION_TOOL_AUDIT3_RESULT_2026-10-08.md))。
型 1・型 3 は、金額の桁の直し(独立監査 GO)の後に**別の封で追加測定する**(人間の指示 2026-10-08)。
期間・母集団の入れ替え 344 件は人が作るもので未測定。

### 3-9. 参照側の単位の族は非対称な設計である

金額の桁の封で `unitRef="JPYPerShares"` を `JPY` と別の族(`円/株`)に分けた(人間の決定:分離は残す)。
**これは非対称である** ― **参照側だけを分けており、本文側のトークンは未対応**である。
本文が「1株当たり当期純利益は69.64円」と平文の「円」で書く一方、XBRL は `JPYPerShares` で記録するため、
**族を分けると両者が一致しなくなる。** 実測した損得(3 書類):

```
分けた   : S100Z4Q1 db=3 id=0 / S100Z4B6 db=48 id=16 / S100YMFV db=8 id=1
分けない : S100Z4Q1 db=3 id=0 / S100Z4B6 db=48 id=16 / S100YMFV db=9 id=2
利得 0 件 / 損失 1 件(「69.64円」→ BasicEarningsLossPerShare)
```

**この 3 書類では利得 0・損失 1 である。** 残す理由は、独立監査が示した risk ―
`円/株` の参照値には `65.0・70.0・75.0・80.0`(Q1)、`1.0`(B6)、`14.0・16.0・18.0・24.0`(MFV)のような
**小さい丸い数**が実在し、本文中の単価・手数料・調整額などの「総額」として偶然同じ数字で出うる。
**3 書類で衝突 0 件なのは標本が 3 件だからで、risk が消えたことではない。**
本文側の「○株当たり」を読む拡張は**入れていない** ― 封じた予測 S-6(「69.64 円は残る」)は**外れ**であり、
**外れを当たりに変えるために実装を足すのは禁じた型**だからである。S-6 は外れのまま固定する。

## 7. 試験の本数の食い違い(記録)

実装担当は「全体 449 本 OK」と報告し、独立監査は同じ凍結ツリーで **pytest をフルに回して 537 本**(全部緑)を実測した。
**司令塔が同じツリーで両方を自分で回し、どちらの数も再現した**(どちらも全部緑):

| コマンド(`audit-core/` で実行) | 本数 |
|---|---|
| `python3 -m unittest discover -s tests -t .` | **449 本 OK** |
| `python3 -m unittest discover -s tests/fixtures -t .` | **65 本 OK** |
| `python3 -m pytest -q` | **537 passed** |

**食い違いではなく、集める範囲と数え方の違いである。** 以後、**本数を書くときは使ったコマンドを添える。**
自分の記憶「件数は推測せず件数の行を読む」の型である。
