**(c) が成立する条件の中に (d) が入っていた。** (c) が正しくても (d) が壊れていれば (c) は効かない。この依存を封じる前に確かめていなかったため、**「次の実 run で (c) が効かなかったら (c) の問題」と読み違える危険があった**。(d) を同じ封に相乗りさせたのは偶然であり、設計の結果ではない。

### 10.2 工程の直し(第 3 版に 3 項を追加した)

`docs/AGENT_PROTOCOL.md` に次を足した。

1. **(2) 予測の対象を「件数」ではなく「識別子の集合」にする。** 実測の後に `intersection` / `predicted_only` / `observed_only` の 3 つへ機械で割る。「何件当たった」を「**どの検査を見落としたか**」に変える。件数は集合から機械で出す。
2. **(3) 機械で取れる数を手で打たない。** ファイル数・行数・件数・sha・差分の件数・試験の本数・変異の本数は、コマンドの出力をそのまま貼る。c4 は予測モデルの誤りではなく入力経路の誤りだった。
3. **(4) 予測項目の独立性を、封じる前に 1 回確かめる。** 項目ごとに、成立に依存する境界・関数・契約・記録面を列挙し、他の項目がそれを変更または検証していないかを見る。**独立と判断した場合も根拠を 1 行残す。** 依存していたら同じ束として扱い、「どちらが壊れていたら効かないか」を書く。

この問いは、d2 のような**沈黙していた試験**を見つける入口にもなる。沈黙が覆っている入力の形が、別の項目が頼っている形だった。**将棋以外の Adapter に広げるときも同じ規律を使う。**

## 11. 追記(2026-10-07) ― S-3 の run を Golden の土台に採用しない判断の固定

人間の判定により、現状維持とし、理由を履歴として固定する。

- **S-3 の run(2026-10-06、費用 4.5351 USD)は実 run として成立した。** 「悪い run だったから」除いたのではない。
- **除いた理由は、Golden が守る契約の世代を混ぜないため。** S-3 は指示文 v1.3・契約 `hypothesis.v0.4`(`observations` に `minItems: 1`)の時代の記録であり、現行の土台(v1.4 以降・`v0.5`)と世代が違う。1 つの土台に 2 世代を混ぜると、以後の差がどちらの世代の変化なのか読めなくなる。
- **代償を明記する: v1.3 時代の封筒の形は、現行の Golden では回帰を保証しない。** これは欠陥ではなく、**Golden の世代境界をどこに置くかという設計判断**である。
- S-4 の run は claude 席が HTTP 400(残高不足)で立たず**完走していない**ため、そもそも土台の候補ではない。
- この判断は人間が覆してよい。覆す場合は、世代の違う記録を同じ土台に置くことを明示し、差を読むときに世代で割る手順を決める必要がある。
