## 6. 限界

封 §8 と日付つきの追記の限界のうち、この結果に効くもの(字は封の側が正本):

- **書き手も読み手も同じ model**。段 1 の読みも全行が道具に揃っており、K-3・K-4 はこの読みに依る。読みはエージェントの読みで、人の目は無い。
- **読む行が少なく一社に寄る**。K-3・K-4 の閾値は読む行の数に対して緩い。
- **注入は 2 型だけで、DB と原本の差の実際の分布ではない**。ρ は T8_REL の変え幅から決めたので K-2 は作りから当たりやすい(封 §10-2)。DB と原本の差が ρ を超える行は P27E でも名指さない。
- **文2(DB の値 = 翌期の有報の前期の欄)はこの標本で起きえない**。段 1・段 2 の会社は最新の有報で、翌期の有報が存在しない(封の追記: EDINET DB の 2026-10-27 の説明)。段 1 の R-10 の実測 0 も一部この構造による。**K-1〜K-5 はこの型を測らない。**
- **評価用は使い切った**。規則を直すなら新しい封と新しい標本で(封 §4)。
- **Cabocia の利用者の三本は第二の評価用**として別の便で測る(同社の表示の直しの公開の後。文の sha256 を先に commit し、R の後に 4 profile で)。この結果の判定には使わない。
- **評価用の XBRL は見たことのある書類**で、新しいのは AI の文の側だけ(封 §8)。会社は 5 月決算の中小型に寄る。
- **書き手と読み手の席は repo の作法の文書と記憶の索引を文脈に持っていた**(段 1 の封の追記)。
- 率の分母は行で、書類は独立でない(claim の多い書類が多くの注入を持つ。表 書類別)。群別の率の差は書類との交絡を含む。
- P27E を有報の原文に当てると偽の「違う」が増える。P27E は有報の原文用の profile ではない。
- 「この封の席・実装の席・この結果を書いた席は評価用の文を開いていない」は git で証明できない。証明できるのは、評価用の文の sha256 が S2 より前に凍結され(W)、評価用の記録が S2 と E の後に足されたことだけ(順序の門)。【門なし】
- repo だけでは再現できない(応答と文は repo の外にあり、再配布できない)。repo の sha256 は「この測定のときの材料」を指すだけ。
