# 止まった数字の「見る順」の診断(2026-11-12)― 封なしのあと知恵

## 0. これは何か

- 買い手の立場で価値を試算したとき(2026-11-12)、いちばん大きい課題は「止めすぎ」だった。道具が止めた数字を、人が全部同じ重さで見直すことになる。
- そこで、**止まった数字のうち、どれに誤りが集まっているか**を、既に在る記録から数え直した。engine は呼ばない。有料の席も呼ばない。0 USD。
- 入口は `measure/xbrl_stop_triage_2026-11-12.py`、記録は `fixtures/xbrl/aiforms/stop_triage_2026-11-12.json`、門は `tests/measure/test_xbrl_stop_triage_diag.py`。
- 人間の言葉 2026-11-12「君に任せる進めて」(止まった数字の内訳を記録から出す、という司令塔の案への返事)。
- **封は無い。** 組の決め方は、FX の全体の数を見たあとに決めた。だから FX の全体の数は「当てはめた結果」で、検証ではない。検証に使えるのは、数える前に予測を書いた割り方(§2)だけ。
- **札(真・偽・判定不能)は盲検の AI の席が付けた。人は付けていない。**

## 1. 組の決め方(判定は足さず変えない。state・reason・engine が持つ証拠の欄から引くだけ)

| 組 | 中身 | 読み手にとっての意味 |
|---|---|---|
| 赤 | `VALUE_MISMATCH`(下の黄を除く)+ `POINTER_NOT_FOUND` の `no_element`・`no_same_value` | 先に見る |
| 黄 | `VALUE_MISMATCH` のうち、engine の証拠の欄 `last_branch_evidence` が `same_element:Prior` で始まる行 | 道具は「違う」と返したが、同じ項目の前期の値とは合っている |
| 灰 | 止まった残り(主語が無い・率の元の数が無い・候補が複数 など) | 道具が決められなかった |
| 緑 | `GROUNDED` | 一致 |

## 2. 予測(割った数と別の 2 組を数える前に書いた字。そのまま)

- 下の囲みは、数える前に書いた file の中身そのまま(sha256 `f22b997d68cf3598a7f91f6510ccc63992de01f5514cb5a5cf46ff74ce13300f`。門が囲みの字の sha256 をこの値と比べる)。
- **順序の証拠は弱い。** 予測の file は commit していない(作業用の場所に書き、同じ 1 回のコマンドの中で sha256 を出してから数えた)。commit の順では示せない。
- 予測の「F1〜F4(`P28E`・札のある行)」「F5」は、この診断より前に数えたことが無い組。

## 4. 読み(表の数の言い換えだけ。新しい数は足さない)

1. **誤り(札 偽)は赤に集まる。** FX・F1〜F4・F5 の 3 組のどれでも、赤の偽率は全体の 3 倍以上で、偽の 7 割以上が赤に在る(表 1・表 5)。
2. **黄には偽がほとんど無い。** 道具は「違う」と返しているが、engine 自身が「同じ項目の前期の値と合う」という証拠を持っている行。いまの報告はこの証拠を出していない(`adapters/xbrl/report_customer.py` は `last_branch_evidence` を読まない)。
3. **灰の偽率は、3 組の全体では全体の偽率以下。** ただし予測に無かった割り方では 2 か所で外れた(表 6: FX の書き手の片方、F1〜F4 の形の 1 つ)。
4. **緑(一致)にも偽が残る。** 道具が通した誤りで、見る順では拾えない(表 1 の緑の列)。
5. **FX の偽は 1 社に偏る。** その 1 社を除いても向きは同じだが、赤の取り分は下がる(表 1 の「除く」の行・表 4)。
6. **予測は全部当たった。** 外れうる形で書いたが、閾(3 倍・7 割)が緩かった可能性がある。予測に無かった割り方(表 6)で外れが 2 か所出たことを、同じ重さで読む。

## 5. 言えないこと

- 「赤だけ見れば足りる」とは言えない。灰にも緑にも偽が残る(表 1)。言えるのは**見る順**だけ。
- 札は AI の席の 1 席目で、人は確かめていない。文の書き手は Claude の 2 つの model だけ。客の実物の文では測っていない。
- 組の決め方は FX の全体を見てから決めた。F1〜F4・F5 は古い profile(`P28E`)の判定で、札の無い行が在る(表 1 は札のある行だけ)。
- 黄の行が「前期の数を当期の数として書いた誤り」なのか「前期の数を正しく前期として書いた行」なのかは、この診断では分けていない。札 真が大半なので後者が多いと読めるが、1 行ずつは読んでいない。

## 6. 次の手(まだやっていない)

- **報告に「見る順」を足す案。** 「違う」の節のうち黄の行を「前期の値と一致」として分け、「要確認」の節を理由で 2 つに分ける。判定(state・reason)は変えない。`adapters/xbrl/report_customer.py` は engine の側の file なので、人間の承認と封が先。
- **人の目での確かめ。** 黄と赤から何行かを人が読む。札が AI の席だけ、という限界を外せるのはこれだけ。
