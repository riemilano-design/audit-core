# 報告の装置(入口の JSON → 人が読める Markdown)

人間の決定(2026-10-13、パッケージ): 譲渡の土台と**並行**して、既存の XBRL 検証結果を人が読める形にする。議事録 adapter はこの後、相手の用途・需要を確認してから。

## 0. なぜ要ったか

入口 `verify_document` は Claim ごとの state・pointer・reason を JSON で返すが、人が読む形が無かった。DD の束・デモ・委託の成果物の**全部の出口**がこれ。

## 1. 何を作ったか

`adapters/xbrl/report.py` ― `render_markdown(out) -> str`(純粋関数)と CLI `python3 -m adapters.xbrl.report --in out.json --out report.md`。

- **判定を足さない。** JSON の state・pointer・reason・値を並べ替えるだけ。LLM なし、通信なし、Core を import しない(境界の試験はそのまま緑)。
- 並び: 書類レベルの旗と件数の表 → **VALUE_MISMATCH**(文の値 / 根拠から出た値 / pointer / 理由 / 文)→ POINTER_NOT_FOUND → UNVERIFIABLE → GROUNDED。知らない state は「その他の状態」の節に落とす(黙って捨てない)。
- 規則の字(`document.rule`)をそのまま印字。engine の指紋と入力の sha256 を頭に。
- 数は桁区切り、整数の float は整数で、小数は末尾の 0 を落とす。表の欄の `|` と改行は潰す。

## 2. 留めたもの [測定]

| 試験 | 何を留めるか |
|---|---|
| golden バイト一致 ×2(S100Z4N9 原文 186 件・S100Z4Q1 + AI 文 412 件) | 実出力 2 件(`fixtures/xbrl/entry_output_*.json`、入口が実際に書いたもの)からの報告が `fixtures/xbrl/report_golden_*.md` と**バイト一致** |
| golden の sha256 を字で留める | 記法を変えたら必ず赤 |
| 同じ入力 2 回で同じバイト列 | 決定論 |
| 全 Claim が 1 回ずつ、**自分の state の節にだけ**現れる | 再分類していない・落としていない |
| 節の件数と件数の表 = JSON の件数 | 数を作っていない |
| 規則の字がそのまま載る / 旗は JSON から読む(再計算しない) | 判定を足さない |
| 知らない state は「その他」へ | 黙って捨てない |
| 数の書式・欄の潰し・文字の主張は word | 書式 |
| CLI が golden と同じバイトを書く | 入口と同じ経路 |

13 本(凡例の試験を含む)。関連する入口 23 本・境界 12 本と合わせて 48 本緑。

### 2-1 変異(壊したら赤くなるか)[測定、変異ごとに新しい bytecode の置き場]

| 変異 | 予測 | 実測 |
|---|---|---|
| 節の順を入れ替える | golden・CLI の 2 本赤 | 2 本赤 |
| reason の無い行を黙って落とす | golden 2 + 全 Claim 1 回 = 3 本赤 | 3 本赤 |
| 桁区切りをやめる | golden 2 + fmt_num = 3 本赤 | 3 本赤 |
| 旗を JSON から読まず GROUNDED 0 件で再計算 | 旗の試験 1 本赤 | 1 本赤 |
| golden を 1 字変える | sha + golden + CLI = 3 本赤 | 3 本赤 |
| 凡例を消す | 凡例 + golden + CLI = 3 本赤 | 3 本赤 |

6 本とも予測どおり(凡例を足した後に 6 本を打ち直した)。復元は sha256 で確認。

## 2-2 独立監査 [記録]

判定 **GO**(問題点なし)。監査席が独立にやったこと: `report.py` 全文を読んで判定の再計算・言い換え・間引きが無いことを確認 /
入口を自分で再実行して commit 済みの fixture と diff(engine の指紋以外は完全一致 ― fixture は本当に入口の出力)/
golden を `cmp` でバイト一致 / 別の変異 2 本(state の名札を別の名札に言い換える → 4 本赤、pointer を 1 件だけ印字 → 2 本赤、予測どおり)/
記録の数 12・23・12・47 を実測で一致。

**所見 3 件(読みやすさ)と対応**: (1) VALUE_MISMATCH の節で「理由」欄が常に `―`(その状態には reason が無い)、
(2)「文」欄は span(抜粋の窓)で語の途中で切れる、(3)`―` が「値が無い」と「見つからなかった」の両方に見える。
→ **凡例 1 段落**を件数の表の下に足した(「文」は抜粋の窓で全文ではない / `―` は欄が無い状態、空欄は値が空 /
「理由」は止めた状態にだけ付く)。出力のバイトが変わるので golden を作り直し、sha を留め直し、変異 6 本を打ち直した(上の表)。
この凡例の差分は同じ監査席に差分だけ見てもらった → **GO**(問題点なし)。監査席の実測: `report.py` の差分は凡例 5 行だけ /
golden を作り直して `cmp` でバイト一致、sha256 も試験の字と一致 / 13 本・48 本緑。

監査席の変異 1 本は**予測が外れた**(そのまま記す): 凡例の中の「―」の説明の 1 文だけを消す → 予測 3 本赤(golden・CLI・凡例の試験)、
実測 **2 本赤**(golden・CLI)。凡例の試験は `「―」` の**文字列**の有無を見ており、同じ文字列が凡例の最後の文にも在るので緑のまま残った。
歯止めとしては golden のバイト一致が消した文を捕まえている(凡例の字は golden が所有する。[[pin-each-property-in-one-owner]] の型)。
凡例の試験は「凡例が在る」ことの約束であって文ごとの約束ではない、と読む。文ごとに留めたくなったら golden を見る。

## 3. 使い方

```bash
python3 -m adapters.xbrl.verify_document --doc S100Z4N9 --out out.json
python3 -m adapters.xbrl.report --in out.json --out report.md
```

## 4. していないこと

- 顧客向けの体裁(PDF・画面)。Markdown まで。
- 文の誤りか結び先の誤りかの判断(VALUE_MISMATCH の節に「この表では決めない」と書いてある)。
- 書類の名前の表示(入力に docID が無いので instance の名前を使う)。
