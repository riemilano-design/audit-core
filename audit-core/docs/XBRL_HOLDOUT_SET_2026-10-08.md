## 2. どう取るか ― `--pick 5`(同じ窓・同じ種)

`fetch_material.py` は `random.Random("<種>|edinet-pick|<from>|<to>").sample(rows, k)` で選ぶ。
**`rows` の並びは `(日付, docID)` で決まっており、k を変えても選ばれる index の列は前方一致する。**
これは実装の細部に頼る話なので**推測せず実測した**(候補 183 件・この種の文字列):

```
k=1 -> [31]
k=2 -> [31, 152]
k=4 -> [31, 152, 119, 3]
k=5 -> [31, 152, 119, 3, 34]
前方一致: True
```

**index 31 がすでに取った `S100Z37J`** である(`--pick 1` で取れたものがこれ)。
だから**同じ窓・同じ種で `--pick 5`** を回せば、

- 1 件目 = `S100Z37J`(**再取得。sha が `d8337184477d6554…` と一致することの照合になる**)
- **2〜5 件目 = 新しい 4 件**

が取れる。**窓も種も変えない**ので、選び方は最初と同じ 1 つの封に従っている。

### なぜ `ADAPTER_USED` に `S100Z37J` を足して `--pick 4` にしないのか

それが本来の直し方である(道具の規約は「`ADAPTER_USED` は選ばない」)。
**だが `fetch_material.py` は本線の作業ツリー(`/Users/midoriko/Desktop/sgogi-coach`)に在り、
このブランチには存在しない。** 共有の木をこの席から書き換えるのは、
並行する席の作業を壊す型の事故なので**しない。**

**本線の担当へ申し送り:** `audit-core/measure/fetch_material.py` の
`ADAPTER_USED = {"S100Z4Q1", "S100Z4B6", "S100YMFV"}` に `"S100Z37J"` を足すこと。
足すと候補が 182 件になり index の対応が変わるので、**足すのは今回の取得の後**にする。

### 取得が封と合っているかの確かめ方(出力を見るだけで分かる)

1. `candidates: 183` であること。**183 でなければ index の対応が変わる**(EDINET に遅れて
   提出が足された等)。その場合は 1 件目が `S100Z37J` にならないので、出力で分かる。
2. `fetched S100Z37J` が **1 件目**に出て、**sha256 が `d8337184477d6554` で始まる**こと。
3. 残りの 4 件が `S100Z4Q1`・`S100Z4B6`・`S100YMFV`・`S100Z37J` のどれでもないこと。

## 5. 封の照合 2 が外れた ― **ZIP の sha256 は封に使えない**

### 5.1 何が起きたか

`S100Z37J` を取り直したら、**バイト数は同じ 541,790 のまま sha256 が変わった。**

```
1 回目(2026-10-08): sha256 d8337184477d6554…
2 回目(同日、--pick 5): sha256 74c51c983fe55d0b…
```

**原因を機械で特定した。** ZIP の中の 31 メンバーの**日時が梱包した時刻**になっている
(26 件が `2026-10-08 15:59:36`、5 件が `15:59:34` = 取り直した瞬間)。
**EDINET は要求ごとに ZIP を作り直すので、ZIP の sha256 は原理的に再現しない。**

### 5.2 中身は同じだった(測り直して証明した)

`measure_xbrl_fix5_2026-10-08.py` を取り直した ZIP で**もう一度全部回し**、
コミット済みの記録と**欄ごとに**突き合わせた。

> **23 構成すべての `tally`・`rows`・`info`・`diff` が 1 欄も違わない。**
> 違ったのは `zip_sha256` だけ。

**だから `XBRL_HOLDOUT_RESULT_2026-10-08.md` の数(`P7` 51.9% → `P13` 38.0%)はそのまま有効である。**

### 5.3 直したこと・直さないこと

**足した道具**: `fixtures/xbrl/zip_content_digest.py` ―
メンバーの**名前・CRC・展開後の大きさ**だけを名前順に並べてまとめた sha256。
**梱包の時刻・並び・圧縮の強さに依らない。** 中身は展開しない(中央ディレクトリを読むだけ)。

| 書類 | 中身の印 |
|---|---|
| `S100Z4Q1` | `5ab0f4a38bb2b16d…` |
| `S100Z4B6` | `50df724a916b0f92…` |
| `S100YMFV` | `4bbdaf4cedc69d7c…` |
| `S100Z37J` | `99493b5a701acfee…` |
| `S100Z4N9` | `ac0e0ff002519bf1…` |
| `S100Z433` | `bab2479e65647061…` |

**取り置きの 2 件(`S100Z1WR`・`S100Z39P`)の印は作らない。**
§3 で「**ZIP を開かない**」と字で書いたからである。中央ディレクトリを読むだけでも
「開かない」には反する。**自分で封じた規定を自分で破らない**(前に同じ型を踏んでいる)。
その 2 件の拠りどころは **docID と、測った記録が存在しないこと**である。
**人間が「中央ディレクトリだけは読んでよい」と決めれば印を作る。**
