## 1. なぜ今これをやるか

D-2a で分母は 4 本・claim 37 件になった。しかし**分解器が存在しないので「分解の正しさ」は 1 ミリも測っていない**
(D-2a 結果 §3)。いま LLM を呼んでも、**出力を正解集合と比べる機械が無い。** 先に作る。

さらに、**基準線が無いまま LLM の数を見ても意味がない。** 素朴な規則ベースの分解器を先に作れば、
「LLM が規則ベースをどれだけ上回ったか」が言える。規則ベースに勝てないなら、それ自体が決定的な情報である。

## 2. やること(LLM の API を 1 回も呼ばない。費用 0.00 USD)

- (a) **D-1 の負債を閉じる**: `decompositionProblems` の単独 export をやめ、`checkClaimDecomposition` を唯一の入口にする。
      試験の呼び出しを入口経由へ移す。**規約(コメント)を構造に変える。**
- (b) **照合器**を作る。分解器が出した doc と、正解集合(`gold_*.json` の `expected_claims`)を比べ、
      次の 4 つを返す純粋関数にする。
      | 指標 | 中身 |
      |---|---|
      | span 一致 | 正解の claim と同じ `[start,end)` を出した件数(交わり / 正解のみ / 実測のみ) |
      | value 一致 | span が一致した claim のうち `value` も一致した件数 |
      | form 一致 | span が一致した claim のうち `form` も一致した件数 |
      | uncovered 集合 | 被覆されない数字入りの文の集合の一致 |
      **件数だけでなく集合(交わり / 正解のみ / 実測のみ)で返す。**
- (c) **基準線の分解器**(規則ベース、LLM なし)を作る。句点で文を切り、数を拾い、
      数のある文を 1 claim として `form: direct_value` を当てる、程度の素朴なもの。
      **良くする努力をしない。** これは下限を測る道具であって、製品ではない。
- (d) (c) を (b) に通し、gold 4 本に対する基準線の数を記録する。

やらない: LLM の分解器(D-2b)、席の契約の変更(D-2b)、`gold_*.json` の変更(**1 本も触らない**)、Core の変更。
