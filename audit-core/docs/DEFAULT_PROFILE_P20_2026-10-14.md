# 既定の規則セットを `P16` から `P20` へ(2026-10-14。**人間の決定**)

人間の決定(2026-10-14): 「**`DEFAULT_PROFILE` を `P20` に変更する。**今回の目的はエンジン全体を合格認定することではなく、
P16 と P20 のどちらを既定にするのが妥当かを判断すること」「**ただし、エンジン全体の品質合格とは認定しない。**」

`DEFAULT_PROFILE` の変更は CLAUDE.md の「委任されないもの」であり、**司令塔は決めていない。**

## 1. 判断の根拠(**P16 と P20 を分ける 3 つの数。すべて独立監査 GO 済み**)

| 分ける数 | 結果 | 出どころ |

| 連結の無い書類での P20 の新規接続 | **N-1 60.5% / N-2 5.3% / N-3 0 件**(母数 21 行) | 同 §1 |

**Q1(engine 全体の E2/G = 11.6%、合格線 10% 未達)は P16 と P20 を分けない。**

**11.6% はどちらを既定にしても残る。**

## 4. 既定の変更で動いた面(**3 本の赤。原因は 1 つだった**)

落ちた 3 本はすべて **`S100Z3HP` と `S100Z433`**(連結の要素 **0 件** = 連結財務諸表を作っていない会社)が
P20 で結ぶようになったことが原因。**設計どおりの変化である。**

| 試験 | 直し方(**記録した P16 の数は 1 つも書き換えていない**) |
|---|---|
| `RobustnessTableTest` | 表は **P16 の測定の記録**なので数は据え置き、`profile_name="P16"` を明示して回す |
| 同(新しい試験) | **既定で動くのはこの 2 書類だけ**であることと、その P20 の止めた件数 **19 / 30** を字で留めた |
| `DocumentLevelRuleTest` | P16 の事実は profile 明示で残す。試験名に `_under_p16` を付けた |
| 同(新しい試験) | **既定の経路でこの 2 書類の旗が外れ `GROUNDED > 0` になること**を門にした(字ではなく振る舞いで) |
| `OutputStabilityTest` | 字で留めた sha を更新。**古い値もコメントに残した** |

**sha が動いた理由を測った**: `S100Z4B6`(連結要素 147)は P16 と P20 で **profile 欄の字だけが違い**、
profile 欄を除いた本体は **byte 単位に同一・行の差 0 件**。

### 4-1. 14 書類の実測(**P16 の記録は全件そのまま再現した**)

| 書類の別 | 件数 | 既定を変えて動いたか |
|---|---|---|
| 連結の要素 > 0 | **12** | **1 行も動かない** |
| 連結の要素 = 0(`S100Z3HP`・`S100Z433`) | **2** | **動く**(止めた件数 62 → 19、87 → 30) |

**副産物**: この 2 書類は以前「fact の取り方の問題」として扱われていたが、実体は同じ連結・単体の問題だった。
頑健さの 14 書類では連結なしが **2 / 14**。

### 4-2. 門が両方向に噛むことを確認した

既定を `P16` に戻すと**新しい試験を含む 4 本が赤**、`P20` で **25 本緑**、実装は byte 単位で元のまま
(`git diff --stat -- adapters/` が空)。**緑が「届いていないだけ」ではない。**

## 5. 回帰確認(**`dd3cff1` を凍結して撮った。数はログから機械で取り出した**)

| 面 | 結果 |
|---|---|
| pytest(path 指定なし = `measure/tests` を含む全数) | **1185 passed**(19 分 55 秒) |
| unittest discover `-s tests -t .` | **Ran 1050 / OK** |
| 変異 89 本 | **緑**(16 分 43 秒) |

**変異の「緑」が何を保証するか**: 試験は `mismatches == []` を **assert** しており、
**89 行すべてが記録した予測どおり**(既知の等価変異 `X-R7b` は `actual_first_measurement` で固定)。
「予測どおり 88 本」の印字は参考で、門は assert の側。

ログは `fixtures/xbrl/default_p20/evidence_2026-10-14.txt`、そこから取り出した数は
`suite_evidence_2026-10-14.json`。ログの 4 か所の `HEAD` がすべて `dd3cff1` で一致し、
run の前後の `git status` が空であることもログに在る。

**Q1・Q2・Q3 は測り直していない**(人間の指示: 「今回の証拠を再取得するのではなく、変更箇所に限定した回帰確認」)。

### 5-1. 証跡の作り方で踏んだ 2 つ(**記録として残す**)

1. **最初の証跡 script は discover の `Ran / OK` 行を取れていなかった**(`tail -3` が試験自身の標準出力に
   押し出された)。行を名指しで取る形に直して撮り直した。**別 run だが HEAD は同じ**で、ログに両方の HEAD が在る。

   `adapters/` を書き換えない処理だが、「測定中に余計なものを走らせない」という規律からは外れている。
   **実害が無かったことは測定で裏付けた**: 変異試験の `test_real_source_sha256_unchanged_after_mutation_run` が緑。
