# 国会会議録の限定デモ ― 計画と予測(封印、2026-10-14)

## 0. 人間の決定(2026-10-13、DECISION_LOG D-023)

- 国会会議録は規約確認後に限定デモへ使う(法務 3 項目は人間が 2026-10-13 に「問題なし」と判断)。
- 最初のデモでは対象を絞る: **発言番号が実在するか / 発言者が一致するか / 引用文が実際の発言と一致するか / 数値などの主張が根拠と一致するか**。
- 結果が良くても、**一般的な議事録に対する精度とは主張しない**。
- 議事録 adapter の本実装は、相手の用途・需要の確認後に判断する(このデモはその判断材料)。

## 1. 目的

「文章を書く側が、数や引用と一緒に根拠(発言番号)を添える」設計で、有価証券報告書以外の文書に Core の 4 状態(GROUNDED / VALUE_MISMATCH / POINTER_NOT_FOUND / UNVERIFIABLE)を当てた例を 1 つ作る。XBRL の 66.8% は「自由な文章から根拠を当てる」精度だった。ここでは根拠が添えてあるので、engine の仕事は「添えられた根拠が本物か・言っていることと合うか」の照合だけになる。その違いを数で見せる。

## 2. 材料

- 衆議院 予算委員会 第 12 号(2026-03-30)、issueID `122105261X01220260330`、発言 159 件、本文 58,297 字。
- `fixtures/kokkai/meeting_122105261X01220260330.json`(API の応答そのまま、sha256 `0013513d6d824fa5a8baf0b2d6d6a87547ecd12e3254f664dc75e0ea85bc0f77`)。出典表示は `docs/NOTICE_KOKKAI.md`。
- 試験は通信しない(`tests/adapters/` 以下で `urlopen` を呼ばない規則は既存のまま)。

## 3. 書き手の席(独立の AI 席)

- 入力: 上の JSON だけ。engine の中身・この計画・判定の語は渡さない。
- 出力: `fixtures/kokkai/summary_122105261X01220260330_seat.json`。要約の文 1 つにつき 1 件の claim: `{id, text, speech_order, speaker, quote?, number?}`。`quote` は発言からの逐語の引用(60 字以内)、`number` は `{text, value, unit}`(文に書いた数と、その値・単位)。
- 20〜40 件。引用つき 8 件以上・数つき 8 件以上を頼む。
- 席の出力は**変換の前にコミットする**(他人の材料は変換前にコミットする規則)。

## 4. engine(`adapters/kokkai/`。Core は変えない)

- `load.py`: JSON → 発言の索引(`speech_order` → 発言)。
- `resolve.py`: scheme `kokkai`、locator `<issueID>#<speech_order>`。在れば `Resolved(value=None, meta={speaker, speech})`、無ければ `None`(Core が POINTER_NOT_FOUND にする)。
- `comparators.py`: `speaker_equals`(空白を除いて完全一致)/ `quote_in_speech`(NFKC・空白と改行を除いた上で部分文字列)/ `number_in_speech`(発言中の漢数字・算用数字を値に直し、単位を揃えて、claim の値と一致するものが 1 つでも在れば一致)。
- `recipes.py`: claim 1 件 → 発言者の recipe(必ず)+ 引用の recipe(quote が在れば)+ 数の recipe(number が在れば)。`speech_order` が無い claim は UNVERIFIABLE `no_pointer_given`。
- `registry_setup.py`・`verify_meeting.py`(入口 CLI、`verify_document.py` と同じ順: load → make_resolver → register_all → build_recipes → verify_all)。claim の state は、その claim の recipe の中で最も悪いもの(PNF > VM > UNV > G の順ではなく: 1 つでも PNF なら PNF、無ければ 1 つでも VM なら VM、無ければ 1 つでも UNV なら UNV、全部 G なら G)。
- 既存の `report.py` は XBRL の JSON の形に合わせてあるので、同じ欄の名前で出力して流用できるかを試す。流用できなければ最小の報告を別に書く(判定は足さない)。

## 5. 誤りを混ぜる(機械・種は固定)

`measure/kokkai_inject_2026-10-14.py`。既存の `measure/inject.py` は触らない。席の claims の写しに 4 型 × 5 件 = 20 件の誤りを入れる(1 claim に 1 型、重ならない):

| 型 | 入れ方 |
|---|---|
| T1 発言番号 | 別の**実在する**発言番号に差し替える(存在しない番号では当たり前に止まるので、難しい方を測る) |
| T2 発言者 | 同じ会議の別の発言者の名前に差し替える |
| T3 引用 | 引用の中の漢字 1 字を、同じ発言に出る別の漢字に差し替える |
| T4 数 | 値を 10 倍にする(`text` と `value` の両方) |

## 6. 独立の確認席(混入なしの分だけ)

別の AI 席が、席の claims を会議録と照らして 4 点(番号実在・発言者・引用・数)を 正 / 誤 / 判定不能 で答える。engine の出力は渡さない。混入した 20 件は作り方で真偽が決まるので席は要らない。

## 7. 指標(分母を分ける。足して 100% にしない数は並べない)

- 未混入: 誤停止率 = (engine が GROUNDED でない ∧ 席が全点 正)/(席が全点 正)。誤通過率 = (engine が GROUNDED ∧ 席が 1 点でも 誤)/(engine が GROUNDED)。
- 混入: 検出率 = 型ごとに (その claim の state が GROUNDED でない)/5。4 型を**別の行**で出す。合計は出さない。
- 一般の議事録の精度は主張しない(§0)。

## 8. 予測(封。測る前に書き、測った後は直さない)

| 欄 | 予測 | 外れ方 |
|---|---|---|
| 書き手の claims 件数 | 20〜40 | 席が指示を外す |
| 引用つき / 数つき | 各 8 件以上 | 同上 |
| 未混入の GROUNDED 率 | 70〜95% | 漢数字の変換の穴で数の recipe が落ちる(**最もありうる外れ**) |
| 誤停止率 | 15% 以下 | 同上、または引用の正規化の穴(席が「同じ」と読む表記の差) |
| 誤通過率 | 5% 以下 | 数の照合が緩すぎる(発言中の別の数に当たる)。出たらこれは**設計の穴**で、「発言中のどこかに在る」の照合を「引用の中に在る」へ狭める候補 |
| 検出率 T1(別の実在番号) | 4/5 以上 | 差し替え先の発言者が同じで、引用も数も無い claim は原理的に捕まらない(発言者だけの claim) |
| 検出率 T2(発言者) | 5/5 | ― |
| 検出率 T3(引用 1 字) | 5/5 | NFKC が差し替えた字を同一視する(同じ発言の字を使うので低い) |
| 検出率 T4(数 ×10) | 4/5 以上 | 10 倍した値が発言中の別の数と偶然一致 |

棄却条件は原因で書く: 数の変換の穴が原因の誤停止は、規則を直さず記録する。直すなら**別の会議**で測り直す。この会議で直して測り直したものは結果に数えない。

## 9. 試験と監査

- 各モジュールの試験、入口の golden(materials に対する出力の byte を固定)、変異 6 本以上(予測を先に書く)、boundary(Core を import するのは `recipes.py`・`registry_setup.py`・`verify_meeting.py` だけ)、試験は通信しない。
- 数を結果として報告する前に独立監査の GO を取る。監査席には engine を渡し、席の claims と混入の種は渡す(監査は再現する)。

## 10. やらないこと

- 一般の議事録・保険営業の議事録への一般化。Core の変更。`measure/inject.py` の変更。判定に LLM を使うこと。発言の内容についての主張。
