読み方の注記(実装担当):
- span の交わりが 4 本すべてで 0 件。基準線の claim の span は「拾った数字そのものの位置」
  (例: "100" の 3 文字)であり、正解集合の span は「その主張を述べる文・節全体」(例: gold_01 の note
  「span は文そのものの区間」)である。**この 2 つは最初から比べる粒度が違う** ― 基準線がどれだけ
  正しい数字を拾えていても、span が一致しない設計なので value 一致・form 一致は常に 0/0 になる
  (spanMatchedCount が分母のため)。これは基準線の実装の誤りではなく、「素朴な規則」が claim の
  範囲をどう決めるかという、計画の目安(「数のある文を1 claim として」)が確定していない点に起因する
  ― 下で「思いついたが実装しなかった工夫」として報告する。
- uncovered(被覆されない数字入りの文)は、この粒度の違いの影響を受けない(claim の span が原文の
  どの数字トークンを覆っているかを coverageReport が独立に測るため)。この欄は意味のある実測値になっている:
  実測の方が正解より uncovered が多い(actualOnly が 27 件)のは、基準線が項目名(M4)・閾値の定義
  (300 点)・ページ番号などの「数字はあるが主張ではない文」も区別なく拾ってしまい、逆に 1 文に複数の
  数字がある場合は 2 件目以降を無視するため、正解が claim にした文の一部を基準線が覆えていないことを示す。

読み方の注記(実装担当・2 回目):
- span の交わりが 37 件中 32 件に上がった(1 回目は 0 件)。残る expectedOnly=5 の主な原因は、
  原文の先頭(見出し + 空行の直後、まだ 1 つ目の句点が現れていない部分)。`splitIntoSentences` は
  句点でしか文を切らないため、1 つ目の句点より前の全体(見出し・空行を含む)が「1 つの文」として
  扱われる。たとえば gold_01 の正解 c1 の span([15, 42])は見出し部分を含まない「対象は、…20 局です。」
  だけを指すが、基準線の最初の claim の span は原文の先頭([0, 42])になり、見出しを含む分だけ長さが
  違って一致しない。これは「原文の最初の文の前に見出しがある」という構造の話であり、句点の扱い
  (直した箇所)とは別の既知の限界 ― 直さずに報告する(「賢くしない」決定どおり)。
- uncovered.actualOnly が 4 本すべてで 0 件になった(1 回目は合計 27 件)。これは正しい改善ではなく、
  span を文全体に広げたことの副作用: 1 文に複数の数字があっても、その文に 1 つでも claim ができれば
  文全体が span で覆われ、同じ文の中の 2 件目以降の数字も(値としては無視していても)coverageReport
  上は「覆われている」ことになる。したがって uncovered の基準で測ると基準線はほぼ何も見逃さなく
  見えるが、これは claim の質(value や form の正しさ)とは無関係で、span の粒度を文単位にした
  ことの形の上の結果である。
