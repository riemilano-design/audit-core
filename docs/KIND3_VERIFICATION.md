# Kind 3 検証プロトコル(有段者レビューの代替)

## この文書の位置づけ

判断的知識(Kind 3)のうち、**相手AI制御データ**について、有段者レビューが得られない場合の代替検証手順を定める正本である。

**この文書が変更しないもの**: Kind 3 の定義([DATA_MODEL.md](DATA_MODEL.md))、Kind 3 が人間承認事項であること、認識用データと制御用データの分離([SCENARIOS.md](SCENARIOS.md))、`review_status` の意味と3値。

**この方式は、有段者レビューと同等の知識的保証を持つものではない。** 有段者レビューが得られない場合に、定義した条件を満たす多段階検証を経ることで**暫定的に代替扱いできる**、という位置づけである。

## 適用範囲

| 対象 | 適用 |
|---|---|
| `openings.scenario` の相手AI制御手順 | **適用する** |
| `data/shapes/*.json` の座標 | 適用しない(既知事項「shape座標の一次資料が未検証」は本プロトコルで解消しない) |
| `data/intents/*.json` の `recognition_pattern` | 適用しない(認識用データ) |
| ユーザーに見せる説明文 | 適用しない([ROLES.md](ROLES.md) により人間の判断事項) |

## 原則

1. **有段者レビューが可能なら、従来どおり有段者レビューを優先する。** 本プロトコルは有段者レビューが得られない場合にのみ使用する。
2. **AI検証は証拠を作る工程であり、採否を決める工程ではない。** 合格は「人間が採否を判断できる状態になった」ことのみを意味する。
3. **AI検証済みを `human_reviewed` として扱わない。**
4. **「AIがそう評価したから正しい」という循環判定を禁止する。**
5. **複数エンジンの一致を「正しさの証明」として扱わない。** 多数決を採らない。
6. **エンジンの独立性は合否条件にしない。** ただし使用したエンジン名・バージョン・探索条件は必ず記録する。
7. **最終採用判断は必ず人間が行う。**

## Phase A: 静的検証(エンジン不要)

| # | 確認項目 | 手段 | 合格基準 |
|---|---|---|---|
| A-1 | 制御手順が合法手のみで構成されているか | `apps/server/src/rules/applyMove.ts` で1手ずつ適用 | **100%** |
| A-2 | 手順途中で盤面が破綻しないか | 各手適用後に SFEN が解釈可能であること | **0件** |
| A-3 | 指定した狙いと着手列が矛盾していないか | 手順完了後の履歴を `detectIntents()` に与え、対象 intent が `matched` になること | **不一致 0件** |
| A-4 | 認識用データと制御用データが混同されていないか | ①制御手順が `recognition_pattern` から生成されていないこと ②実行時コードが `recognition_pattern` を制御手順の生成・選択に読まないこと | **0件** |

### A-3 における `recognition_pattern` の位置づけ

`recognition_pattern` は、制御データの検証時に**テスト・オラクル**としてのみ使用してよい。**実行時のAI制御手順の生成・選択には絶対に使用しない**([SCENARIOS.md](SCENARIOS.md) の分離方針)。

**`recognition_pattern` / `detectIntents()` の一致が意味すること**は、認識用データとの**機械的整合性**が確認できた、という一点に限られる。この一致は、**制御手順そのものの将棋知識としての正しさ、戦法名の妥当性、狙いの意味論的妥当性を証明するものではない。** A-3 が通過しても、その手順をその戦法と呼んでよいかは別の判断であり、Phase D・Phase F で人間が確認する。

## Phase B: 単局エンジン検証

| 項目 | 内容 |
|---|---|
| 実施 | 制御手順の**各手の直前局面すべて**でエンジン解析を行う |
| 記録 | 指定手の MultiPV 順位・評価値・エンジン名・バージョン・探索条件 |
| **合否基準** | **設けない。** 評価値・MultiPV順位は**記録資料**として扱い、任意の cp 閾値による合否判定を設定しない |
| **禁止** | 「AI評価値が高い = 将棋知識として正しい」と単純化すること |

記録は Phase F の人間判断の材料として使う。

## Phase C: 複数局検証

| 項目 | 内容 |
|---|---|
| 実施 | ユーザー側(先手)の序盤進行を変えたパターンを用意し、各パターンで制御手順を再生する |
| **応手パターン数** | **3種類以上** |
| **合格基準** | すべてのパターンで**手順全長を維持できること**(維持手数 = 手順長) |
| 根拠 | ユーザーは目標形を3つから選べ(`ranked.slice(0, 3)`)、選んだ形によって序盤の指し手が変わるため、最低3パターンは実際に発生する |

## Phase D: 狙いと結果の整合性検証

| # | 確認項目 | 手段 | 合格基準 |
|---|---|---|---|
| D-1 | 登録した狙いの説明と実際の着手が整合しているか | `current_aim_explanation` が述べる駒種・方向と、手順が実際に動かす駒種・方向を人間が読んで照合 | **重大な矛盾 0件** |
| D-2 | 特定の棋譜を再生しているだけになっていないか | Phase C の結果 | 3パターンすべてで維持 |
| D-3 | 「目的→手→理由」が実挙動と矛盾しないか | 人間が読んで確認 | **重大な矛盾 0件** |

D-1・D-3 は**有段者でなくても実施できる**。

## Phase E: 実対局検証と対局後の人間確認

| 項目 | 内容 |
|---|---|
| **対局数** | **5局以上**。MVP で対象となる**3件の狙いを最低1局ずつ含める** |
| 根拠 | [PHASES.md](PHASES.md) Phase 5 の完了条件「人間が5局程度を実際に通しプレイし」の先例 |

確認項目(いずれも有段者でなくても実施できる):

| # | 確認項目 |
|---|---|
| E-1 | UI上で戦法名・狙い名が不当に露出していないか(相手の狙いが開示されていない / `draft` の名前が断定表示されていない) |
| E-2 | AIが毎局同じ手順を機械的に再生していないか |
| E-3 | 「認識」と「AIの制御」が混同されていないか(制御側の選択が画面・APIレスポンスに現れない) |
| E-4 | **何も操作せずページを開く・リロードする・放置する**という初回接触の経路([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 3.-5.) |

## Phase F: 人間による最終採用判断

| 項目 | 内容 |
|---|---|
| 実施者 | 人間。**有段者である必要はない** |
| 確認対象 | Phase A〜E の検証結果・記録・局面・候補手順 |
| 承認内容 | 「この制御データを実運用で採用する」ことの明示的承認 |
| **AIの役割** | 検証結果の提示まで。**承認を代行しない** |

**Phase F を経ていない制御データを、相手AIの実運用に使わない。**

## 判定

| 判定 | 条件 | 帰結 |
|---|---|---|
| **合格** | Phase A・C・D・E の合格基準をすべて満たす | Phase F へ進む |
| **条件付き合格** | Phase A・D は満たすが Phase C・E に留保がある | 使用範囲を限定して Phase F へ進む |
| **不合格** | Phase A(合法性・盤面・整合性・混同)のいずれかが不合格 | 採用しない。手順を作り直す |
| **要人間判断** | 下記のいずれか | 人間が判断する |

要人間判断へ回す条件:

- 複数エンジンで結果が一致しない
- Phase B の記録から、人間が判断を要すると考える事象が見つかった
- AIでは判定できない意味論的問題(「この手順をその戦法と呼んでよいか」等)
- 新規性の高い戦法・狙い
- 検証が不十分(段階を実施できない等)
- Phase C で1つの応手にしか成立しない

## 検証状態の管理

`review_status` はユーザーへの知識露出を制御する。**Kind 3 制御データの検証・採用状態はこれとは完全に分離して管理し、一方の値から他方を導出しない。**

**フィールド定義(ζ-4b で確定済み)**:

| 案 | 値 | 意味 |
|---|---|---|
| `verification_method` | `expert_review` / `ai_multi_stage` / `null` | どの方法で検証したか。`expert_review` は有段者レビューを実施した場合のみ |
| `verification_status` | `unverified` / `ai_verified` / `human_approved` | `human_approved` は**人間のみが設定できる** |
| `verification_record` | object | 使用エンジン名・バージョン・探索条件・各Phaseの結果・不一致の有無・最終判断者・日付 |

**この3フィールドは `data/schemas/openings.schema.json` の `scenario.variants[]` に、variant 単位で定義済みである。** 定義の正は [DATA_MODEL.md](DATA_MODEL.md) と `data/schemas/openings.schema.json` とする。

**運用規則**:

- AI検証で問題が確認された場合、`verification_status` を `unverified` へ戻す(`review_status` は触らない)
- 有段者レビューが後日可能になった場合、`ai_multi_stage` から `expert_review` への**追認・格上げができる**
- **未承認の Kind 3 制御データが実運用に入らないゲートを実装要件とする。** 検証状態を単なる記録項目にせず、実運用への投入可否に実際に効く仕組みを設ける

## この方式の限界

本プロトコルは有段者レビューを再現しない。以下の限界を持つ。

1. **エンジン同士が同じ誤りを共有する可能性がある。** 系譜の近いエンジンは同じ局面で同じ偏りを示しうる。複数エンジンの一致は独立性の証明ではない
2. **評価値と「狙い」の意味は別物である。** エンジンは局面を数値化するが、「この手順がその戦法である」とは判定しない。戦法の命名は将棋界の慣習である
3. **一般的な将棋知識と、このアプリが説明する意味づけは別物である**([PROJECT_VISION.md](PROJECT_VISION.md) 1.)
4. **手順が合法でも、狙いの説明が不正確である可能性がある。** Phase A-3 が確認するのは `recognition_pattern` との機械的一致であり、その `recognition_pattern` 自体の名前の妥当性は検証範囲外である
5. **序盤は評価値の解像度が低い。** Phase B の判別力は序盤ほど低い
6. **エンジンの独立性そのものを実行結果から判定できない**
