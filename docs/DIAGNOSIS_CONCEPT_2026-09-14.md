## 1. 決定(何を、なぜ)

### 1.1 決めたこと

**主役を「対局中に⑤候補手を言うこと」から「対局後に、棋譜を横断して負け方の繰り返しを見せること」へ移す。** ただし「将棋コーチ」を捨てて別の製品を作るのではない。**同じ解析基盤から 2 つの出口を出す。**

| 出口 | 問い | 状態 |
|---|---|---|
| 対局中コーチ(Live Coach) | 「今、何を考える?」 | **残す。** 帯「いま注意する駒」・①何が起きているか・②相手の狙い・③何が重要か は、今日の状態のまま |
| 対局後診断(Leak Detector) | 「なぜ負ける? 繰り返している? どう直す?」 | **新しく作る。** 棋譜群 → 破滅の分岐 → 物理イベント → 死因候補 → 個人パターン → 本人の実戦局面から作る練習問題 |

**止めるのは 1 つだけ**: [DESIGN_REVIEW_2026-09-13.md](DESIGN_REVIEW_2026-09-13.md) §11 の **(お)(⑤の候補手を読み筋から作り、本番導線を切り替える)と (か)(画面に出す)**。U6 の解析層(U6-O 文の組み立て・U6-T MultiPV 5 の分布・U6-I4(2) ②の表)は**完了させる**(4. のとおり診断側でも使う)。

### 1.2 なぜ

1. **いちばん難しい部分が、いちばん価値の薄い部分だった。** 対局中に⑤を言う工程は、Phase 7 で最も苦しんだ(囲いを組まない指し方で 48 手中 0 件。形からの逆算をやめて読み筋から作り直し中)。しかも 1 局ごとの候補手や悪手指摘は、無料の道具がすでに持っている
2. **対局後バッチにすると、構造的な苦しみが消える。** ③⑤が届くまでの 9〜13 秒、対局が 1 つしか持てないサーバー(`server.ts` のモジュール変数)、エンジンの取り合い(AGENT_PROTOCOL 10 番・12 番)、時間制限による非決定性(P-33・P-38)。いずれも「対局中・リアルタイム」から来ていた
3. **棋譜を横断して「繰り返し」を見せる道具は、将棋にはまだ無い。** 差が出るのは「50 局を通して、あなたはこの条件でこう壊れる」と言えることで、1 局ごとの解析では出ない
4. **今日までの資産の回収率が高い。** 「事実の抽出と文言を分ける」「LLM に将棋の事実判断をさせない」「②〜④は確定値ではなく仮説」という現行の設計思想は、そのまま診断側の設計原則になる(3.)。捨てるのは画面への配線と、形からの経路計画だけ

### 1.3 変えないもの

- 最重要コンセプトの核(「最善手を教えるアプリではない」「盤上で実際に生じたものだけを述べる」)。改定するのは「対局中に」という一句であり、案は 9. に置く。**確定は人間の判断で、7. の結果が出てから**
- 絶対に守るルール 1〜7、絶対的な上位原則、承認の委任と 3 条件
- `data/` が将棋知識の唯一のソースであること、`review_status` の運用
- 外側のループ(対局ハーネス → 記録 → 不変条件 → 人間の仕分け)

## 3. 3 層と、現行モジュールの対応

現行の `analysis/` は「事実の抽出(`*Detector`)」と「文言(`*Explanation`)」を別ファイルにしている。診断側はこれを 3 層として読み直す。

| 層 | 問い | 現行モジュール | 診断側で足すもの |
|---|---|---|---|
| **A. Observation(観測)** | 盤上で何が起きた? | `boardEventDetector` 捕獲・王手・成り / `moveOutcomeDetector` 直前の一手の変化 / `captureSummary` 駒の得喪 / `pieceThreatDetector` 当たり / `escapeSquareThreat` 逃げ道 / `shapeDetector`・`shapeFormationAnalyzer` 形 / `engineReference` 評価と読み筋 / `searchPv` 読み筋と標識 / `pvMaterials` 読み筋を進めた材料 1〜12 | **無い。** 足りないのは「記録」の欄 2 つ(4.2) |
| **B. Interpretation(解釈)** | それは何を意味しうる? | `intentDetector` 相手の狙い(仮説) / `candidateMoveReferenceFilter` 安全確認 | **Failure Event**(5.)と **死因候補のタグ**。いずれも「候補事象」として draft から始める |
| **C. Explanation(説明)** | 人にどう伝える? | `*Explanation.ts` 群 / `explanationGenerator` / `pvSentence`(U6-O) | 診断レポートの文。最初は `check.ts` と同じ Markdown。LLM を使うなら「確定した数字の言い換え」だけ(ルール 5) |

**A の層に将棋の判断は入っていない。B の層は仮説であり、`draft → approved` の運用を通す。** これは現行の②〜④(認識は確定値ではない)と、不変条件(検出は候補事象、登録は人間の仕分け)の運用そのままである。

**現行モジュールの責務を読み違えないための注記**(外部の意見にあった誤り):
- `pvMaterials` は**詰みや退路を数えない**。数えるのは接触・捕獲・持ち駒・玉の周りの枚数・前進/後退・利きの升数。詰みは `usiInfoParser` の `score mate`、退路は `escapeSquareThreat`
- 分岐点の検出はエンジンの評価値に依るので、**「100% ルールベース」ではない**。同じ局面・同じノード数でも 118 組中 0 組しか一致しなかった(P-33)。診断の数字は観測であり、判定ではない(AGENT_PROTOCOL 11.)

## 4. A: 観測事実を何として記録するか

### 4.1 答えはほぼ出ている ― `replay.ts` の JSONL

`scripts/playtest/replay.ts` が書く記録(`kind: "record"`、`scripts/playtest/invariants/types.ts` の `RecordLine`)が、**一つの敗戦についてコンピューターが記録できる事実**である。

| 欄 | 中身 | 診断での使い方 |
|---|---|---|
| `ply` / `sfen` / `senteMove` / `goteMove` / `phase` | 各手番の局面と手 | 分岐点の位置 |
| `response.coach` | 帯・①②③④の出力(status・根拠のマス・`refers_to_intent_id`) | 発症条件(相手の狙いを認識していたか、形が完成していたか) |
| `response.plan` | 経路・候補手の状態 | 現行の④⑤(診断では使わない) |
| `engineReference`(ready 行) | `baseline`(現局面)・`afterPass`(パス局面)の `scoreCp` / `mate` / `bestmove`、`dropCp`、`nodes` | **評価値の推移と急落の検出、詰みの検出** |
| `searchPvs`(ready 行) | 本番が使った探索の読み筋(`pv[]`・`scoreCp`・`mate`・`lowerbound`/`upperbound`) | **反事実(最善手 PV)の材料** |
| `meta` 行 | `gitHead`・`dirty`・`dirtyPaths`・`enginePath`・探索条件 | どの道具で測ったかの保証(U6-R) |

**連続する 2 つの ready 行の `engineReference.baseline.scoreCp` の差 = 「自分の手 + 相手の応手」の効果**である。したがって**急落の検出は、既存の記録を読むだけで作れる**(エンジンを回し直さない)。

### 4.2 足りないもの(2 つ。どちらも記録の拡張で済む)

1. **相手の手番の評価値。** いまは ready 行(自分の手番)だけに `engineReference` が付く。「自分の手で落ちた」のか「相手の応手で落ちた」のかを分けるには、相手の着手直後の評価も要る。ただし**診断 1(死因①)は連続 ready 行の差で足りる**ので、最初は足さない
2. **実戦の続きを数手進めた結果。** 「悪手の 3〜5 手後に自玉へ王手/詰み」は、実戦の棋譜そのものを進めれば分かる(`boardEventDetector` を実戦手順に当てる)。読み筋ではなく実戦の続きを見るので、`pvMaterials` の再生と同じ手順で書ける

### 4.3 記録の入口

固定棋譜の JSON(`scripts/playtest/kifu/*.json`: `{ id, source, moves: [USI...] }`)が入口。**外部の棋譜(KIF / CSA)をこの形に変換する部品**が要る(shogiops 0.21 の `notation/kif`・`notation/csa`。確認中 ― Diagnostic Spike 0)。

## 5. B: Failure Event(破滅の分岐)

### 5.1 定義

**Failure Event は死因ではない。**「この着手を境に、何が壊れたか」を、観測事実の組み合わせとして記録するもの。死因(候補)は、その上に付ける仮説のタグであり、個人パターンは複数局を集計して初めて言える。

```
① Observation      評価 +820 → −650(ply 42)。実戦の続き: ply 45 で王手、ply 47 で詰み
② Physical Event   評価の急落 / 自玉への王手 / 詰み(すべて A 層の事実)
③ Failure Candidate  "mate_threat"(仮説のタグ。draft)
④ Personal Pattern   同じ発症条件で 50 局中 8 回(集計。閾値は人間の判断)
```

### 5.2 構造(案。実装で変わりうる)

```jsonc
{
  "kifuId": "...",
  "ply": 42,                         // 分岐点(自分の手)
  "trigger": {                       // 発症条件 = 分岐点の直前の観測
    "scoreCpBefore": 820,            // engineReference.baseline
    "shape": { "id": "mino_honmino", "status": "forming" },   // response.coach
    "opponentIntent": { "id": "boh_gin", "status": "matched" }, // 認識していたか
    "phase": "middlegame"            // 定義は後で決める(手数か駒の交換か)
  },
  "action": { "playedMove": "2d2c+", "bestmoveAtBefore": "5i4h" },
  "consequences": [                  // 実戦の続き 3〜5 手で起きた物理イベント
    { "ply": 45, "event": "check" },
    { "ply": 47, "event": "mate" }
  ],
  "counterfactual": {                // 反事実。searchPvs の最善手 PV を pvMaterials で数えた材料
    "played": { /* PvMaterials */ },
    "best":   { /* PvMaterials */ }
  },
  "candidateModes": ["mate_threat"], // 仮説。draft → approved
  "evidence": { "gitHead": "...", "nodes": 4000000, "dirty": false }
}
```

- `trigger` と `consequences` は **A 層の値をそのまま写す**(新しい判断を持ち込まない)
- `candidateModes` は**規則で付ける仮説**で、規則そのものが判断的知識(ルール 4)。不変条件と同じく `draft` から始め、人間が仕分ける
- 「発症条件 → 着手 → 相手の対応 → 結末」の鎖が、ユーザーの記録の核になる

### 5.3 最初の死因: ①「優勢時の自玉の危険化」

4 種の死因(即時壊滅・戦力壊滅・速度敗北・機能不全)を最初から作らない。**死因①だけ**から始める。理由は 3 つ。

1. 物理イベント(評価の急落・王手・詰み)が離散的で、A 層の値だけで判定できる
2. 「相手が暴れてきて運悪く頓死した」と本人が片づけがちな場面で、事実と本人の認識の差が最も大きい
3. 現行の不変条件 I-5(当たりがあるのに急ぐことが出ない)・I-6・I-7 が判定の原型

**判定規則(仮。数字は人間の判断事項。測る前に書く)**:

| 条件 | 値(仮) | 出どころ |
|---|---|---|
| 分岐点の直前が優勢 | `baseline.scoreCp ≥ +300` | `engineReference`(**NNUE の評価で**。今の駒得だけの評価では使わない) |
| 分岐点で急落 | 次の ready 行との差が `≤ −400`、または `afterPass` が `mate` | 同上 |
| 直後に自玉が危険 | 実戦の続き 3〜5 手以内に自玉への王手、または詰み | `boardEventDetector`・`gameStatus` を実戦手順に当てる |

「速度敗北」「機能不全」は、人間の主観的・文脈的な概念を含むため、**A 層の値だけでは判定できない**。後回しにし、必要なら発症条件の組み合わせ(例: 優勢 + 攻め継続 + 相手の反撃)として表す。

### 5.4 発症条件の材料 ― `data/shapes`・`data/intents` は凍結しない

- **「自玉が囲いから離れている」「囲いが未完成」** = `shapeFormationAnalyzer` の `status`(`none / forming / completed`)
- **「相手の狙いを認識していたのに攻め続けた」** = `response.coach` の②が `refers_to_intent_id` を持っていたか(U6-I4 の②の表が数えるもの)
- 「優勢時」= `engineReference.baseline.scoreCp`

形と狙いのデータは、局面の分類には使わず、**発症条件のタグ**として使う。診断側で初めて本領を発揮する。

## 6. C: Personal Pattern(個人の傾向)― 急がない

「何回起きたら癖と言えるか」は判断的知識であり、検証で決める。本書では**定義しない**。決めるときの原則だけ書く。

- 「繰り返し」は同じ発症条件の下で数える。条件を変えると数が変わることを明記する
- 合否基準を設けない。「異常」と呼ばない(AGENT_PROTOCOL 11.)
- 「認知的欠陥」のような決めつけの語を使わない。観測されたパターンを述べ、解釈は控えめな表現で(ルール 6)

### 7.2 「調査価値」の基準(**2026-09-15 の人間の決定で、「面白い」の主観の基準を数の基準に置き換えた**)

> 実在の 1 人の棋譜 20 局以上で、`diagnose.ts` が拾った急落のうち、**同じ発症条件(7.3 の 2. の名前つきの死因候補)に該当するものが 3 件以上**あり、**そのうち 2 件以上で本人が「指したとき危ないと思っていなかった」と答え**、**その局を実際に落としたか、5 手以内に自玉へ王手か詰みを受けている**。

「面白い」「有段者が気になる」といった主観の基準は使わない。調査価値は、評価値の変化・駒得損の変化・王手の発生・逃げ道の変化・攻撃駒と守備駒の変化・第一候補との差・同じ条件の過去の出現回数・死因候補への該当回数、といった**計測できる指標**で定義する(7.3)。「人間が面白いと思ったから取り上げる」ではなく、「機械的に重要度を出し、重要なものを取り上げる」に変える。**本人への質問**(「この場面、指したとき危ないと思っていましたか」― はい / いいえ / 覚えていない)は、目利きの推測より直接の証拠であり、D4 の計画で質問の文言と記録の形を決める。

これが出れば、CLAUDE.md と PROJECT_VISION.md を改定して転換を正式に取り込む。出なければ見送る。**結果を見てから基準を選ばない。**

**置き換える前の基準(2026-09-14、履歴として残す)**: 「死因①を 3 件以上、同じ発症条件で拾い、将棋の分かる人が見て『本人は気づいていなさそう』と言える」。有段者の目利きを常設で必要とする点が実現しにくく(2026-09-15 の人間の言葉)、7.3 の分解に置き換えた。

固定棋譜 7 局(Claude が初心者を演じて弱いエンジンと指したもの)は**道具の動作確認にしか使わない**。人の癖は入っていない。実棋譜での最初の記録は `records/real-01`(1 人目、先手 6 局)以降。

### 7.3 「目利き」の分解(**2026-09-15 の人間の決定。この節の原則は今後も固定**)

**目的**: 有段者が実戦棋譜から行っている判断を、そのまま AI に再現させない。「目利きを AI で再現する」という言い方は捨て、**「目利きを機械的に検証できる小さな判断へ分解する」**と定義する。判断を次の 4 つに分ける。

1. 機械で測定できる事実
2. 事実から条件式で導ける死因候補
3. 反事実によって検証できる差
4. 機械的に確定できない人間の判断

これにより、有段者による全棋譜の目利きを必要とせず、**定義の承認**と、**機械判定が難しい代表例の確認**だけを人間に委ねる。

**1. 機械で測る** ― 局面から取得できる事実を、解釈せず記録する。
- 既実装: 評価値、駒得・駒損(`pvMaterials`)、王手(`detectBoardEvents`)、玉の周囲の味方駒(`kingSurroundings`)、玉の逃げ道(`escapeSquareThreat` 系)、エンジン第一候補、エンジンの読み筋(記録の `searchPvs`・`engineReference`)
- 今後追加: 攻撃駒数、守備駒数、各駒の利き、攻撃までの速度、相手玉への脅威、自玉への脅威
- ここでは「良い・悪い」「見落とした」などの解釈を行わない。

**2. 名前つきの死因候補を条件として定義する** ― 「攻め急ぎ」「受け不足」などを、LLM の判断ではなく再現可能な条件式として定義する。例: **攻め急ぎ(仮)** = 自分の攻撃駒が減少 かつ 自玉の逃げ道が減少 かつ 第一候補の続きでは上記の変化が起きない。該当すれば「攻め急ぎ(仮)の条件に該当」とし、「この人は攻め急ぎをした」とはまだ言わない。該当件数・非該当件数・類似局面数を蓄積する。**条件の定義は判断的知識であり、確定には人間の承認が要る**(CLAUDE.md 4 番)。死因①(5.3)はこの形の最初の 1 件である。

**3. 反事実によって条件を検証する** ― 実戦の続きと第一候補の続きを同じ尺度(駒得損・王手・玉の安全・逃げ道・攻撃駒・守備駒・利き・速度)で比べ、差分を事実として提示する。**これが D2 の中心になる。** 「○○が正解」「攻め急ぎで悪い」とは書かず、**事実 → 比較 → 気づき**の順にする。

**4. 人間の判断を残す** ― 機械的に確定できないものだけを人間に渡す。有段者の役割は、① 定義の承認(「この条件を『攻め急ぎ(仮)』として扱ってよいか」)と、② 低信頼の代表例の判定(100 件を条件判定して 80 件が明確・15 件がやや曖昧・5 件が判断不能なら、曖昧と判断不能の代表例だけを見る)。意見が割れた場合は「判定不能 / 低信頼」として残し、断定しない(CLAUDE.md 6 番)。有段者でなくても本人より明らかに強い人の判定は ② の補強になる(要るのは段位ではなく本人との差)。

**最終的な階層**

```
観測(評価値・駒・利き・王手・逃げ道・速度)
  ↓
物理イベント(駒損・玉の安全度低下・攻撃力低下・反撃発生)
  ↓
死因候補(攻め急ぎ(仮)・受け不足(仮)・駒の働き低下(仮)・その他)
  ↓
反復・集計(発生回数・発生条件・反事実との差・信頼度)
  ↓
個人パターン(「この条件でこの失敗が繰り返される」)
  ↓
学習課題
```

その外側に LLM を置く。**LLM は「将棋を判断する脳」ではなく、「機械が確定した診断材料を人間に伝える言語インターフェース」**である(CLAUDE.md 5 番の言い換えに限る、と同じ)。認識(形・相手の狙い)は `data/shapes`・`data/intents` の候補集合に対する規則の照合であり、LLM に自由生成させない。**AI に AI を監査させる形は、将棋の事実には使わない**(事実の検証はエンジンと規則で行う)。

**進め方**: この節を上位構想に確定 → D2 の実装仕様へ降ろす(反事実の差分を事実で書く)→ 名前つきの死因候補の定義(D3)→ 反復と信頼度の集計(D4)。順序は 20 局版のレポート(real-02・real-03)の後。

## 9. CLAUDE.md の一文の改定案(**確定は人間。7.2 の後**)

現行:

> このプロジェクトは、「定跡を覚えさせるアプリ」ではなく、**「将棋の考え方を対局中に身につけさせる AI コーチ」**である。「最善手を教えるアプリ」ではない。

案:

> このプロジェクトは、「定跡を覚えさせるアプリ」ではなく、**「盤上で実際に起きた事実から、将棋の考え方を身につけさせる AI コーチ」**である。対局中には「今、何を考えるか」を、対局後には「なぜ負けたか、繰り返していないか」を、同じ事実から述べる。「最善手を教えるアプリ」ではなく、「あなたは弱い」と言うアプリでもない。

変えたのは「対局中に」の一句と、対局後の出口の追加だけ。「最善手を教えない」「事実から述べる」は動かない。あわせて [PROJECT_VISION.md](PROJECT_VISION.md) 2.(完成イメージ)・3.(判定基準)と [PHASES.md](PHASES.md) の Phase 8(仮)を書く必要がある。**本書の時点では、どれも書き換えていない。**
