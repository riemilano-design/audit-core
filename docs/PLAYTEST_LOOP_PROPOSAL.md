## 1. 一言で言えば

**「仕様 → 実装 → 仕様どおりか監査」の内側のループはそのまま残し、その外側に「AIが対局する → 記録を取る → 機械的な不変条件で検査する → 人間が仕分ける」というループを足す。**

これは「AIにもっと自由に作らせる」提案ではない。AIに任せるのは**テスト**であり、仕様変更・実装・承認の権限は現行どおり動かさない。

## 2. なぜ変えるか(今日の観測)

2026-09-10、Claude がブラウザで先手を10手指し、一手ごとに画面の文を記録した(付録 A)。そこで次が起きた。

1. 相手の馬が７七の桂に当たった局面で、[4] の道のりは「玉を２八へ 残り1手(３九→２八)」を表示し続けた
2. 候補手は STEP 4-2 の安全確認で全件除外された(`candidateMove.status: "not_ready"`, `notReadyReason: "excluded_by_reference_evaluation"`)。**除外自体は正しい**
3. しかし除外された事実は画面に出ない。`apps/web/src/main.ts` の候補手セクションは、この状態を「既存仕様のまま何も表示しない(今回の変更対象外)」と明記して黙る
4. 道のりの文どおりに ２八玉 を指すと、桂を失った
5. 次の画面は「この手は、直前に表示していた候補手の一つです。」と述べた。表示していない

この一連は、**仕様どおりに作られ、監査も仕様に対して GO を出し、初心者が駒を失う画面になった**。副作用そのものは STEP 4-2 の完了記録が「Unit 5 の論点として持ち越す」と記録している。つまり工程は正常に回っている。正常に回った結果がこれである。

原因は個々の STEP ではなく、工程の形にある。

- 監査は「STEP の仕様と一致するか」を見る。「コーチとして自然か」は確認項目にない
- 問題の発見が人間の実機プレイに依存している。ランク別検証(P-1〜P-14)も今日の記録も、人間か Claude が手で指した1回きりの観測である
- 一度「変更対象外」と決めた沈黙は、次の STEP の仕様にも入らないため、誰も再検出しない

## 3. この領域だけの利点

普通の Web アプリは、テストのために状態を人工的に組み立てる。将棋コーチでは**対局そのものが状態を生む**。局面・指し手・捕獲・成り・王手・囲いの形成・候補手の除外・終局が、一局の中で自然に、しかも毎局違う順で発生する。さらに良し悪しの判定者(エンジン)が横にいる。

「実際に人間っぽく40手指して、各局面でコーチが何を言ったかを記録する」ことが、そのまま巨大な統合テストになる。この利点は今まで使っていない。[TESTING_STRATEGY.md](TESTING_STRATEGY.md) の「5. UI・E2Eテスト」は「MVPでは自動化しない。人間による通しプレイテストのみ」としている。

## 4. 仕組みの構成

### 4.1 対局ハーネス(記録を取る)

- HTTP を経由せず、本番関数を直接呼ぶ。`createInitialGameState` → `playHumanMove` → `playOpponentMove` → `buildStateResponseWithPlan` / `computeReachablePlan`(いずれも `apps/server/src/` の既存 export)。STEP 4-4・4-5 の完了確認が既に「本番関数 `buildStateResponseWithPlan` で行った」のと同じ経路である
- 一手ごとに、局面(SFEN)・指し手・API レスポンス全体(`coach` / `plan` / `urgentMessages` / `lastMoveOutcome` / `candidateMove` の状態)を **JSONL に保存**する。画面の文はすべてこのレスポンスから作られるため、レスポンスを保存すれば画面の文を再現できる
- 一局は「自分側の指し手列」で再現できる。記録には自分側の USI 列を必ず残す(再現手順になる)
- 相手側は本番と同じ(素のエンジン、`movetime 1000`)。**相手AIの強さは変えない**(Kind 3。P-13 は別問題のまま)

### 4.2 対局者(自分側の手を作る)

状態の多様さが目的なので、最善手を指させない。次の3種を混ぜる。

| 種類 | 内容 | 目的 |
|---|---|---|
| 台本 | 「飛車先を突く」「角が当たったら逃がす」「囲いの道のりをそのまま指す」「候補手をそのまま指す」のような初心者の定型行動を、盤面条件つきの短い規則で書く | 今日の桂のような「文どおりに指した結果」を再現する |
| 浅い読み | エンジンに短い `movetime` で指させる | 形が崩れない普通の進行を作る |
| 乱択 | 合法手から低確率で無作為に選ぶ | 想定外の局面を作る |

台本は**テストの入力**であり、ユーザーに見せる知識ではない。CLAUDE.md ルール5(LLMに将棋の事実判断をさせない)に触れない。台本の規則は将棋の正しさを主張しないので、記述的知識にも判断的知識にも当たらないが、迷う場合は [CHANGE_MANAGEMENT.md](CHANGE_MANAGEMENT.md) の原則どおり重い側(判断的)として扱い、人間が確認する。

### 4.3 不変条件(検査器)

保存した JSONL に対して**真偽を返す決定的な関数**。LLM を使わない。今日の観測と既知事項から、初期セットを次のように起こせる。

| ID | 条件(これが成り立てば異常) | 出典 | 機械判定 |
|---|---|---|---|
| I-1 | 候補手が全件除外(`excluded_by_reference_evaluation`)なのに、[4] に除外を伝える文が無く、道のりは表示されている | 今日 C-1、STEP 4-2 完了記録の副作用 | 可 |
| I-2 | `played_candidate` が出た手が、直前の局面で `candidateMove.status: "ready"` の候補に含まれていない | 今日 C-2、P-9 | 可 |
| I-3 | 終局(`status.isEnd`)後に道のり・候補手・組み上がりが出る | P-6、STEP 4-5 X-1 の回帰 | 可 |
| I-4 | `completed` の形に対する道のりが同時に出る、または対象形が完成済みの祖先へ戻る | P-1、STEP 4-1 の回帰 | 可 |
| I-5 | 自分の駒に相手の利きがある(`squareAttackers`)のに [0] に当たりの行が無い(対象駒種は 4-3 の承認どおり) | P-3、STEP 4-3 の回帰 | 可 |
| I-6 | 本文の座標(「７七の桂」等)にある駒が、SFEN 上のそのマスに無い | P-12 | 可 |
| I-7 | 同一画面に同じ文が2回以上出る | P-8、U1-7 | 可 |
| I-8 | 本文に SFEN / USI 形式の文字列が含まれる | U1-11、今日 C-6 | 可 |
| I-9 | 本文に出た将棋用語が `glossary_terms` にも説明文にも無い(用語の一覧は人間が承認したものだけを使う) | P-10 | 可(一覧が要る) |
| I-10 | 相手の狙いの根拠の手番号が、`recognitionTimeline` の最新変化点より古い | P-4、STEP 4-4 の回帰 | 可 |
| I-11 | 捕獲の文に取った駒の名前が無い | 今日 C-4 | 可 |

**不変条件は「何を異常と呼ぶか」の決定である。** したがって AI は下書き(`draft`)として自由に追加してよいが、有効化(STEP の完了条件に入れる)は人間の承認を要する。`draft` の不変条件は報告に出るだけで、何もブロックしない。これは `review_status` による露出制御([DATA_MODEL.md](DATA_MODEL.md))と同じ考え方である。

### 4.4 仕分け(人間が見る量を減らす)

100局回せば違和感候補は数百件になる。一件ずつ見せると、承認の負担が仕分けの負担に変わるだけである。そこで、

- 各検出を **型 × 発生条件** で束ねる。型は「沈黙・矛盾・断定・未説明用語・盤との不一致・陳腐化」の6つから始める。発生条件は `template_id` / メッセージの `kind` / `notReadyReason` のような既存の識別子で取る
- 人間に出すのは**型ごとの件数、代表例3件、再現手順(自分側の USI 列と手数)**だけ
- 前回のビルドとの差分(増えた・減った)を先頭に置く

人間の仕分けは既知事項と同じ三択にする: **直す / 仕様として正しい(受容) / 持ち越す**。「仕様として正しい」と仕分けた項目は、その不変条件を無効化するか、条件を狭める(判断は人間)。

### 4.5 概念の境界(テストシステムが勝手に仕様化しないための規定)

外側のループには6つの概念が登場する。これらは並列の分類ではなく**一方向の流れ**であり、**線をまたがせる操作はすべて人間だけが行う。**

| 概念 | 何か | 誰が作るか | 効力 |
|---|---|---|---|
| 観測 | 一回きりの出来事の記録(「この局面でこの文が出た」)。付録 A や [PLAYTEST_RANKED_2026-09-10.md](PLAYTEST_RANKED_2026-09-10.md) がこれ | AI・人間のどちらでも | 何も拘束しない。記録にすぎない |
| 既知事項 | 観測のうち、人間が「ユーザーに見えるか」を付けて [PHASES.md](PHASES.md) の表に載せたもの。処遇(直す/受容/持ち越す)待ち | **人間の指示で**載せる([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 1. により司令塔は一覧を編集しない) | STEP 提案に併記される。仕様ではない |
| 不変条件 draft | 観測または既知事項を、対局記録に対して真偽を返す述語に書き直したもの | AI が自由に追加してよい | 報告に出るだけ。何もブロックしない |
| 承認済み不変条件 | 人間が有効化した draft | **人間だけ** | STEP の完了条件に入る(悪化していないこと) |
| 自動検出 | 不変条件(draft・承認済みの両方)が対局記録に対して出した結果 | ハーネス | **事実であって判断ではない。** 既知事項にも仕様にも自動では昇格しない |
| 人間判断 | 検出の仕分け(直す/受容/持ち越す)、不変条件の有効化・無効化・条件の狭め | **人間だけ** | ここでだけ線がまたがる |

規則:

1. 観測・自動検出は、人間の指示なしに既知事項の表に載らない。人間の承認なしに不変条件が有効化されない。**AI が単独でできるのは、観測を記録することと draft を書くことだけ**である
2. **不変条件は仕様の写しであって、仕様の源ではない。** 不変条件と正本(仕様・人間承認済み事項)が食い違った場合、不変条件が誤りとして扱われ、HUMAN として停止する([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 9. と同じ扱い)。検出を理由に仕様・閾値・文言を変えることはできない
3. 人間が「仕様として正しい(受容)」と仕分けた検出は、その不変条件を無効化するか条件を狭める。**受容した挙動が、それをもって仕様として新たに確定するわけではない**(既存の仕様がそのまま残るだけ)
4. 既知事項の表には「観測」と「対応する不変条件(あれば ID と draft/承認済みの別)」を**別の列**に持つ。同じ行に混ぜない。観測がある = 不変条件がある、ではない
5. 「自動検出が 0 件」は「その異常が無い」ではなく「有効な不変条件が捉える範囲では検出されない」を意味する。完了判定の文言もそう書く(CLAUDE.md ルール6)

### 4.6 二つの実行モード(数字を比較可能にするため)

「沈黙 31件 → 8件」のような比較は、同じ局面列に対してでなければ成立しない。ところが相手のエンジンは `movetime` で指すため同じ手を返さず、乱択も種を固定しなければ毎回違う局面になる。そこでモードを二つに分ける。

| モード | 相手の手 | 自分側の手 | 用途 |
|---|---|---|---|
| 固定棋譜 | **一度記録した相手の手をそのまま再生**する(エンジンを呼ばない) | 記録した USI 列を再生 | **回帰**。STEP の前後で同じ局面列に対して検出数を比べる。完了条件に使うのはこちら |
| 探索 | 本番と同じ(素のエンジン) | 台本・浅い読み・乱択(種は記録する) | **発見**。新しい局面を作り、観測と draft の材料にする。数字は比較に使わない |

探索モードで見つかった局面列は、固定棋譜として保存して回帰に回せる(P-1〜P-14 の3局、今日の10手も固定棋譜の最初の候補)。「変更によって対局時の異常が減ったか」という評価軸は、**固定棋譜モードの数字に限って**成り立つ。

### 4.7 LLM の役割

初期段階では使わない。将来使うとしても「不変条件では拾えない文の自然さ」の指摘に限定し、事実判断(この形は何か、相手は何を狙っているか)はさせない(CLAUDE.md ルール5)。LLM の指摘は常に `draft` 扱いで、人間が仕分ける。

## 5. 工程の変更(現行との差分)

```
        人間(仕分け: 直す / 受容 / 持ち越す)
                  ▲
                  │ 型ごとの件数・代表例・再現手順
   ┌──────────────┴─────────────────┐
   │ 外側のループ(新設)              │
   │  対局ハーネスが N 局指す        │
   │  → JSONL に記録                 │
   │  → 不変条件で検査               │
   │  → 型×条件で束ねて報告          │
   └──────────────┬─────────────────┘
                  │「直す」と仕分けられた項目だけが STEP になる
                  ▼
   ┌────────────────────────────────┐
   │ 内側のループ(現行どおり)        │
   │  司令塔 → 実装担当 → 監査担当   │
   │  GO / REVISE / HUMAN            │
   └──────────────┬─────────────────┘
                  │ STEP 完了時に外側のループを1回回す
                  ▼
        不変条件の結果が悪化していないことを完了条件に含める
```

変わること:

- **問題の発見**が、人間の実機プレイ頼みから、対局ハーネスの定期実行になる
- **監査の確認項目**に「対局記録に対する不変条件の結果(悪化していないか)」が加わる。仕様との一致は引き続き確認する
- **STEP の完了条件**に「有効な不変条件が悪化していない」が加わる。ブラウザ実測は置き換えない(初回接触の経路は引き続き人間か司令塔が見る)
- **人間の役割**は「計画の承認者」から「結果の仕分け人」へ比重が移る。承認事項の一覧は変えない

変わらないこと:

- AI は仕様を確定しない。HUMAN 事項を GO にしない。実装担当は STEP を越えない。監査担当は実装しない
- 不変条件の結果を理由に、閾値(300cp 等)や除外規則を AI 判断で変えない
- 相手AIの強さ調整をしない
- **人間の初心者テストの代替にしない。** AI が見つける問題は、AI が読んで気づく問題である。「読まれなかった」「意味が取れなかった」は、このループでは拾えない。ループが上げるのは下限であって、上限は初心者一人に触ってもらうことでしか決まらない

## 7. やらないこと

- AI が問題発見 → 仕様変更 → 実装 → 承認 → 次へ、を自律的に回すこと
- 不変条件を根拠に、閾値・除外規則・文言を AI 判断で変えること
- 相手AIの強さ・手加減の調整(P-13。Kind 3)
- 人間の初心者テストを省くこと
- 台本・不変条件を「将棋の知識」として `data/` に入れること(テストの入力であり、教育用データではない)
