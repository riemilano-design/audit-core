## Phase 0 ― 土台

**目的**: 何もない状態から、盤面が表示され、将棋エンジンと接続でき、四間飛車vs居飛車の対局が(仮のUIで良いので)成立する状態を作る。

**成果物**:
- `apps/web`・`apps/server` の雛形
- shogiops を使った合法手判定
- やねうら王とのUSI疎通(`usi`→`usiok`→`isready`→`readyok`→`position`→`go`→`bestmove`)
- AI側(居飛車)の序盤を一定の手順で強制進行させる仕組みの最小実装(定跡を「大量に」用意する必要はなく、四間飛車vs居飛車が成立する最小限の手順で良い)
- Node.js 環境構築(`package.json` 作成、`scripts/validate-data.mjs` を実行できる状態にする)

**完了条件**:
- ブラウザで盤面が表示され、人間が四間飛車側を指し、AIが居飛車らしい手を返してくる対局が最後まで成立する
- `scripts/validate-data.mjs` が実行でき、`data/examples/` の全ファイルが検証を通る

**触ってよい主なディレクトリ**: `apps/`, `scripts/`, ルートの `package.json`

## Phase 1 ― 観察コーチ

**目的**: パイプラインの②〜④・⑨(現在の形・相手の意図・相手の次の狙い・初心者向け説明)を実装し、対局しながら「今何が起きているか」が見えるようにする。ユーザーはまだ目標形を選べない(システムが候補を提示するのみ)。

**成果物**:
- `data/shapes/` に美濃系の形を3種類程度(本美濃・高美濃・銀冠など)
- `data/openings/` に四間飛車・居飛車のエントリ
- `data/intents/` に居飛車側の代表的な狙いを3〜4種類(棒銀・斜め棒銀・早仕掛けなど)
- 形判定ロジック・意図推定ロジック(定跡照合を第一手段、汎用ヒューリスティックをフォールバックとする設計。詳細は実装時に別途設計メモを作る)
- 「目的→手→理由」テンプレートによる説明生成(⑨)
- 用語集とツールチップ

**完了条件**:
- 四間飛車vs居飛車の対局を最初から最後まで行い、現在の形・相手の意図・相手の次の狙いが、専門用語の説明つきで画面に表示される
- 定跡データが持つ範囲の局面で、明らかに誤った意図表示が出ないことを人間が確認する
- 定跡から外れた局面でも、アプリが無言・エラーにならず「未分類」等の穏当な表示に落ちる

**触ってよい主なディレクトリ**: `apps/server/src/analysis`, `apps/web`, `data/shapes/`, `data/openings/`, `data/intents/`

**注意**: このPhaseで初めて本番データを作り始める。[../CLAUDE.md](../CLAUDE.md) のルール4番(大量生成禁止)を守り、数件ずつ人間レビューを挟むこと。

## Phase 2 ― 経路コーチ

**目的**: パイプラインの⑤〜⑧(自分の目的・目指せる形・候補手・その手の目的)を実装し、ユーザーが目標形を選び、そこまでの道筋(候補手の並び)を見られるようにする。

**成果物**:
- 目指せる形のランキングロジック(shape graphを使ったスコアリング)
- 経路プランナー(path planner): 現在局面と目標形から、次に指すべき手の候補を算出
- 候補手とエンジンのMultiPV結果を突き合わせ、安全確認(悪手排除)を行うロジック
- ユーザーが2〜3個の候補から目標形を選べるUI

**完了条件**:
- ユーザーが目標形を選ぶと、次の一手候補が「目的→手→理由」つきで表示される
- 表示される候補手が、エンジンの評価値で見て明らかな悪手でないことを人間が複数局面で確認する

**触ってよい主なディレクトリ**: `apps/server/src/analysis`, `apps/web`

**実対局確認で判明した設計上の限界(記録)**: Phase 5の通しプレイ確認の過程で、「目指せる形」から「この形へ近づく手の候補」(⑦候補手)を生成する `apps/server/src/analysis/pathPlanner.ts` が**単一手先読みのみ**(`typical_build_order` 上の次の1マスへ、現局面から1手で直接到達できる合法手しか候補にできない)であり、複数手先の経路計画を行っていないことを確認した(実対局での`candidateMoveState: "unavailable"`の再現、および`pathPlanner.ts`のコード上のコメントで確認済み)。現在の3形(本美濃・高美濃・銀冠)はいずれも `typical_build_order` の先頭が `8h`(玉)であり、玉が初期位置からそこへ到達するまでの間、候補手が出せない局面が非常に多い。

この限界への対応は Phase 6(下記)で行う。

## Phase 6 ― 経路コーチ / 毎手説明

**目的**: 次の3つを統合し、「選んだ形に近づくために、今この局面で何を指せばよいか」が対局中つねに分かる状態にする。

- 選択したshapeに近づくための**経路計画**(複数手先の道のり)
- その経路の、**現在局面における最初の一手**の提示
- **毎手説明**(1手ごとに何が起きたか・次に何を考えるべきか)

**背景**: Phase 5の記録(上記)のとおり、`pathPlanner.ts` が単一目標マス・1手先読みに限定されているため、3形すべてで序盤に候補手が出せなかった。Phase 6ではこの制約を解消する新しい経路探索ロジックを正式に導入する(Phase 5では禁止されていた作業)。

**Unit構成**:

「目的」の3項目とUnitの対応:

| 目的 | 担当Unit | 状態 |
|---|---|---|
| 選択したshapeに近づくための経路計画 | Unit 1 | 実装済み |
| その経路の、現在局面における最初の一手の提示 | Unit 1 | 実装済み |
| 毎手説明 ― 何が起きたか(形・経路の変化) | Unit 2 | 実装済み |
| 毎手説明 ― 何が起きたか(盤面上の出来事: 捕獲・王手・成り) | Unit 3 | 実装済み |
| 毎手説明 ― 次に何を考えるべきか | Unit 4 | 完了(人間判定済み) |

- **Unit 1(実装済み)**: 経路計画と候補手生成の基盤。
  - `apps/server/src/analysis/routePlanner.ts` を新設(複数の未達成マスを同時に扱い、各マスへの複数手の経路と、その経路の「現在局面で指せる最初の一手」を求める)。エンジン非依存・決定的な純粋ロジックで、将棋のルール判定はshogiopsと既存の `rules/` に委ねる。
  - 既存の `pathPlanner.ts` は削除も変更もせず温存する(本番の候補生成経路からは使わなくなった)。
  - 目標マスを自駒が塞ぐ場合の**準備手**を扱う。ただし「どこへ退避させるのが良いか」という将棋的な評価は導入せず、合法手を機械的に列挙するに留める。
  - 既に形の一部として成立しているマスの駒は動かさない(形を壊す候補手を作らない)。同じ駒を複数の目標マスへ二重に割り当てない。
  - `notation/japaneseSquare.ts` を新設し、説明・UI表示のマス目を日本語表記(`8h`→`８八`)に変換する([DATA_MODEL.md](DATA_MODEL.md) の座標表記の規約に従い、内部データはUSI形式のまま)。
  - UIは「選択した形 → 必要なマス → 今どこまで出来ているか → 未達成部分の道のり → その最初の一手 → 候補手」という因果を表示する。
- **Unit 2(実装済み)**: 毎手説明(1手ごとの事実抽出と説明生成)。
  - `apps/server/src/analysis/moveOutcomeDetector.ts` を新設。ユーザー着手直前と、相手の応手まで終えた現在の局面について、Unit 1 の経路計画と形判定の結果を突き合わせ、**直前の一手で何が変わったか**を機械的な事実として列挙する(経路が進んだ/完成した/続けられなくなった、準備手が必要になった/不要になった、目標形が変わった等)。エンジンにもLLMにも依存しない決定的な純粋関数。
  - `apps/server/src/analysis/moveOutcomeExplanation.ts` を新設。事実 → 初心者向けの文言への対応表。評価語(最善・おすすめ・安全・悪手・形勢)は一切使わない。
  - **原因の帰属は3ルールに限定する**: (1) ユーザーの着手そのものから直接確認できる変化、(2) 既存の `planChangeReason.ts` が確定分類した理由、(3) それ以外は原因を断定せず変化した事実だけを述べる。推測による原因説明はしない。
  - 目標形が変わった手では、形・経路の差分を一切出さない(形ごとに必須マスの定義が違うため、比較すると誤った「崩れた」等の説明になる)。目標形の変更直後は `lastMoveOutcome` を null にリセットする。
  - `planChangeDetector.ts` / `planChangeReason.ts` の判定条件は変更していない(結果を受け取って使うだけ)。
  - UIは既存の「形 → 未達成マス → 経路 → 残り手数 → 候補手」を変更せず、その上に「直前の一手」ブロックを追加する。
- **Unit 3(実装済み)**: 盤面で実際に起きたこと(捕獲・王手・成り)の事実抽出と説明生成。
  - `apps/server/src/analysis/boardEventDetector.ts` を新設。着手の前後の局面だけから、捕獲・王手・成りを、自分の手によるものか相手の手によるものかの帰属つきで確定する。将棋の知識データ(shapes/openings/intents)には一切依存せず、エンジンにもLLMにも依存しない決定的な純粋関数。

**目的**: 何もない初期局面から対局を始め、一手ごとの盤面変化から形・戦型・意図・狙いが徐々に生まれ、それが初心者にも**盤面上で**理解できる状態を目指す。**最初に答えを決めて、そこへ誘導しない。**

**プレイ画面の情報設計(人間の判断。Unit 3 に適用。2026-09-09 に人間が再確認)**

**プレイ画面に表示する情報を過剰にしない。** 特に「意図」に関する情報を重複させない。「今の意図」「相手の意図」「この手の意図」「意図の説明」をそれぞれ独立した情報として並べず、**「意図」という一つの情報体系に統合する**。

基本案:

> **「この手の意図」** → この手が何を意図しているのか → 必要に応じて、その背景として相手の意図や局面上の意図を含める

一方、**戦術の説明**と**具体的なやり方**は、意図とは別の情報として残す。したがって情報の大枠は次の階層を基本とする。

```
1. 何が起きたか
2. この手の意図
3. 戦術の説明
4. やり方
```

**これは現時点でUIの最終配置まで固定するものではない。** Unit 2 で一手ごとの認識を実装し、Unit 3 で盤上による視覚的提示を実装したあと、**実際のプレイ画面を触りながら情報量と配置を最終調整する**。Unit 3 では特に、上記「盤面上の対象駒 → 移動元を強調 → 移動先を矢印で表示 → その下に『なぜこの手なのか』」という基本UIとの整合を確認する。

**実装担当への指示**: 上記の案を機械的にそのまま実装する必要はない。次の点で**明らかに優れた設計案がある場合は、実装前に必ず代替案として提示すること**。

- 情報量を減らせる
- 同じ内容の重複をさらに排除できる
- 初心者が局面を理解しやすい
- 「何が起きたか → なぜそうしたか → どうすればいいか」という流れをより自然にできる
- 盤面を見るだけで理解できる部分を増やせる

**ただし、この案を勝手に変更して実装してはいけない。代替案を提示し、人間の判断・承認を得てから採用すること。**

**「情報を増やせば分かりやすくなる」という方向へ安易に進まない。** 同じ意味を複数の場所で説明することを避け、可能な限り一つの情報に統合する。**本番画面を、情報を大量に並べて教える画面にはしない。** 局面から必要な情報が自然に立ち上がり、ユーザーが盤面を見ながら理解できるUIを目指す。これは Phase 7 の上位原則(「四間飛車 vs 居飛車という設定そのものをやめる。何もない状態から、一手ごとに生まれていく」)と整合させる。

**人間の判断が必要**: 「直す / 現仕様として受容する / 次Phaseへ持ち越す」のいずれかを明示するまで**未処遇**として扱う。なお本ファイルの Unit 3 に記録された情報設計の方針(情報を過剰にしない・同じ意味を複数箇所で説明しない)に照らすと、**Unit 3 または Unit 5 で整理する対象にもなりうる**。

**実施順序(人間が確定)**:

```
Unit 0(何もない状態へ戻す)
  → Unit 1(素のエンジンで実測) → 人間の判断
  → Unit 2(一手ごとの認識)
  → Unit 3(盤上で見せる)
  → 実際に触って「分かりやすいか」を確認する(人間)
  → Unit 4(分かってきたこと + N-3)
  → Unit 5(コーチング拡張)
  → Unit 6(知識の追加)
```

**知識の追加を最後に置く理由**: ユーザーが画面上で「何を認識したのか」「なぜそう認識したのか」「次に何をすればいいのか」を直感的に理解できない状態でデータを増やすと、**増やすほど複雑になる**ため。形・使いやすさを先に作る。

**Unit 1 の後に必ず人間の判断を挟む。** 相手AIの強さ・手加減は Kind 3 であり、実測の結果を見てから人間が決める。

**「候補手を主導線にしない」と Unit 3(盤上で見せる)の関係**: 前者が決めるのは候補手を**いつ**出すか(主導線ではなく、認識を示したうえでユーザーが求めたときに出す)、Unit 3 が決めるのは**どう**出すか(文字の羅列ではなく盤上で)である。**矛盾しない。** 全体の順序は次のとおり。

```
認識 → 盤面上で「何が起きたか」を示す → 必要なら候補手を見る → その候補手を盤上で視覚的に示す
```

#### 4段階の文言

| 段階 | 文言 |
|---|---|

自分の形が**完成している**場合(`completed`)と相手の狙いが `matched` の場合は、従来どおり名前を出してよい(`draft` の場合は上記「`draft` の表示」に従う)。

乙(表の適用範囲を対局経過ブロックに限定する案)は採らない。同じ画面の2つのブロックが同じ対象について片方は名前を出し片方は出さない状態になり、既知事項②(現在の形と目標形が別々の名前で並ぶ)を悪化させるためである。

#### 序盤の強制進行中の文言(人間判断・論点3)

`apps/server/src/analysis/explanationGenerator.ts` の強制進行中の説明は、次の一文に差し替える。

> 相手の今の手は、対局序盤の決まった手順によるものです。

現行の後半「そのため、狙いはまだ判定できません。」を削る。「相手の狙い」への言及をなくすことで、ζ-4a の非開示境界(相手AIの狙い・制御手順・選択理由を出さない)との両立をより明確にする。**どの狙いを選んだかは依然として一切述べない。**

#### 露出制御の実装要件(ζ-3 で確定)

`review_status` は ζ-3 の時点で `apps/` から**一切参照されておらず**、`ShapeDefinition` は `review_status` をフィールドとして持ってすらいなかった。その結果、`draft` の「銀冠」が次の**7経路**で断定表示されていた。

**訂正の記録**: ζ-3 はこれを「5経路」と記載したが、STEP ζ-5 の計画レビューで**2経路の見落とし**(候補手の説明文・候補手セクションの見出し)が独立監査により指摘され、実コードで確認された。以下は訂正後の7経路である。

| # | 経路 | ζ-3 時点の表示 | `draft` のときの表示(ζ-5 で実装) |
|---|---|---|---|
| 1 | 現在の形の説明(`explanationGenerator.ts`) | 今、銀冠の形ができています。 | 今、銀冠と呼ばれる並びに近い形になっています。ただし、この形の説明は内容を確認中のため、参考程度に見てください。 |
| 2 | 相手の狙いの説明(`explanationGenerator.ts`) | 相手は{名前}の形になっています。 | **名前を出さず、既存の unclassified 文言に落とす**(新しい文言を作らない)。intents は全件 `human_reviewed` のため現状の画面に変化はない |
| 3 | 目標形の進捗(`stateResponse.ts` → `apps/web/src/main.ts`) | 「銀冠」の組み上がり | 「銀冠」(内容を確認中の形)の組み上がり |
| 4 | 目標形の選択ボタン(`apps/web/src/main.ts`) | 銀冠 | 銀冠(内容を確認中の形) |
| 5 | 必要なマスの説明(`nextConsiderationExplanation.ts`) | 「銀冠」に必要なマスは、すべて埋まっています。 | 「銀冠」(内容を確認中)に必要なマスは、すべて埋まっています。 |
| 6 | **候補手の説明文(`candidateMoveExplanation.ts`)** | 「銀冠」の銀を…(1つの説明文に最大4回、名前が出る) | **説明文は変えない。** 候補手セクションの見出しの直下に「この形の説明は内容を確認中のため、参考程度に見てください。」を1行出す |
| 7 | **候補手セクションの見出し(`apps/web/src/main.ts`)** | 「銀冠」に近づく手の候補 | 「銀冠」(内容を確認中の形)に近づく手の候補 |

経路6で名前の出現ごとに注記を付けない理由は、1つの説明文に最大4回名前が出るため初心者に読めなくなるからである(人間承認済み)。見出し(経路7)がフォールバックしても注意書きは独立に出るため、漏れない。

実装要件:

1. `ShapeDefinition` / `IntentDefinition` が `review_status` を読み込む(`apps/` は `data/openings/` を `scenarioRepository` 経由でしか読んでおらず、戦型名をユーザーへ出す経路が存在しないため、openings は対象外)
2. 戦法・陣形・狙いの名前をユーザーへ出す経路は**すべて1つの関数を通す**。ζ-4a の `toPublicGameState()` と同じ許可リスト方式とし、経路を新設しても既定では名前が素通りしないようにする
3. `draft` の場合の表示は上記「`draft` の表示」に従う
4. `review_status` の**生値はAPIレスポンスへ出さない**。出すのは表示用の注記だけとし、名前を出してよいかの判断はサーバー側に閉じる
5. 現在は本番から呼ばれていない経路(`candidateMoveExplanation.ts` の旧 pathPlanner 経路)にも同じゲートを通す。**将来の再有効化で名前が素通りしないようにするため**であり、削除はしない

**この7経路の是正は Phase 7 完了条件「`draft` の知識が断定表示されない」の対象であり、Unit 4 の実装STEP(ζ-5)で扱う。**
