# 開発計画: Phase 0〜7

## 使い方

各Phaseには「目的」「成果物」「完了条件(次に進んでよい基準)」「触ってよい主なディレクトリ」を書く。Phaseは順番に進めることを基本とするが、完了条件を満たさないまま次のPhaseの作業を始めない。完了の判定は人間(あなた)が行う([ROLES.md](ROLES.md) 参照)。

現在地: **Phase 6 完了(人間判定済み)**。Phase 0〜5 を経て `apps/web`・`apps/server` は実装済みで、Phase 6(下記)の内訳は、Unit 1(経路計画と、現在局面で指せる最初の一手)・Unit 2(直前の一手による形・経路の変化)・Unit 3(盤面で起きたこと: 捕獲・王手・成り)までが実装・検証済み(コミット `19523a3`)、Unit 4(次に何を考えるべきか)も実装・検証・独立監査を終えた。統合した通し確認を経て、人間が Phase 6 全体を完了と判定した(未解決の既知事項は下記に記録している)。各Unitの詳細・完了条件・既知事項は下記 Phase 6 を参照。なお `spike/`(shogiops+やねうら王のUSI疎通確認)・`prototypes/`(shape-matcherプロトタイプ等)は Phase 0 着手前の技術検証であり、`apps/` の本実装とは別物である。**Phase 7 は「局面からの逐次認識と、その視覚的な理解」として再定義された**(人間の方針変更。[../CLAUDE.md](../CLAUDE.md) の「絶対的な上位原則」)。旧定義「対局経過による認識形成と露出制御」の Unit 1(相手AIに狙いを持たせる)は廃止し、Unit 構成を差し替えた。旧 Unit 4(初心者向け説明の段階化)にあたる文言仕様の確定(STEP ζ-3)と `review_status` による露出制御の実装(STEP ζ-5)は**完了済み**だが、**これは途中成果物であり、本番導線はまだ旧方式(固定戦型)のままである。** 本番導線を新方式へ戻すのは Phase 7 の Unit 0 であり、**未着手**である。詳細は下記 Phase 7 を参照。

## Phase 0 ― 土台

**目的**: 何もない状態から、盤面が表示され、将棋エンジンと接続でき、四間飛車vs居飛車の対局が(仮のUIで良いので)成立する状態を作る。

**成果物**:
- `apps/web`・`apps/server` の雛形
- shogiops を使った合法手判定
- やねうら王とのUSI疎通(`usi`→`usiok`→`isready`→`readyok`→`position`→`go`→`bestmove`)
- AI側(居飛車)の序盤を一定の手順で強制進行させる仕組みの最小実装(定跡を「大量に」用意する必要はなく、四間飛車vs居飛車が成立する最小限の手順で良い)
- Node.js 環境構築(`package.json` 作成、`scripts/validate-data.mjs` を実行できる状態にする)

**完了条件**:
- ブラウザで盤面が表示され、人間が四間飛車側を指し、AIが居飛車らしい手を返してくる対局が最後まで成立する
- `scripts/validate-data.mjs` が実行でき、`data/examples/` の全ファイルが検証を通る

**触ってよい主なディレクトリ**: `apps/`, `scripts/`, ルートの `package.json`

## Phase 1 ― 観察コーチ

**目的**: パイプラインの②〜④・⑨(現在の形・相手の意図・相手の次の狙い・初心者向け説明)を実装し、対局しながら「今何が起きているか」が見えるようにする。ユーザーはまだ目標形を選べない(システムが候補を提示するのみ)。

**成果物**:
- `data/shapes/` に美濃系の形を3種類程度(本美濃・高美濃・銀冠など)
- `data/openings/` に四間飛車・居飛車のエントリ
- `data/intents/` に居飛車側の代表的な狙いを3〜4種類(棒銀・斜め棒銀・早仕掛けなど)
- 形判定ロジック・意図推定ロジック(定跡照合を第一手段、汎用ヒューリスティックをフォールバックとする設計。詳細は実装時に別途設計メモを作る)
- 「目的→手→理由」テンプレートによる説明生成(⑨)
- 用語集とツールチップ

**完了条件**:
- 四間飛車vs居飛車の対局を最初から最後まで行い、現在の形・相手の意図・相手の次の狙いが、専門用語の説明つきで画面に表示される
- 定跡データが持つ範囲の局面で、明らかに誤った意図表示が出ないことを人間が確認する
- 定跡から外れた局面でも、アプリが無言・エラーにならず「未分類」等の穏当な表示に落ちる

**触ってよい主なディレクトリ**: `apps/server/src/analysis`, `apps/web`, `data/shapes/`, `data/openings/`, `data/intents/`

**注意**: このPhaseで初めて本番データを作り始める。[../CLAUDE.md](../CLAUDE.md) のルール4番(大量生成禁止)を守り、数件ずつ人間レビューを挟むこと。

## Phase 2 ― 経路コーチ

**目的**: パイプラインの⑤〜⑧(自分の目的・目指せる形・候補手・その手の目的)を実装し、ユーザーが目標形を選び、そこまでの道筋(候補手の並び)を見られるようにする。

**成果物**:
- 目指せる形のランキングロジック(shape graphを使ったスコアリング)
- 経路プランナー(path planner): 現在局面と目標形から、次に指すべき手の候補を算出
- 候補手とエンジンのMultiPV結果を突き合わせ、安全確認(悪手排除)を行うロジック
- ユーザーが2〜3個の候補から目標形を選べるUI

**完了条件**:
- ユーザーが目標形を選ぶと、次の一手候補が「目的→手→理由」つきで表示される
- 表示される候補手が、エンジンの評価値で見て明らかな悪手でないことを人間が複数局面で確認する

**触ってよい主なディレクトリ**: `apps/server/src/analysis`, `apps/web`

## Phase 3 ― 適応コーチ

**目的**: パイプラインの⑤〜⑧を、相手の指し手に応じて動的に再計算できるようにする(道筋の変更とその理由の説明)。

**成果物**:
- 計画済みの道筋が相手の手によって崩れたことを検知するロジック
- 再計画と、「なぜ計画が変わったか」の説明生成

**完了条件**:
- 相手が候補手の前提を崩す手を指したとき、道筋が変わり、その理由が説明として表示される
- 極端なケース(相手が大駒を取りに来る等)でも、安全確認(Phase2の仕組み)が機能し続ける

**触ってよい主なディレクトリ**: `apps/server/src/analysis`

## Phase 5 ― 仕上げ

**目的**: 通しプレイによる表現・タイミング・UIの調整に限定する(新しい将棋知識・新しいロジックは扱わない)。

**成果物**:
- 通しプレイ(5局程度)で見つかったUI・文言・表示タイミングの問題の修正
- 既存ロジックの軽微な不具合修正(判定結果そのものを変えるような修正は含まない)

**完了条件**:
人間が5局程度を実際に通しプレイし、以下をすべて確認する。
- 対局操作に破綻がない
- UI表示に破綻がない
- 説明の表示タイミングに大きな違和感がない
- 説明文が初心者にも理解できる
- 「目的→手→理由」の流れが自然である
- forced opening時の説明が不自然でない
- intentが判定できない局面で無理な断定をしていない
- 対局状態と説明内容に不整合がない

**Phase 5で修正してよい範囲**(通しプレイで発見された問題に限る):
- UI上の問題
- 表現・文言の問題
- 説明表示タイミングの問題
- 既存ロジック上の軽微な不具合

**Phase 5で追加・変更しないもの**:
- 新しい将棋知識(shapes/openings/intentsの新規追加)
- 新しい戦法・形・intentデータ
- 新しいヒューリスティック
- 新しい重み・閾値
- LLMによる将棋事実の判断
- 既存の判定ロジックを覆す新規推測ロジック
- 対局シナリオ本実装(`scenarioOpponentOpening.ts`の本番機能化を含む。[SCENARIOS.md](SCENARIOS.md)参照)**← Phase 7 の再定義により、これは「このPhaseではやらない」ではなく「本番では行わない」に変わった**

**触ってよい主なディレクトリ**: `apps/web/`, `apps/server/src/analysis/`(既存ロジックの軽微な不具合修正のみ), 既存の `data/shapes|openings|intents` 内の文言フィールド(`characteristics`等の言い回し修正のみ、新規追加は不可)

**注意**: Phase 5の完了判定は人間が行う。「体験として破綻がない」ことをAIエージェントが独自に判定してPhase完了扱いにしない([ROLES.md](ROLES.md))。

**実対局確認で判明した設計上の限界(記録)**: Phase 5の通しプレイ確認の過程で、「目指せる形」から「この形へ近づく手の候補」(⑦候補手)を生成する `apps/server/src/analysis/pathPlanner.ts` が**単一手先読みのみ**(`typical_build_order` 上の次の1マスへ、現局面から1手で直接到達できる合法手しか候補にできない)であり、複数手先の経路計画を行っていないことを確認した(実対局での`candidateMoveState: "unavailable"`の再現、および`pathPlanner.ts`のコード上のコメントで確認済み)。現在の3形(本美濃・高美濃・銀冠)はいずれも `typical_build_order` の先頭が `8h`(玉)であり、玉が初期位置からそこへ到達するまでの間、候補手が出せない局面が非常に多い。

Phase 5では新しい将棋知識・判定ロジックを追加しないという制約により、本Phaseでは対応しない。**shapeを追加するだけでは解決せず、pathPlanner自体の仕様再設計(複数手先の経路計画への対応)が必要**になる見込み。現在のshapeは本美濃・高美濃・銀冠の3種類のみで、これ以外のshapeを追加する計画は現時点で存在しない(スコープ変更には[../CLAUDE.md](../CLAUDE.md)の「現在のスコープ」に対する人間の承認が必要)。

この限界への対応は Phase 6(下記)で行う。

## Phase 6 ― 経路コーチ / 毎手説明

**目的**: 次の3つを統合し、「選んだ形に近づくために、今この局面で何を指せばよいか」が対局中つねに分かる状態にする。

- 選択したshapeに近づくための**経路計画**(複数手先の道のり)
- その経路の、**現在局面における最初の一手**の提示
- **毎手説明**(1手ごとに何が起きたか・次に何を考えるべきか)

**背景**: Phase 5の記録(上記)のとおり、`pathPlanner.ts` が単一目標マス・1手先読みに限定されているため、3形すべてで序盤に候補手が出せなかった。Phase 6ではこの制約を解消する新しい経路探索ロジックを正式に導入する(Phase 5では禁止されていた作業)。

**Unit構成**:

「目的」の3項目とUnitの対応:

| 目的 | 担当Unit | 状態 |
|---|---|---|
| 選択したshapeに近づくための経路計画 | Unit 1 | 実装済み |
| その経路の、現在局面における最初の一手の提示 | Unit 1 | 実装済み |
| 毎手説明 ― 何が起きたか(形・経路の変化) | Unit 2 | 実装済み |
| 毎手説明 ― 何が起きたか(盤面上の出来事: 捕獲・王手・成り) | Unit 3 | 実装済み |
| 毎手説明 ― 次に何を考えるべきか | Unit 4 | 完了(人間判定済み) |

- **Unit 1(実装済み)**: 経路計画と候補手生成の基盤。
  - `apps/server/src/analysis/routePlanner.ts` を新設(複数の未達成マスを同時に扱い、各マスへの複数手の経路と、その経路の「現在局面で指せる最初の一手」を求める)。エンジン非依存・決定的な純粋ロジックで、将棋のルール判定はshogiopsと既存の `rules/` に委ねる。
  - 既存の `pathPlanner.ts` は削除も変更もせず温存する(本番の候補生成経路からは使わなくなった)。
  - 目標マスを自駒が塞ぐ場合の**準備手**を扱う。ただし「どこへ退避させるのが良いか」という将棋的な評価は導入せず、合法手を機械的に列挙するに留める。
  - 既に形の一部として成立しているマスの駒は動かさない(形を壊す候補手を作らない)。同じ駒を複数の目標マスへ二重に割り当てない。
  - `notation/japaneseSquare.ts` を新設し、説明・UI表示のマス目を日本語表記(`8h`→`８八`)に変換する([DATA_MODEL.md](DATA_MODEL.md) の座標表記の規約に従い、内部データはUSI形式のまま)。
  - UIは「選択した形 → 必要なマス → 今どこまで出来ているか → 未達成部分の道のり → その最初の一手 → 候補手」という因果を表示する。
- **Unit 2(実装済み)**: 毎手説明(1手ごとの事実抽出と説明生成)。
  - `apps/server/src/analysis/moveOutcomeDetector.ts` を新設。ユーザー着手直前と、相手の応手まで終えた現在の局面について、Unit 1 の経路計画と形判定の結果を突き合わせ、**直前の一手で何が変わったか**を機械的な事実として列挙する(経路が進んだ/完成した/続けられなくなった、準備手が必要になった/不要になった、目標形が変わった等)。エンジンにもLLMにも依存しない決定的な純粋関数。
  - `apps/server/src/analysis/moveOutcomeExplanation.ts` を新設。事実 → 初心者向けの文言への対応表。評価語(最善・おすすめ・安全・悪手・形勢)は一切使わない。
  - **原因の帰属は3ルールに限定する**: (1) ユーザーの着手そのものから直接確認できる変化、(2) 既存の `planChangeReason.ts` が確定分類した理由、(3) それ以外は原因を断定せず変化した事実だけを述べる。推測による原因説明はしない。
  - 目標形が変わった手では、形・経路の差分を一切出さない(形ごとに必須マスの定義が違うため、比較すると誤った「崩れた」等の説明になる)。目標形の変更直後は `lastMoveOutcome` を null にリセットする。
  - `planChangeDetector.ts` / `planChangeReason.ts` の判定条件は変更していない(結果を受け取って使うだけ)。
  - UIは既存の「形 → 未達成マス → 経路 → 残り手数 → 候補手」を変更せず、その上に「直前の一手」ブロックを追加する。
- **Unit 3(実装済み)**: 盤面で実際に起きたこと(捕獲・王手・成り)の事実抽出と説明生成。
  - `apps/server/src/analysis/boardEventDetector.ts` を新設。着手の前後の局面だけから、捕獲・王手・成りを、自分の手によるものか相手の手によるものかの帰属つきで確定する。将棋の知識データ(shapes/openings/intents)には一切依存せず、エンジンにもLLMにも依存しない決定的な純粋関数。
  - 局面遷移は既存の `rules/applyMove.ts`(合法性確認込みの唯一の局面遷移API)に委ね、独自の遷移ロジックを複製しない。ユーザーの手と相手の手を別々の局面遷移として個別に評価するため、どの手による出来事かが構造上つねに一意に決まる(Unit 2 のような原因帰属の曖昧さが発生しない)。
  - ドロップ(持ち駒を打つ手)を捕獲・成りとして誤認しない。駒種を確定できない場合(対応表に無い成駒など)は推測せず、駒名を付けずに「駒」とする。
  - `apps/server/src/analysis/boardEventExplanation.ts` を新設。事実 → 初心者向けの文言への対応表。評価語・損得・危険性・推奨(「損をした」「危険です」「取り返しましょう」等)は一切使わない。「成れる状態だった」「取られそう」といった、実際には起きていないことも述べない。
  - `apps/server/src/analysis/pieceMapping.ts` に `roleToJapanese` を追加する(既存の関数は変更しない)。
  - Phase 3 の「前回の計画が使えなくなりました。」と Unit 2 の `route_lost` が同一局面で同じ事象を二重に述べる場合、Phase 3 側の通知を表示しない(判定ロジックは一切変更せず、表示の抑止のみ)。
  - `routePlanner.ts` / `moveOutcomeDetector.ts` / `moveOutcomeExplanation.ts` など、Unit 1・Unit 2 のモジュールは変更しない。
  - UIは Unit 2 の「直前の一手」ブロックをそのまま使い、盤面で起きたことを形・経路の説明より先に述べる。
- **Unit 4(完了)**: 毎手説明のうち「次に何を考えるべきか」。
  - 直前の一手による差分(Unit 2・Unit 3)ではなく、**現在局面の静的な状態**を整理して示す。着手前の局面・`lastMoveOutcome`・`lastBoardEvents` は使わない。`server.ts` は変更しない(現在局面だけから計算できるため、モジュール変数を増やさない)。

## Phase 7 ― 局面からの逐次認識と、その視覚的な理解

> **この Phase を一言で言えば、「戦型を教える Phase」から「局面から学習対象が生まれる Phase」への転換である。**
>
> 旧 Phase 7 の資産は捨てない。**認識エンジンを残し、対局の入口と情報提示の順序を変える。** これが変更の本質である。

**目的**: 何もない初期局面から対局を始め、一手ごとの盤面変化から形・戦型・意図・狙いが徐々に生まれ、それが初心者にも**盤面上で**理解できる状態を目指す。**最初に答えを決めて、そこへ誘導しない。**

**再定義の記録**: 本 Phase は当初「対局経過による認識形成と露出制御」として定義され、Unit 1 に「相手AIに狙いを持たせる(固定シナリオ)」を置いていた。人間の方針変更([../CLAUDE.md](../CLAUDE.md) の「絶対的な上位原則」)により、**Phase 8 を新設せず本 Phase の Unit 構成を差し替える**形で再定義した。旧 Unit との差分は下記「旧 Unit 構成との差分」に残す。

**Phase 7 の最重要原則**:

> **システムは対局開始時に何も決めない。述べてよいのは、その時点で盤面から実際に生じたものだけである。**

既存の原則も維持する。

> **知識の追加可能性と、知識のユーザーへの露出可能性は独立した制御である。**

- Kind 1(記述的知識)は件数制限なく追加できる
- `review_status` はユーザーへの**断定的な露出**を制御する(STEP ζ-5 で実装済み)
- Kind 2・Kind 3 の確定・制御利用には、それぞれ定められた人間承認を要求する

**STEP ζ-5 の位置づけ**: ζ-5(`review_status` の露出制御 + `forming` で名前を出さないこと)を「完成させれば新方式になる」ものと考えない。**ζ-5 は既存の露出制御を整理した途中成果物である。** 本番導線そのものを新方式へ戻すのは Unit 0 である。ζ-5 の成果は新方針でも有効なので捨てないが、それだけでは対局の入口は旧方式のままである。

**Unit構成**:

- **Unit 0: 本番対局を「何もない状態から開始する」状態へ戻す**
  - **これは整理作業ではない。** 対局の入口から、事前に決められたものをすべて取り除くことが目的である
  - 進め方は次の順とする(人間の指示): **①現在どこに固定戦型・固定目標形が残っているかを完全に洗い出す → ②本番導線から外す → ③ブラウザで何もない状態から対局できることを確認する。** いきなり大改修しない
  - `engine/forcedOpponentOpening.ts` を**本番の対局ロジックから外す**(削除しない。開発・検証用へ降格する)
  - 画面の固定ラベルから戦法名を外す(置換文言は下記「初心者向け説明の段階化の文言仕様」の「固定ラベルの置換」で確定済み)。画面タイトルの陳腐化(既知事項 N-4)もあわせて直す
  - [../CLAUDE.md](../CLAUDE.md)・本ファイル・[SCENARIOS.md](SCENARIOS.md) を新方針に合わせて書き換える(**MVPスコープの変更。[CHANGE_MANAGEMENT.md](CHANGE_MANAGEMENT.md) に従い同時に直す**)
  - 序盤の強制進行中の文言(「相手の今の手は、対局序盤の決まった手順によるものです。」)が本番導線で必要かを再確認する。`forcedOpponentOpening` が本番から外れるなら**本番では不要**になる見込みで、開発モード(`?scenario=`)では引き続き必要
  - **完了条件(すべて満たすこと)**: ①四間飛車 vs 居飛車を初期設定しない ②美濃囲いを目標として初期設定しない ③相手に居飛車を強制しない ④`forcedOpponentOpening` が本番の対局ロジックから外れている ⑤`scenario` 系は開発・検証専用として残っている(本番導線からは到達しない) ⑥初期局面に戦型・形・意図を設定していない
  - **やらないこと**: 相手AIの強さ調整(Kind 3。Unit 1 の実測結果を見て人間が判断する)
- **Unit 1: 素のエンジンでの対局を実測する(実装ではなく観測)**
  - 何も指定しない状態でエンジンに指させ、**ブラウザで実際に対局する**
  - 観測項目: 初心者に対して強すぎないか / 不自然な手・人間離れした手がどの程度出るか / 既存の認識機能がどの程度働くか / 「一手ごとに形が生まれる」体験になっているか / **認識できない場面・認識が不自然になる場面**(Unit 6 の入力になる)
  - 結果を本ファイルに記録し、**人間へ提示する**
  - **この Unit で Kind 3 の AI 挙動を作らない。**「エンジンが強すぎるから初心者向けにこういう手を指させよう」とすぐ実装しない。まず実際の対局を観察してから判断する
  - **完了条件**: 実測記録が人間へ提示され、AIの強さ・手加減・応答ロジックについて人間が次の判断を下せる状態になること
- **Unit 2: 一手ごとの認識の時系列**
  - 指し手履歴から認識状態を**毎回再計算**する(`server.ts` にモジュール変数を増やさない)
  - 認識の段階は `none` → `forming` → `matched` → `completed`
  - 既存の `shapeFormationAnalyzer.ts`(特に `formationEvidence`)と `intentDetector.ts` を土台にする。**新しい判定方式・閾値を発明しない**
  - 自分側・相手側を区別せず、一手ごとに盤面から認識する構造に一本化する(旧 Unit 5 の統合先)
  - 履歴を途中まで切り詰めて再計算する際、対応する中間局面のSFENも同時に用意する
  - 決定的な純粋関数とし、エンジンにも LLM にも依存しない
- **Unit 3: 盤上で見せることを、コーチングの基本UIにする(最重要級)**
  - **これは装飾ではない。**「４五 → ５五」のような文字情報だけでは、初心者は**盤上のどの駒をどこへ動かすのか**が分からない
  - 提示の順序: **盤面上の対象駒 → 移動元を強調 → 移動先を矢印で表示 → その下に「なぜこの手なのか」を短い文章で**
  - **「何をどこへ動かすのか」が一瞬で分かること**を最優先とする。理由の説明はその下に置く
  - 認識結果(形・意図)についても、根拠になったマス・駒を盤上で示せるようにする
  - **将棋の手順を文字列として読ませるUIから、盤面を見て理解できるUIへ変える**
  - **やらないこと**: 新しい将棋の意味づけをUI側で作らない(提示のみ)

**プレイ画面の情報設計(人間の判断。Unit 3 に適用)**

**プレイ画面に表示する情報を過剰にしない。** 特に「意図」に関する情報を重複させない。「今の意図」「相手の意図」「この手の意図」「意図の説明」をそれぞれ独立した情報として並べず、**「意図」という一つの情報体系に統合する**。

基本案:

> **「この手の意図」** → この手が何を意図しているのか → 必要に応じて、その背景として相手の意図や局面上の意図を含める

一方、**戦術の説明**と**具体的なやり方**は、意図とは別の情報として残す。したがって情報の大枠は次の階層を基本とする。

```
1. 何が起きたか
2. この手の意図
3. 戦術の説明
4. やり方
```

**これは現時点でUIの最終配置まで固定するものではない。** Unit 2 で一手ごとの認識を実装し、Unit 3 で盤上による視覚的提示を実装したあと、**実際のプレイ画面を触りながら情報量と配置を最終調整する**。Unit 3 では特に、上記「盤面上の対象駒 → 移動元を強調 → 移動先を矢印で表示 → その下に『なぜこの手なのか』」という基本UIとの整合を確認する。

**実装担当への指示**: 上記の案を機械的にそのまま実装する必要はない。次の点で**明らかに優れた設計案がある場合は、実装前に必ず代替案として提示すること**。

- 情報量を減らせる
- 同じ内容の重複をさらに排除できる
- 初心者が局面を理解しやすい
- 「何が起きたか → なぜそうしたか → どうすればいいか」という流れをより自然にできる
- 盤面を見るだけで理解できる部分を増やせる

**ただし、この案を勝手に変更して実装してはいけない。代替案を提示し、人間の判断・承認を得てから採用すること。**

**「情報を増やせば分かりやすくなる」という方向へ安易に進まない。** 同じ意味を複数の場所で説明することを避け、可能な限り一つの情報に統合する。**本番画面を、情報を大量に並べて教える画面にはしない。** 局面から必要な情報が自然に立ち上がり、ユーザーが盤面を見ながら理解できるUIを目指す。これは Phase 7 の上位原則(「四間飛車 vs 居飛車という設定そのものをやめる。何もない状態から、一手ごとに生まれていく」)と整合させる。

**Unit 4 との重複についての懸念(司令塔の判断・要人間確認。人間が明示した指示ではない)**

Unit 4(「ここまでの対局で分かってきたこと」)は認識を文章で述べるブロックであり、上記の「この手の意図」と**内容が重複する可能性がある**。ただし Unit 4 には既に確定した制約がある。

```
認識 → 盤面上で「何が起きたか」を示す → 必要なら候補手を見る → その候補手を盤上で視覚的に示す
```

| `none` | 観測されたシグネチャが 0 件 |

#### 4段階の文言

| 段階 | 文言 |
|---|---|
| 何も認識できていない(相手がまだ指していない/候補ゼロ) | まだ手数が少ないため、相手の狙いについて言えることはありません。 |
| 認識前(`none`)・相手が指している | 相手はここまでに{n}手指しています。まだ、狙いを読み取れる手がかりは現れていません。今の段階で相手の作戦を決めつけず、もう少し様子を見ましょう。 |
| `forming` | {n}手目の{駒}{マス}から、相手の駒が{向き}へ向かってきているように見えます。ただ、これがどの作戦になるかは、まだ決まっていません。 |
| `matched` の初出 | 相手の指し手が「{名前}」という作戦の形と一致しました。{名前}は、{初心者向けの説明}。{n}手目の{駒}{マス}が、そう見える手がかりになっています。ただし、必ずそうなると決まったわけではありません。 |
| 認識が変わったとき | {n}手目の{駒}{マス}で、見えている手がかりが増えました。今は{新しい段階の言い方}。 |

**`{向き}` の決め方**(機械的。MVP は自分=先手固定):

| 観測されたシグネチャの移動先の筋 | 表現 |
|---|---|
| 1〜3筋 | あなたから見て右側 |
| 4〜6筋 | 盤の中央 |
| 7〜9筋 | あなたから見て左側 |

**`{初心者向けの説明}`**: `data/intents/*.json` の `current_aim_explanation` をそのまま使う。実行時に新しい将棋の意味づけを生成しない。

**`forming` では説明文も出さない**: `data/intents/naname_bogin.json` の `current_aim_explanation` は本文中に「斜め棒銀」「棒銀」を含み、`data/intents/hayajikake.json` の `next_aim_explanation` は「棒銀や斜め棒銀」を含む。したがって `forming` で `{名前}` だけを伏せて説明文を出すと名前が漏れる。**`forming` では `current_aim_explanation` / `next_aim_explanation` を表示しない。** これらは `matched` の初出で名前を導入するときに初めて使う。

**認識が変わったときの制約**: 前の認識を否定する文を作らない。「〜ではありませんでした」「実は〜でした」は使わない。述べてよいのは**観測が増えた**という事実だけである。

| 状況 | 文言 |
|---|---|
| 双方 0 枚 | **この文を出さない** |

#### 既存文言への影響(人間判断・論点1 = 甲、両方に適用)

[DATA_MODEL.md](DATA_MODEL.md)「初心者への提示のしかた」の表は `forming` を「戦法の名前を出さず」と定めているが、既存の Phase 1 コーチ説明(`apps/server/src/analysis/explanationGenerator.ts`)は `forming` 相当の段階で名前を出している。**実装を表に合わせる**(= 甲)。適用範囲は**相手の狙いと自分の形の両方**とする。

| 対象 | 現行 | 変更後 |
|---|---|---|
| 自分の形・未完成 | `{名前}を作ろうとしている可能性があります(まだ完成はしていません)。` | 今の陣形は、選んだ形に近づいてきていますが、まだ完成していません。 |
| 相手の狙い・`forming` | `相手は{名前}を狙っている可能性があります(まだ断定はできません)。` | 上記「4段階の文言」の `forming` 行に従う |
| 相手の次の狙い・`forming` | `まだ断定はできませんが、{next_aim_explanation}` | 表示しない(説明文に名前が含まれるため) |

自分の形が**完成している**場合(`completed`)と相手の狙いが `matched` の場合は、従来どおり名前を出してよい(`draft` の場合は上記「`draft` の表示」に従う)。

乙(表の適用範囲を対局経過ブロックに限定する案)は採らない。同じ画面の2つのブロックが同じ対象について片方は名前を出し片方は出さない状態になり、既知事項②(現在の形と目標形が別々の名前で並ぶ)を悪化させるためである。

#### 序盤の強制進行中の文言(人間判断・論点3)

`apps/server/src/analysis/explanationGenerator.ts` の強制進行中の説明は、次の一文に差し替える。

> 相手の今の手は、対局序盤の決まった手順によるものです。

現行の後半「そのため、狙いはまだ判定できません。」を削る。「相手の狙い」への言及をなくすことで、ζ-4a の非開示境界(相手AIの狙い・制御手順・選択理由を出さない)との両立をより明確にする。**どの狙いを選んだかは依然として一切述べない。**

#### 露出制御の実装要件(ζ-3 で確定)

`review_status` は ζ-3 の時点で `apps/` から**一切参照されておらず**、`ShapeDefinition` は `review_status` をフィールドとして持ってすらいなかった。その結果、`draft` の「銀冠」が次の**7経路**で断定表示されていた。

**訂正の記録**: ζ-3 はこれを「5経路」と記載したが、STEP ζ-5 の計画レビューで**2経路の見落とし**(候補手の説明文・候補手セクションの見出し)が独立監査により指摘され、実コードで確認された。以下は訂正後の7経路である。

| # | 経路 | ζ-3 時点の表示 | `draft` のときの表示(ζ-5 で実装) |
|---|---|---|---|
| 1 | 現在の形の説明(`explanationGenerator.ts`) | 今、銀冠の形ができています。 | 今、銀冠と呼ばれる並びに近い形になっています。ただし、この形の説明は内容を確認中のため、参考程度に見てください。 |
| 2 | 相手の狙いの説明(`explanationGenerator.ts`) | 相手は{名前}の形になっています。 | **名前を出さず、既存の unclassified 文言に落とす**(新しい文言を作らない)。intents は全件 `human_reviewed` のため現状の画面に変化はない |
| 3 | 目標形の進捗(`stateResponse.ts` → `apps/web/src/main.ts`) | 「銀冠」の組み上がり | 「銀冠」(内容を確認中の形)の組み上がり |
| 4 | 目標形の選択ボタン(`apps/web/src/main.ts`) | 銀冠 | 銀冠(内容を確認中の形) |
| 5 | 必要なマスの説明(`nextConsiderationExplanation.ts`) | 「銀冠」に必要なマスは、すべて埋まっています。 | 「銀冠」(内容を確認中)に必要なマスは、すべて埋まっています。 |
| 6 | **候補手の説明文(`candidateMoveExplanation.ts`)** | 「銀冠」の銀を…(1つの説明文に最大4回、名前が出る) | **説明文は変えない。** 候補手セクションの見出しの直下に「この形の説明は内容を確認中のため、参考程度に見てください。」を1行出す |
| 7 | **候補手セクションの見出し(`apps/web/src/main.ts`)** | 「銀冠」に近づく手の候補 | 「銀冠」(内容を確認中の形)に近づく手の候補 |

経路6で名前の出現ごとに注記を付けない理由は、1つの説明文に最大4回名前が出るため初心者に読めなくなるからである(人間承認済み)。見出し(経路7)がフォールバックしても注意書きは独立に出るため、漏れない。

実装要件:

1. `ShapeDefinition` / `IntentDefinition` が `review_status` を読み込む(`apps/` は `data/openings/` を `scenarioRepository` 経由でしか読んでおらず、戦型名をユーザーへ出す経路が存在しないため、openings は対象外)
2. 戦法・陣形・狙いの名前をユーザーへ出す経路は**すべて1つの関数を通す**。ζ-4a の `toPublicGameState()` と同じ許可リスト方式とし、経路を新設しても既定では名前が素通りしないようにする
3. `draft` の場合の表示は上記「`draft` の表示」に従う
4. `review_status` の**生値はAPIレスポンスへ出さない**。出すのは表示用の注記だけとし、名前を出してよいかの判断はサーバー側に閉じる
5. 現在は本番から呼ばれていない経路(`candidateMoveExplanation.ts` の旧 pathPlanner 経路)にも同じゲートを通す。**将来の再有効化で名前が素通りしないようにするため**であり、削除はしない

**この7経路の是正は Phase 7 完了条件「`draft` の知識が断定表示されない」の対象であり、Unit 4 の実装STEP(ζ-5)で扱う。**
