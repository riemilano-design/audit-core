# 開発計画: Phase 0〜5

## 使い方

各Phaseには「目的」「成果物」「完了条件(次に進んでよい基準)」「触ってよい主なディレクトリ」を書く。Phaseは順番に進めることを基本とするが、完了条件を満たさないまま次のPhaseの作業を始めない。完了の判定は人間(あなた)が行う([ROLES.md](ROLES.md) 参照)。

現在地: **Phase準備段階(開発基盤構築中)**。`spike/`(shogiops+やねうら王のUSI疎通確認)や `prototypes/`(shape-matcherプロトタイプ等)による技術検証は行われているが、これらはPhase 0の成果物(下記「成果物」の `apps/web`・`apps/server` の雛形など)そのものではなく、Phase 0着手前の技術検証という位置づけである。Phase 0 本体(`apps/` の作成)はまだ開始していない。

## Phase 0 ― 土台

**目的**: 何もない状態から、盤面が表示され、将棋エンジンと接続でき、四間飛車vs居飛車の対局が(仮のUIで良いので)成立する状態を作る。

**成果物**:
- `apps/web`・`apps/server` の雛形
- shogiops を使った合法手判定
- やねうら王とのUSI疎通(`usi`→`usiok`→`isready`→`readyok`→`position`→`go`→`bestmove`)
- AI側(居飛車)の序盤を一定の手順で強制進行させる仕組みの最小実装(定跡を「大量に」用意する必要はなく、四間飛車vs居飛車が成立する最小限の手順で良い)
- Node.js 環境構築(`package.json` 作成、`scripts/validate-data.mjs` を実行できる状態にする)

**完了条件**:
- ブラウザで盤面が表示され、人間が四間飛車側を指し、AIが居飛車らしい手を返してくる対局が最後まで成立する
- `scripts/validate-data.mjs` が実行でき、`data/examples/` の全ファイルが検証を通る

**触ってよい主なディレクトリ**: `apps/`, `scripts/`, ルートの `package.json`

## Phase 1 ― 観察コーチ

**目的**: パイプラインの②〜④・⑨(現在の形・相手の意図・相手の次の狙い・初心者向け説明)を実装し、対局しながら「今何が起きているか」が見えるようにする。ユーザーはまだ目標形を選べない(システムが候補を提示するのみ)。

**成果物**:
- `data/shapes/` に美濃系の形を3種類程度(本美濃・高美濃・銀冠など)
- `data/openings/` に四間飛車・居飛車のエントリ
- `data/intents/` に居飛車側の代表的な狙いを3〜4種類(棒銀・斜め棒銀・早仕掛けなど)
- 形判定ロジック・意図推定ロジック(定跡照合を第一手段、汎用ヒューリスティックをフォールバックとする設計。詳細は実装時に別途設計メモを作る)
- 「目的→手→理由」テンプレートによる説明生成(⑨)
- 用語集とツールチップ

**完了条件**:
- 四間飛車vs居飛車の対局を最初から最後まで行い、現在の形・相手の意図・相手の次の狙いが、専門用語の説明つきで画面に表示される
- 定跡データが持つ範囲の局面で、明らかに誤った意図表示が出ないことを人間が確認する
- 定跡から外れた局面でも、アプリが無言・エラーにならず「未分類」等の穏当な表示に落ちる

**触ってよい主なディレクトリ**: `apps/server/src/analysis`, `apps/web`, `data/shapes/`, `data/openings/`, `data/intents/`

**注意**: このPhaseで初めて本番データを作り始める。[../CLAUDE.md](../CLAUDE.md) のルール4番(大量生成禁止)を守り、数件ずつ人間レビューを挟むこと。

## Phase 2 ― 経路コーチ

**目的**: パイプラインの⑤〜⑧(自分の目的・目指せる形・候補手・その手の目的)を実装し、ユーザーが目標形を選び、そこまでの道筋(候補手の並び)を見られるようにする。

**成果物**:
- 目指せる形のランキングロジック(shape graphを使ったスコアリング)
- 経路プランナー(path planner): 現在局面と目標形から、次に指すべき手の候補を算出
- 候補手とエンジンのMultiPV結果を突き合わせ、安全確認(悪手排除)を行うロジック
- ユーザーが2〜3個の候補から目標形を選べるUI

**完了条件**:
- ユーザーが目標形を選ぶと、次の一手候補が「目的→手→理由」つきで表示される
- 表示される候補手が、エンジンの評価値で見て明らかな悪手でないことを人間が複数局面で確認する

**触ってよい主なディレクトリ**: `apps/server/src/analysis`, `apps/web`

## Phase 3 ― 適応コーチ

**目的**: パイプラインの⑤〜⑧を、相手の指し手に応じて動的に再計算できるようにする(道筋の変更とその理由の説明)。

**成果物**:
- 計画済みの道筋が相手の手によって崩れたことを検知するロジック
- 再計画と、「なぜ計画が変わったか」の説明生成

**完了条件**:
- 相手が候補手の前提を崩す手を指したとき、道筋が変わり、その理由が説明として表示される
- 極端なケース(相手が大駒を取りに来る等)でも、安全確認(Phase2の仕組み)が機能し続ける

**触ってよい主なディレクトリ**: `apps/server/src/analysis`

## Phase 4 ― 定跡外への耐性強化・対局シナリオ着手検討

**目的**: 定跡ツリーの外に出た局面でも実用的な説明が出るよう、汎用ヒューリスティックを強化する。[SCENARIOS.md](SCENARIOS.md) の対局シナリオ実装に着手するかどうかをここで判断する。

**完了条件**: Phase1〜3で溜まった「よく外れるパターン」への対応が一通り入っている。

**対局シナリオ本実装の判断(記録)**: [SCENARIOS.md](SCENARIOS.md)が想定する本格的な対局シナリオ機能(AI序盤制御)の着手について、本Phaseの完了時点では「見送り・別途仕様確定後に改めて検討する」と判断した。`apps/server/src/engine/scenarioOpponentOpening.ts` はIntent判定の検証用実装にとどまり、この判断を変更するものではない。`data/openings/*.json` の `scenario` フィールドは引き続き `null` のまま維持する。

## Phase 5 ― 仕上げ

**目的**: 通しプレイによる表現・タイミング・UIの調整に限定する(新しい将棋知識・新しいロジックは扱わない)。

**成果物**:
- 通しプレイ(5局程度)で見つかったUI・文言・表示タイミングの問題の修正
- 既存ロジックの軽微な不具合修正(判定結果そのものを変えるような修正は含まない)

**完了条件**:
人間が5局程度を実際に通しプレイし、以下をすべて確認する。
- 対局操作に破綻がない
- UI表示に破綻がない
- 説明の表示タイミングに大きな違和感がない
- 説明文が初心者にも理解できる
- 「目的→手→理由」の流れが自然である
- forced opening時の説明が不自然でない
- intentが判定できない局面で無理な断定をしていない
- 対局状態と説明内容に不整合がない

**Phase 5で修正してよい範囲**(通しプレイで発見された問題に限る):
- UI上の問題
- 表現・文言の問題
- 説明表示タイミングの問題
- 既存ロジック上の軽微な不具合

**Phase 5で追加・変更しないもの**:
- 新しい将棋知識(shapes/openings/intentsの新規追加)
- 新しい戦法・形・intentデータ
- 新しいヒューリスティック
- 新しい重み・閾値
- LLMによる将棋事実の判断
- 既存の判定ロジックを覆す新規推測ロジック
- 対局シナリオ本実装(`scenarioOpponentOpening.ts`の本番機能化を含む。[SCENARIOS.md](SCENARIOS.md)参照)

**触ってよい主なディレクトリ**: `apps/web/`, `apps/server/src/analysis/`(既存ロジックの軽微な不具合修正のみ), 既存の `data/shapes|openings|intents` 内の文言フィールド(`characteristics`等の言い回し修正のみ、新規追加は不可)

**注意**: Phase 5の完了判定は人間が行う。「体験として破綻がない」ことをAIエージェントが独自に判定してPhase完了扱いにしない([ROLES.md](ROLES.md))。

**実対局確認で判明した設計上の限界(記録)**: Phase 5の通しプレイ確認の過程で、「目指せる形」から「この形へ近づく手の候補」(⑦候補手)を生成する `apps/server/src/analysis/pathPlanner.ts` が**単一手先読みのみ**(`typical_build_order` 上の次の1マスへ、現局面から1手で直接到達できる合法手しか候補にできない)であり、複数手先の経路計画を行っていないことを確認した(実対局での`candidateMoveState: "unavailable"`の再現、および`pathPlanner.ts`のコード上のコメントで確認済み)。現在の3形(本美濃・高美濃・銀冠)はいずれも `typical_build_order` の先頭が `8h`(玉)であり、玉が初期位置からそこへ到達するまでの間、候補手が出せない局面が非常に多い。

Phase 5では新しい将棋知識・判定ロジックを追加しないという制約により、本Phaseでは対応しない。**shapeを追加するだけでは解決せず、pathPlanner自体の仕様再設計(複数手先の経路計画への対応)が必要**になる見込み。現在のshapeは本美濃・高美濃・銀冠の3種類のみで、これ以外のshapeを追加する計画は現時点で存在しない(スコープ変更には[../CLAUDE.md](../CLAUDE.md)の「現在のスコープ」に対する人間の承認が必要)。

この限界への対応は Phase 6(下記)で行う。

## Phase 6 ― 経路コーチ / 毎手説明

**目的**: 次の3つを統合し、「選んだ形に近づくために、今この局面で何を指せばよいか」が対局中つねに分かる状態にする。

- 選択したshapeに近づくための**経路計画**(複数手先の道のり)
- その経路の、**現在局面における最初の一手**の提示
- **毎手説明**(1手ごとに何が起きたか・次に何を考えるべきか)

**背景**: Phase 5の記録(上記)のとおり、`pathPlanner.ts` が単一目標マス・1手先読みに限定されているため、3形すべてで序盤に候補手が出せなかった。Phase 6ではこの制約を解消する新しい経路探索ロジックを正式に導入する(Phase 5では禁止されていた作業)。

**Unit構成**:

- **Unit 1(実装済み)**: 経路計画と候補手生成の基盤。
  - `apps/server/src/analysis/routePlanner.ts` を新設(複数の未達成マスを同時に扱い、各マスへの複数手の経路と、その経路の「現在局面で指せる最初の一手」を求める)。エンジン非依存・決定的な純粋ロジックで、将棋のルール判定はshogiopsと既存の `rules/` に委ねる。
  - 既存の `pathPlanner.ts` は削除も変更もせず温存する(本番の候補生成経路からは使わなくなった)。
  - 目標マスを自駒が塞ぐ場合の**準備手**を扱う。ただし「どこへ退避させるのが良いか」という将棋的な評価は導入せず、合法手を機械的に列挙するに留める。
  - 既に形の一部として成立しているマスの駒は動かさない(形を壊す候補手を作らない)。同じ駒を複数の目標マスへ二重に割り当てない。
  - `notation/japaneseSquare.ts` を新設し、説明・UI表示のマス目を日本語表記(`8h`→`８八`)に変換する([DATA_MODEL.md](DATA_MODEL.md) の座標表記の規約に従い、内部データはUSI形式のまま)。
  - UIは「選択した形 → 必要なマス → 今どこまで出来ているか → 未達成部分の道のり → その最初の一手 → 候補手」という因果を表示する。
- **Unit 2(実装済み)**: 毎手説明(1手ごとの事実抽出と説明生成)。
  - `apps/server/src/analysis/moveOutcomeDetector.ts` を新設。ユーザー着手直前と、相手の応手まで終えた現在の局面について、Unit 1 の経路計画と形判定の結果を突き合わせ、**直前の一手で何が変わったか**を機械的な事実として列挙する(経路が進んだ/完成した/続けられなくなった、準備手が必要になった/不要になった、目標形が変わった等)。エンジンにもLLMにも依存しない決定的な純粋関数。
  - `apps/server/src/analysis/moveOutcomeExplanation.ts` を新設。事実 → 初心者向けの文言への対応表。評価語(最善・おすすめ・安全・悪手・形勢)は一切使わない。
  - **原因の帰属は3ルールに限定する**: (1) ユーザーの着手そのものから直接確認できる変化、(2) 既存の `planChangeReason.ts` が確定分類した理由、(3) それ以外は原因を断定せず変化した事実だけを述べる。推測による原因説明はしない。
  - 目標形が変わった手では、形・経路の差分を一切出さない(形ごとに必須マスの定義が違うため、比較すると誤った「崩れた」等の説明になる)。目標形の変更直後は `lastMoveOutcome` を null にリセットする。
  - `planChangeDetector.ts` / `planChangeReason.ts` の判定条件は変更していない(結果を受け取って使うだけ)。
  - UIは既存の「形 → 未達成マス → 経路 → 残り手数 → 候補手」を変更せず、その上に「直前の一手」ブロックを追加する。

**Phase 6でも変えないこと**:
- shapeデータ(本美濃・高美濃・銀冠)の座標・内容。現在の3形の座標を仕様として扱う
- 新しいshape/opening/intentの追加
- エンジンの最善手を「形に近づく手」として提示すること(エンジン評価は従来どおり参考評価に限る)
- エンジン評価値に対する新しい閾値の導入

**完了条件(Unit 1)**:
- 3形(本美濃・高美濃・銀冠)のいずれを選んでも、初期局面から候補手が提示される
- 提示された候補手について、「どの形の、どのマスへ向かう、何手の道のりの一手か」を画面から追跡できる
- 候補手が「将棋として良いから表示されている」と誤解させる表現がない

**触ってよい主なディレクトリ**: `apps/server/src/analysis/`, `apps/server/src/notation/`, `apps/server/src/api/`, `apps/web/`
