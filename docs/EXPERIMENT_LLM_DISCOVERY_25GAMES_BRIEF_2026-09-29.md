# 実験の指示書 ― 25 局 LLM 独立分析実験(2026-09-29・人間の指示。司令塔が付記)

**セッション名**: 将棋コーチ｜25局LLM独立分析実験
**位置づけ**: 本番の納品レーン(5 人目まで・`deliver.ts` の 4 段・批評の輪)は**変更しない**。それとは別に、独立した比較実験として行う。記録は `docs/COMMAND_STRUCTURE.md` に「実験席」として足す(権限は動かない)。
**人間の本文は §1〜§8 にそのまま置く。§9 以降が司令塔の付記(材料の在り処・保存の仕方・守る規則)。**

---

## 1. 目的(人間)

現在の 25 局分析について、既存の「承認済み条件 → 行動」ルートとは別に、エンジンが生成した 25 局分の数値・観測結果をそのまま材料として、**LLM がゼロベースで何を発見できるかを検証する**。これは本番レポートの設計変更ではない。第 5 人目までの現行納品レーンを壊さず、独立した比較実験として実施する。

## 2. 重要原則(人間)

1. エンジンが出した数値・観測を LLM 側で再集計しない。
2. LLM に数値を「修正」「補完」「推定」させない。
3. エンジンの第 1 候補を「正解」と表現しない。
4. 「実戦が第 1 候補と違った」ことから、直ちに「見落とした」「苦手」「知らない」などの診断をしてはいけない。
5. 心理状態・意図・知識の有無を推測しない。
6. 「今回の 25 局で観測された事実」と「LLM が立てた仮説」を明確に分離する。
7. 顧客の自己申告がないものについて、「本人が気にしている」と仮定しない。
8. 顧客に試せる行動を提案する場合、その行動がどの観測・仮説から導かれたかを明示する。
9. 行動を無理に作らない。
10. 「差がなかった」「判断材料が足りない」も正式な分析結果として扱う。

## 3. 入力(人間)

25 局について、既にエンジン・決定論的集計によって生成済みの数値・観測データを使用する。入力には可能な限り以下を含める: 対局 ID / 勝敗 / 手数 / 各局面の評価値 / 分かれ道の定義と件数 / 実戦手とエンジン候補の関係 / 第 1 候補〜第 5 候補までの情報 / 攻め候補・自玉側候補の分類 / 駒打ち・駒取り・チェック・犠牲・退避等の候補属性 / 長考時間 / 長考後の次の手 / 崩れとの対応 / その他、既に機械的に算出済みの数値。
**入力された数値は「観測事実」として固定する。LLM は数え直さない。**

## 4. LLM にやらせること(人間)

25 局全体を横断して、以下を独立に分析する。

**A. 顧客にとって意味がありそうなパターン** ― どの数値・組み合わせが特徴的か / 勝ち局と負け局で何が違うか / 分かれ道の前後で何が起きているか / 複数の指標が同じ現象を示しているか / 逆に、数字は目立つが顧客への意味が薄そうなものは何か。
**B. 仮説** ― 各仮説について必ず: 仮説 / 根拠となる観測 / 反証になり得る観測 / 現時点で不足している証拠 / 次の 25 局で検証するなら何を測るか。
**C. 顧客の「どうしたら」に繋がる可能性** ― 各仮説を「行動にできる」「行動にできそうだが証拠不足」「行動にするべきではない」のいずれかに分類。「行動にできる」とした場合は、具体的な行動を 1 文で提示し、その直前に必ず「なぜこの行動なのか」を観測ベースで説明する。
**D. 現行ルートとの比較材料** ― 現在使っている「承認済み条件 → 行動」からは出ていないが、この 25 局の数字から新しく浮上した仮説を抽出する。ただし「新しい = 正しい」とは扱わない。

## 5. 禁止事項(人間)

「この人は○○が苦手」「○○を見落としている」「○○を考えていない」「○○を知らない」「居玉だから負ける」「戦型が苦手」「時間の使い方が悪い」など、観測から直接確認できない診断。
「第 1 候補を指さなかった」= 「第 1 候補を見えていなかった」とは解釈しない。「駒を打つ候補を指さなかった」= 「駒を打つ手を思いつかなかった」とも解釈しない。

## 6. 特に確認すること(人間)

今回の顧客には「普段指さない戦型の局が影響しているのではないか」という自己申告上の関心がある。**この実験ではその自己申告を根拠に結論を作らない。** 戦型について機械的に認識可能なデータが別途存在する場合は、それを使って戦型別の分布・勝敗・分かれ道・エンジン候補との乖離・時間・崩れに差があるかを見る。差が確認できなければ「今回の 25 局では戦型による明確な差は確認できなかった」という結果も残す。

## 7. 出力形式(人間)

1. 25 局から読み取れる重要な観測 / 2. LLM が立てた仮説一覧 / 3. 各仮説の根拠 / 4. 各仮説への反証・弱点 / 5. 顧客向け行動にできる候補 / 6. 行動にしない方がよい候補 / 7. 戦型に関する分析 / 8. 現行の承認済み条件 → 行動ルートでは拾えていない新規仮説 / 9. 次の 25 局で検証するための指標 / 10. 「今回のデータだけでは判断できないこと」。
**この出力はまだ顧客向け文章ではない。「発見レイヤー」として保存する。** その後、決定論的な検証が可能な仮説だけを機械検証に回し、検証を通過したものだけを「採用候補」とする。LLM の 3 席が同じ仮説を出した場合も、それ自体を証拠とはしない。3 席一致は「再検証する価値がある仮説」として扱う。

## 8. 比較実験(人間)

可能なら同じ入力データを GPT / ChatGPT / Gemini の独立した文脈ゼロの席に渡す。各席には他の LLM の結果を見せない。比較する項目: 共通して出た仮説 / 1 席だけが出した仮説 / 顧客の自己申告に関係する仮説 / 現行ルートでは拾えていない仮説 / 後から機械検証できた仮説 / 検証によって棄却された仮説。
最終目的は「LLM に正解を出させる」ことではない。現在の固定された分析ルートだけでは拾えない「顧客固有の可能性」を LLM が発見できるかを測定することである。現行の本番レーンは変更せず、この実験結果を後で比較する。

## 10. 席と手順(司令塔の付記)

1. 実験席(この指示書を読むセッション)が §9 の束を作り、sha256 と抽出の記録(どのファイルのどの鍵から)を `docs/EXPERIMENT_LLM_DISCOVERY_25GAMES_LOG.md` に書く(束そのものは `out/` に置きコミットしない)。
2. 依頼文は §1〜§7 の本文 + 束。**3 席に同じ文**。(a) Claude の文脈ゼロの席(実験席が subagent で起こす。会話は新規)、(b) GPT/ChatGPT、(c) Gemini((b)(c) は人間がブラウザで掛ける。**会話を新規に**。将来は API)。各席には他の席の結果を見せない。
3. 回答は**原文のまま** `docs/EXPERIMENT_LLM_DISCOVERY_25GAMES_SEAT_{A,B,C}.md` に保存(語を変えない)。
4. 比較(§8 の 6 項目)は実験席が表にする。**「現行ルートで拾えていない」は、`answer_menu.json`(M1〜M9)と 2 周目の本編の行動・観測と突き合わせて決める。**
5. 機械検証に回せる仮説は `scripts/playtest/schemas/hypothesis.v0.3.schema.json` の契約に載せる(CLAUDE.md 8 番 (1): 引いた数が観測項目に実在すること・反証が試みられたこと・次の 25 局で動くはずの数が測る前に書かれていること)。載せられない仮説は「載せられない理由」を書いて残す。
6. 結果は司令塔(セッション「指示システムの整理」)へ SendMessage で報告。採否は司令塔の承認系統(AI の批評・発見 = 採用ではない)。

## 11. 守る規則(司令塔の付記)

- CLAUDE.md 8 番: 内部の工程では LLM は仮説生成器・批判者・整理者。**手の目的を列挙しない**(幾何の事実の組み合わせまで)。形・戦法・狙いの名前は `data/` の認識を経たものだけ ― 今回の戦型は**すべて draft** なので、席の出力に戦型名が出ても**実験の記録の中に留め、顧客の文には出さない**。複数の LLM の一致を証拠に数えない。
- 本番のレーン(`deliver.ts`・`report-pdf/`・`out/c5/deliver1/` の冊子と封)には**触らない**。共有ツリーの原本を動かさない(`docs/AGENT_PROTOCOL.md` 共有ツリーでの後片付け)。
- 顧客に試せる行動は、承認済みの表(`answer_menu.json`)の外のものでも**実験の記録には書いてよい**(それがこの実験の目的)。ただし顧客に出すには人間の承認を経て表に入る経路が要る(Phase 2 ①)。
- 「数え直さない」: 席が数を作った場合(束に無い数)、その数は**束に無い**と印を付けて残し、採用候補にしない。
- 期限は置かない。止まったら「止まった」と 1 行、司令塔へ。

## 12. この実験が答える問い(司令塔の付記)

人間の言葉: 「現在の固定された分析ルートだけでは拾えない『顧客固有の可能性』を LLM が発見できるか」。測るのは §8 の 6 項目の数。**採用に直結しない**。2 周目までの本番の輪(観測 → 根拠 → 行動)と並べ、Phase 2 ①④ の設計の入力にする。
