## 1. 探りの設計(封じる。率の意味を後から動かさないため)

### 1.1 材料は会社自身の文章(AI の出力ではない)

1 本目は **会社が書いた MD&A の文章**(textBlock `jpcrp_cor:ManagementAnalysisOfFinancialPositionOperatingResultsAndCashFlowsTextBlock`。実名は探りで確かめる)を主張の材料にし、同じ書類の XBRL の数へ束縛する。**LLM の要約は使わない**(抽出器の出来と Core の束縛の力を分けて測るため)。2 本目で同じ書類を LLM に要約させ、1 本目との差を「AI が落とした修飾」として測る(2 本目の予測は別に封じる)。

### 1.2 Claim の数え方(封じる)

| 種類 | 定義 | 抜き方 |
|---|---|---|
| **数の Claim** | 文の中の、金額・%・件数・倍率・差額のうち、主語(何の数か)が同じ文か直前の文から機械で決まるもの。1 つの数 = 1 件 | **正規表現で機械が抜く**(LLM を使わない) |
| **文章の Claim** | 数を含まない、方向か状態の主張(「増収」「減益」「堅調」「厳しい」「改善」)。1 つの述語 = 1 件 | 人が抜く(規則: 方向の語・状態の語の一覧を探りの前に書く) |
| **数えない** | 日付・期の呼び名(第 2 四半期・当連結会計年度)・注番号・条項番号・ページ・表の見出しの数・単位だけの語(百万円) | 除外の一覧を探りの前に固定 |

### 1.3 束縛と検証の定義

| 指標 | 分子 / 分母 |
|---|---|
| 数の束縛率 | Evidence Pointer(`xbrl:要素名@contextRef`、派生なら 2 つ以上の pointer + 式)を付けられた数の Claim / 数の Claim |
| 文章の束縛率 | pointer を付けられた文章の Claim / 文章の Claim。「増収」は `NetSales@Current − NetSales@Prior1 > 0`(構造上の 0 との比較。Q-1 で承認不要)として束縛できる。「堅調」は線が無いので束縛できない |
| 再計算一致率 | 束縛できた数の Claim のうち再計算できるもの(% と差額と合計)で、fact から再計算した値が文の値と **`decimals` を既定の許容幅**として一致した件数 / 再計算の対象 |
| 直接一致率(参考) | 束縛できた数の Claim のうち fact の値そのもの(scale を解決)と一致した件数 / その対象 |

束縛率は「正しいか」ではなく「証拠へ結び付けられたか」。一致率の分母は束縛できたもの(分母の出どころを書く。一致率を束縛率と並べて比べない)。

### 1.4 材料の選び方(封じる。手で選ばない)

**規則**: 鍵を得た日の **直前の平日**に提出された有価証券報告書(docTypeCode 120)のうち、**連結財務諸表があり(`jppfs` の連結の fact がある)、XBRL(type=1)が取得でき、docID が辞書順で最小のもの** 1 件。業種・規模で選ばない。該当が 0 件ならさらに 1 平日さかのぼる。

### 1.5 探りの出力(1 本のファイルで持つ)

探りは 1 本の JSON を出す: 書類の id・提出日・会社名(顧客向けの出力ではないので可)、Claim の一覧(種類・原文の区間・pointer・form・結果・一致/不一致・不一致の理由)、§2 の数の実測、Core 変更の分類。**完走した 1 本で証跡を持つ**(落ちた run に手回しを足して書かない)。

## 2. 封じる数

| 指標 | 予測レンジ | 根拠 |
|---|---|---|
| **数の束縛率** | **50〜70%** | MD&A の数には XBRL に要素が無いものが多い(店舗数・受注高・販売数量・為替レート・設備投資の内訳・人員の増減)。% は 2 つの fact と式で結ぶ派生なので束縛できるが、分母が百万円と千円で違う |
| **文章の束縛率** | **25〜45%** | 「増収」「減益」「増加」「減少」は前期との差の符号で束縛できる。「堅調」「底堅い」「厳しい」「改善傾向」は線が無い。方向の語の混ざり方で決まる |
| **再計算一致率** | **80〜95%** | `decimals` を既定の許容幅にすれば大半は通る。外れるのは、会社が千円単位で計算した % を百万円の fact から再計算した場合・連結と個別の取り違え・損失の符号・「前年同期比」と「前期比」の取り違え |
| 直接一致率(参考) | 90〜100% | fact の値そのものは scale を解決すれば一致するはず |
| 数の Claim 件数 | **40〜120** | 中堅の有報 1 件の MD&A。会社の規模で倍は動く |
| 文章の Claim 件数 | **20〜60** | |
| 再計算の対象 | **10〜40** | % と前期比の差額 |
| 形の分布(数の Claim) | direct 50〜65% / derived 25〜40% / threshold 5〜15% / aggregate 10% 未満 | aggregate はセグメントの合計くらい |
| scheme の種類 | **`xbrl:` と `filing:` の 2 つだけ** | 他が要ったら設計が将棋に寄っている |
| 層の数 | **4 のまま** | 追加の層が要ったら v0.2 は「将棋の門の整理」 |
| XBRL 固有の追加要素 | **登録の追加だけ**(鍵の約束 1: contextRef の正規化 / 正規化の規則 4: scale・format・unitRef・符号 / tolerance の既定 1: decimals) | インターフェース拡張 0・意味変更 0 |
| 束縛できない理由の最多 | **「要素が無い」が半分以上** | 2 位は「主語が機械で決まらない」 |
| 不一致の理由の最多 | 桁(千円 / 百万円)の取り違え | |

## 3. 外れたときの読み方

- 数の束縛率が 70% を超えたら、MD&A が思ったより財務諸表の数しか書いていない(会社の選び方の偏り)か、数えない規則が緩い。
- 50% を下回ったら、`xbrl:` の locator の設計(要素名 + contextRef)が足りない。契約を直す前に、束縛できなかった理由の札を全部読む。
- 再計算一致率が 80% を下回ったら、許容幅の既定(`decimals`)が足りない。人が承認する丸めの幅を文章側に足す(X-1)。
- 層が 5 つになったら、XBRL 固有の概念が Core に入ろうとしている。入れずに記録する。
