## 0. 人間の決定(2026-09-25)

   - **2b. 目録を 5〜10 件ずつ埋める。** 順は 囲い(全部)→ 戦法(全部)→ 狙い。**順の見直し(2026-09-25 夕、司令塔。知識レーンの測った事実 3 つによる)**: 形は 35 件で沈黙が下げ止まり(増えるのは証拠なしの主張だけ)、戦型は認識のコードが無く測れない、相手側の形は効いた(0 → 365 局面)。狙い(`data/intents`)は `intentDetector` が読むので測れ、狙いだけの沈黙が 30 手までで 279 / 1096 ある。したがって **戦法 47 / 184 で一度区切り、狙い → 相手側の形 → 戦法の残り** の順にする。網羅の目標は変えない(戦法の残りは目録に「未(出典あり)」で残し、狙いと相手側の形が尽きたら戻る)。狙いの測り方: 形と同じく **証拠 1 件で立つ forming と、証拠 2 件以上か matched** を分けて前後を出す(狙い 3 件が相手の 1 手で立つ事実があるため)。1 まとまりごとに §2 の「増やしたら必ず測る」。

## 2. 守る決まり

- **スキーマ準拠**: `data/schemas/*.schema.json`。作成は skill `shape-authoring`・`new-shape`、点検は `schema-consistency-check`。[DATA_MODEL.md](DATA_MODEL.md) の記述的知識(Kind 1)の範囲だけ。**スキーマの形式を変えない**(構造的 = 人間承認)。
- **すべて `review_status: draft`**。`human_reviewed` に上げるのは司令塔の F′(CLAUDE.md 承認の委任)。`expert_verified` にはしない。**未レビューの名前は断定的に見せない** ― 露出制御はコードの側にあり、このレーンは触らない。
- **出典を `source` に書く。** 一次資料(書籍・公開解説)の名前とページ/URL。座標の一次資料確認は保留中のまま(ROLES.md)なので、**「確認していない」と書く**。
- **増やしたら必ず測る**(CLAUDE.md、2026-09-12 の読み替え)。足したまとまりごとに、固定棋譜(`scripts/playtest/kifu/`)と 4 人分の棋譜で認識を回し、**沈黙率**(認識が空の局面の割合)と**誤認**(`forming/completed` が盤面と食い違う件数)を記録する。**測らずに増やさない。** 測り方は開発・診断レーンに聞く(エンジンが要る測定はエンジン 5 本の枠。要らない測定は自由)。
- **相手 AI 制御(Kind 3)には触れない**(`scenario`・`BOH_GIN_SCRIPT` 等は開発・検証専用)。
- `data/` には**新規ファイルの追加だけ**。既存レコードの変更は司令塔へ案を出す。コミットはパス指定(`git add -N` → `git commit -F - -- <paths>`)。**`git stash`・`git add` を使わない。**
- **記録は自分のファイル** `docs/LANE_KNOWLEDGE_LOG_2026-09.md`(1 ファイル 1 席)。何を足したか・出典・測った数・認識できなかった場面の一覧。README に 1 行。

## 3. 報告と横の連絡

- 報告先: 司令塔。まとまり(例: 5〜10 件)ごとに「足した ID・出典・沈黙率と誤認の前後」を 3 行で。
- 横: **開発・診断レーン**へ「語彙の列(`obs.vocab.shapeStatus/openingStatus/intentStatus`)にどの ID が使えるか」を伝える。設計案 §10.4 のとおり 1 周目は語彙に依存しないので、**向こうを待たせない・向こうに待たされない**。
- 認識のコード(`apps/server/src/analysis/`)に手を入れたくなったら止めて司令塔へ(開発・診断レーンの持ち物)。

## 5. 最初の 1 まとまり(着手の形)

1. 4 人分の棋譜で、今の 3 形 + 8 狙いの認識を回し、**認識できなかった局面の一覧**を作る(数える範囲を先に書く: どのツリー・どのフォルダ)。**訂正(2026-09-25、司令塔)**: 戦型(`data/openings` 3 件)を認識するコードは `apps/server/src/analysis/` に無い(`opening_id` は狙いに付く欄で、絞り込みにも使われていない)。したがって戦型を足しても沈黙率は動かない。戦型の下書きは足してよいが、報告に「**測れない(認識のコードが無い)**」と明記する。**本人が後手の局は、納品の道具と同じ `lib/sideAlignment.ts` の回し方(180 度回して本人の手を先手の手にそろえる)を通してから数える**(そろえずに先手番の局面を数えると相手の陣形を数えることになる)。沈黙率は **形だけ・狙いだけ・どちらか** の 3 つを分けて出す(狙いは相手の 1 手で forming になるものが 3 件あり、合わせた数では形の沈黙が見えない)。
2. その一覧から、最も多く現れた**形 3 件・戦型 2 件**を draft で足す(出典つき)。
3. 同じ棋譜でもう一度回し、沈黙率と誤認の**前後**を記録。
4. 司令塔へ 3 行で報告。

**置き場の決定(2026-09-25、司令塔。知識レーンの報告に対して)**: `data/shapes|openings|intents/` に足すと本体(`apps/server/src/analysis/*Repository.ts`)が読み、対局中の「目指せる形」上位 3 件から銀冠が押し出される(挙動の変更。`stateResponse.ts` の上限 3、2026-09-12 U6-A §9.4 に記録済み)うえ、実データを読む vitest が 5 本落ちる。したがって知識レーンの下書きは **`data/drafts/<日付>-knowledge/{shapes,openings,intents}/`** に置いてコミットする(最終の置き場と同じ階層にして、移すときは `git mv` だけで済むように)。本体はこのフォルダを読まない。測定は、知識レーンが渡す shapes/intents の集合を明示して回すので、置き場に依存しない(「本体に入れたらどうなるか」の測定であって、本体の今の挙動ではない、と報告に書く)。`data/drafts/` は `validate:data` の対象外なので、スキーマ検証は知識レーンが自分で回して件数を報告する。**本体へ移すときの門(2026-09-25 知識レーンの実測)**: `data/openings` は認識には使われないが、相手 AI 制御(Kind 3)の口 `apps/server/src/engine/scenarioRepository.ts` が全 JSON を読み、形式が合わないと例外を投げる。移す前に同じ呼び出しで例外なしを確かめる。相手側の陣形(`side: opponent` の shapes)は `shapeDetector.ts` が後手視点で読むので囲いと同じ方法で測れる(分母は相手玉の局面、自分側と分けて出す)。**`data/shapes|openings|intents/` へ移すのは司令塔の判断**(上限 3 件と試験の実データ依存を開発・診断レーンがどう扱うかを見てから。1 周目は語彙の列を使わないので急がない)。
