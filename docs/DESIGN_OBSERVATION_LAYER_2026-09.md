## 0. この文書が決めること・決めないこと

**決めること(設計思想)**
- 対局後診断の出力を「観測 → 仮説 → 反証 → 統合 → 予測 → 照合」の 1 本の流れに置き直し、**どこまでが機械の事実で、どこからが仮説か**の線を最初から引く(人間の決定 1・2・3)。
- LLM は判定者ではなく **仮説生成器・批判者・整理者**。「複数の LLM が一致した」を証拠に数えない(決定 3)。
- 仮説は **機械で検査できる契約(JSON スキーマ)** に載せる。数の実在・反証の有無・数の予測の 3 つを、人が読む前に機械が落とす(Failure Event と同じ流儀)。
- 観測レイヤーと知識レイヤーを分け、知識は 3 種類 × 3 分類で蓄積する(決定 6)。

**決めないこと(人間が決める。§13 に一覧)**
- 規則 8(内部工程の規則、§4.2 の案)を正本に書く文(最重要コンセプトに触る)。別の規則として立てることは決定済み(決-A、2026-09-25)。
- 失効(降格)の状態を `review_status` に足すこと(スキーマ変更 = 構造的知識 = 人間承認)。
- 語彙(形・戦型)を**増やす作業はこの文書の外**: 知識レーンが並行して集める(決-G、2026-09-25 決定済み)。この文書は語彙の ID を**受け取る側**の規則だけを書く(§3)。
- 同意文 5 番(匿名の統計)を任意にするか必須にするか。
- 実装の GO(この文書の外)。

**用語**(この文書の中だけ。正本にする言葉ではない)
- **観測項目(obs)**: 道具が棋譜とエンジンの出力から機械的に作る値。ID を `obs.<列>.<名前>` で振る(§1・§2)。
- **仮説(H)**: 観測項目の組に対する、断定しない形の説明。契約 §7 に載ったものだけを仮説と呼ぶ。
- **レーン**: 1 つの視点から仮説を出す LLM の役割(§3)。**反証レーン**は仮説と事実だけを受け取る盲検の役割(§5)。
- **1 周**: 観測 → レーン(1 本以上)+ 反証 → 統合 → 予測 → (次の 20 局で)照合、の 1 回(§10)。

## 3. 観測項目がどの LLM レーンに供給されるか

**レーンの数は最小から。** 全レーンを作る前に §10 の 1 周を回す。ここに書くのは供給の規則で、レーンの本数は人間が増減する。

| レーン | 役割 | 受け取る観測 | 受け取らないもの | 出す物 |
|---|---|---|---|---|
| **L-時間** | 時間の消費と分かれ道・崩れの関係から仮説を出す | `obs.time.*`・`obs.timeSearch.*`・`obs.eval.*`・`obs.fork.*`(数だけ)・`obs.time.decisionContext` | 本人の言葉(ヒアリング)、他レーンの仮説、盤面の画像 | 仮説 H(契約 §7) |
| **L-側** | 攻め/自玉側の選び方の仮説 | `obs.side.*`・`obs.fork.*`・`obs.geo.attackers/defenders`・`obs.geo.moveFacts` | 同上 | H |
| **L-形**(語彙の列が育ってから) | 形・狙いの認識と崩れの関係 | `obs.vocab.*`・`obs.geo.king*`・`obs.fe.*` | 同上 | H |
| **反証** | 各 H の反例・分母・別の説明を探す(**盲検**、§5) | **その H が引いた観測 + 同じ顧客の全観測(数)**。H の文 | **他レーンの推論・統合の途中経過・本人の言葉** | 反証の記録(契約 §7 の `counterEvidence`) |
| **統合** | H ごとに支持/反証/未確認を整理し「今どこまで言えるか」を決める(§6) | 全 H + 全反証 + 観測の一覧 | 一致の数を証拠にする権限 | 仮説台帳の状態更新 |
| **言い換え**(既存 = B の書き手) | 統合の結果を冊子の文にする。**規則 5 の現行の範囲** | 統合の出力 + `check_answer.py` の材料 | 新しい数・新しい手を作る権限 | B の md(検査 1〜7 を通る) |
| **事前仮説**(ヒアリングがあるときだけ) | 本人の言葉を Y-1〜Y-6 の形(言葉 → 確かめられる数 → 予測)に写す | 本人の言葉 | 道具の数(**封をする**。4 人目の運用と同じ) | 照合項目の表(`02-突き合わせ` の形) |

**供給の規則**
1. どのレーンも、**観測項目の ID と値の対**で受け取る。文章化された事実(B の文)は渡さない(F-1 の型: 数は実在するが主張が支えられていない、が上流に混ざる)。
2. 反証レーンには、**仮説 1 本と観測だけ**。他レーンの推論・統合の途中経過は見せない(決定 3・司令塔 B)。
3. ヒアリングは事前仮説レーンにだけ入る(決定 4)。**ヒアリングが無くても L-時間・L-側は同じ入力で回る。**
4. 語彙の列(`obs.vocab.*`)を受け取るレーンは、その `review_status` を一緒に受け取り、`draft` の名前を文に出さない(検査 6 と同じ線)。
5. **語彙の列の ID の出どころは知識レーン**(`data/shapes|openings|intents/*.json` の `id`。決-G、2026-09-25)。知識レーンが足した ID は、**認識のコード(`apps/server/src/analysis/`、開発・診断レーンの持ち物)が読める形になった時点で** `obs.vocab.shapeStatus/openingStatus/intentStatus` の値域に入る。この経路は L-形が立つ前から開いている(ID が増えても、1 周目のレーンの入力は変わらない)。ID の追加は記述的知識(Kind 1)、認識のコードの変更は開発・診断レーン、`human_reviewed` への昇格は司令塔(承認の委任)。

## 5. 反証レーンの独立性(盲検)

**すでにある運用に名前を付ける**: 4 人目で使った「封」(`out/<4 人目>/00-本人の言葉` §封: 診断を回す席に渡さない・数が出そろうまで開かない・当たりも外れも測れずも同じ大きさで書く)と、条件式 C-1 の検証(「1 人目の組の欄・g3 の中身は見ていない」「3 人の組の欄は見ていない」= 予測を先に書いて封をする)は、**同じ形**。反証レーンはこれを LLM に適用する。

**手順**
1. 反証レーンに渡すのは、**仮説 1 本(契約 §7 の `statement`・`observations`・`prediction`)と、同じ顧客の観測項目の全値(ID と数)**。他レーンの仮説、統合の途中経過、本人の言葉、B の文、冊子は渡さない。
2. 反証レーンの出力は 3 種類に限る(それ以外の文は捨てる):
   - **反例**(`counterexample`): 仮説と逆の向きの観測が**実在する局・手**(例: Y-5 の g02 序盤 18 秒で切れ負け、g06 序盤 60 秒で生き残り)。
   - **分母**(`denominator`): 仮説が引いた割合の分母が全体の何分のいくつか、比べている 2 つの割合の出現率が同じか(§2.2b の型。側の 151/238、62.6% 対 36.5% の型)。
   - **別の説明**(`alternative`): 同じ観測を説明する別の仮説(例: 「形を知らない」ではなく「時間が無い」)。**別の説明は新しい仮説として台帳に入る**(反証レーンが「正しい説明」を決めるのではない)。
3. 反証レーンは**同じ LLM の別セッションでよい**が、**入力の中身が違うこと**を機械で確かめる(渡したファイルの一覧を `provenance` に残す。他レーンの出力のパスが含まれていたら落とす)。
4. 反証が 1 つも出なかったときは、`counterEvidence: []` ではなく **`attempted: true, result: "none_found"`** と書く(「無い」を空で埋めない ― Failure Event の流儀)。

**測れないこと**: 反証レーンが挙げた「反例」が将棋として本当に反例か(局面の意味)は、この設計では監査しない。監査するのは**反例の観測が実在するか**(数の照合)だけ。

## 6. 統合方法

**やらないこと**: 「一番もっともらしい説明を書け」。**やること**: 仮説ごとに 4 欄を埋める。

| 欄 | 中身 | 機械で見るもの |
|---|---|---|
| 支持証拠 | 仮説が引いた観測(ID・値)と、その向き | 観測 ID の実在、値の一致(検査 1 の流儀) |
| 反証 | 反証レーンの出力(反例/分母/別の説明)と、それを受けて仮説が**残ったか・弱まったか・落ちたか** | `counterEvidence` が空でない、または `attempted: true` |
| 未確認 | 測っていないもの・測れないもの(§12 の項目を引く) | ― |
| 今どこまで言えるか | 3 値: **残る**(反証後も観測と整合)/**弱い**(反証と両立するが分母が小さい・別の説明が残る)/**落ちる**。**「正しい」は無い** | 状態遷移が契約 §7 の `status` に写っている |

**規則**
1. **一致を数えない。** 2 本のレーンが同じ仮説を出しても、支持証拠は観測の数で数える(同じ観測を 2 度数えない)。
2. 「弱い」の仮説も台帳に残し、予測を付ける。**捨てるのは「落ちる」だけ**(§8 の失効)。
3. 統合は「今回の顧客」の範囲でだけ言う。「初心者一般」に上げるのは知識レイヤーの昇格(§11)であって、統合レーンの権限ではない。
4. 統合の出力の**言葉は禁止語の検査(検査 3)を通す**(内部文書でも「原因」「癖」を使わない。使うと外に漏れる)。

### 7.2 機械が落とす条件(人が読む前に)

| # | 検査 | 流儀の出どころ |
|---|---|---|
| H-1 | `statement` と `counterEvidence.items[].text` の中の数は、`observations[].value` に実在する(登録済みの組の並びに一致。単独の数がどこかにあるだけでは通らない) | `check_answer.py` 検査 1 |
| H-2 | `observations[].obsId` は観測項目の一覧(§1・§2)に登録された ID である。未登録は落ちる | `condition.ts` 「表に無いパスは読まない」 |
| H-3 | `counterEvidence.attempted` が true で、`items` が空なら `result: "none_found"` | Failure Event「無いを 0 で埋めない」 |
| H-4 | `prediction` に `metric`(登録済み ID の式)・`comparator`・`value`・`window`・`writtenAt` が全部ある。**照合の日付より前** | §8、「予測は数で、測る前に書く」 |
| H-5 | `statement`・`text` に禁止語(18 語 + 断定語)が無く、「〜という読みです」「〜の可能性があります」の形 | 検査 3、規則 6 |
| H-6 | `provenance.inputs` に他レーンの出力・本人の言葉のパスが無い(反証レーンの出力について) | §5 盲検 |
| H-7 | `scope: "beginners_general"` は `knowledge.reviewStatus` が `human_reviewed` 以上でなければ落ちる | §11 昇格 |
| H-8 | `hypothesisId`・`provenance` に人名・絶対パスが無い | `pathForProvenance`、同意の線 |

**F-1 の型への答え**: 「数は実在するが主張が支えられていない」は H-1 では落ちない(数は実在する)。落とすのは **H-3 + §6 の統合**(反証が試みられ、分母の点検が記録されること)。**機械で落とせるのは形式まで**で、主張の妥当性は反証レーンと人間の監査(§10 の GO 条件)に残る。これを設計の限界として明記する。

## 8. 次の 20 局で検証可能にする方法

**今ある形**: 本編の「次の 20 局が来たら、何で答え合わせをするか」の表(試したこと / 動くはずの事実 / 今の値。素材は M の `verifyName`)。これは**承認済みの行動(M)にだけ**付いている。**広げる**: すべての仮説 H に `prediction` を必須にする(H-4)。

**仕組み**
1. **予測は数で、測る前に書く。** `prediction.writtenAt` が納品日以前であることを機械で見る。予測の後づけは、統括の「レーン長が測ってよい 3 条件」の 1 番と同じ理由で禁じる。
2. **同じ数え方でだけ比べる。** `window` は「同じ持ち時間の組の次の 20 局」に固定(本編の注記「同じ持ち時間の組で、同じ数え方をしたときだけ比べられます」を契約に写す)。
3. **分母の下限**(`alsoRequires`)を付ける。満たさなければ結果は **`unmeasured`**(外れではない)。4 人目の Y-2「測れなかった」と同じ扱い。
4. **照合の結果は 4 値**: `verified`(当たり)/`missed`(外れ)/`partial`(半分)/`unmeasured`(測れず)。4 人目の突き合わせ(当たり 2・半分 1・外れ 2・測れず 1)と同じ言葉。**当たりだけを数えない。**
5. **失効**: `missed` が続いた仮説は `expired` に落とす。**何回で落とすかは人間が決める**(候補: 2 回の照合で 2 回 `missed`)。`expired` は台帳から消さず、状態だけ変える(過去の仮説と確定知識が混ざらないため。決定 6)。
6. **答え合わせの表の機械可読化**: 本編の表は `hypothesis.*.json` の `prediction` から**生成**する(手で書かない)。これで「表に書いた数と契約の数が食い違う」型を塞ぐ。

**測れないこと**: 次の 20 局が来ない顧客では、この仕組みは動かない。**1 冊で成立する**(§2.5 の基本契約 4 つ目)ことは変えない ― 予測は書くが、当たり外れの確認は「来れば」。

### 10.3 実例(4 人目の材料で、この文書の中で 1 周を**紙の上で**回す)

- **③仮説(L-時間が出す形。例)**: **H-p4-min3-001**「崩れ 30 回はすべて 10 秒未満の手で起きていて、10 秒以上考えた手では 0 回。長く考える手と崩れる手が分かれている、という読みです」。引く数: 崩れ 30、内訳 17/10/0。
- **④反証(盲検で出うる 3 種)**: 反例 = 無し(10 秒以上で崩れた手が 0 なので反例は定義上無い)/**分母** = 「10 秒以上考えた手そのものが 18 局で何回あったか」が③の文に無い。0 回なら仮説は空(分母 0)。→ ①の `longThinkTotal` を引いて分母を書かせる/**別の説明** = 「切れ負けの 3 分では 10 秒以上考える手が構造的に少ない。長考が崩れを防いだのではなく、長考する余地が無かった」→ 新しい H として台帳へ。

## 11. 知識レイヤー(観測レイヤーとは分ける)

### 11.1 対応表: DATA_MODEL の 3 分類 × 知識 3 種類

| | **1. 将棋そのものの知識** | **2. 棋譜から発見した知識** | **3. コーチング知識** |
|---|---|---|---|
| **記述的(Kind 1)**: 既存スキーマに準拠した新レコード。件数の制限なし、露出制御必須 | `data/shapes|intents|openings/*.json`(今 3+8+3 件) | **仮説台帳の 1 行**(`hypothesis.*.json`。`scope: this_user`・`draft`)。件数の制限なし、**外に出さない** | 「このユーザーへの合わせ方」の 1 行(例: 「p4 には M9 が当たった/外れた」の記録) |
| **構造的(Kind 2)**: スキーマの形式・フィールドの意味・参照関係の変更。**人間承認** | `data/schemas/*` の変更 | `hypothesis.vN.schema.json` の版上げ、**`review_status` に失効(降格)の状態を足すこと** | 行動の表(`ANSWER_MENU`)の**欄**の変更(`minN` の型など) |
| **判断的(Kind 3)**: 判定結果・優先度・閾値・安全性・挙動を変える。**人間承認** | `STANDING_BOUNDS`(承認済み)・`WHATIF_VALUES`・`TIME_VALUES`・`GATE_VALUES`(仮置きを含む) | 仮説を **`beginners_general`** に上げる判断/`expired` にする回数 | **M1〜M9 の行そのもの**(条件・`minN`・文言)。**= 3 種類目の判断的知識の既存の実例**。表を増やすのは人間の承認 |

### 11.2 `review_status` を 2・3 種類目にも敷く

| 状態 | 1 種類目(既存) | 2 種類目(発見) | 3 種類目(コーチング) |
|---|---|---|---|
| `draft` | AI が追加した未レビュー | レーンが出した仮説(`proposed/weak/stands`) | 「このユーザーへの合わせ方」の記録 |
| `human_reviewed` | 人間のレビュー済み | **N 人で再現**(下の昇格条件)し、人間が読んだもの | 人間が表に載せる前の候補 |
| `expert_verified` | 有段者・一次資料(**0 件、保留**) | (同じ。**有段者の監修はしない**方針のため、当面 0 件) | 承認済みの表 M1〜M9 に相当(**ただし今の表は人間承認 = `human_reviewed` の位置**) |
| **`expired`(新。人間承認事項)** | ― | 次の 20 局の予測が外れ続けた仮説 | 効かなかった処方(ROADMAP Phase 4「効かなかった処方は表から消す」) |

**昇格の条件(条件式 C-1 で使った形をそのまま)**: **材料 / 試す / 盲検**。(1) 材料の顧客で `stands`。(2) **別の顧客(試す側)**で同じ `metric` が同じ向き(G-4 の形: 符号が同じで 0 でない)。(3) 試す側の数は、材料側の仮説を**見ずに**先に予測を書く。**N 人で再現するまで「一般」(`beginners_general`)に上げない。N は人間が決める**(候補: 3。C-1 は「3 人目で確定」の 3 段だった)。

### 11.3 2 種類目に必ず持たせるもの
- **出どころ**(`knowledge.origin`): 棋譜(どの顧客・どの組)/顧客の言葉(事前仮説)/レーン(どのレーン)。
- **範囲**(`knowledge.range` = `scope`): このユーザー / 初心者一般。**既定はこのユーザー。**
- **状態**(`status`)と**照合の履歴**(4 値の列)。

### 11.4 失効(降格)
- 予測が外れた(`missed`)仮説は `expired` に落とす。回数は人間が決める(§8)。
- **`review_status` に `expired` を足すことは、スキーマの変更 = 構造的知識 = 人間の承認事項。** この文書では「要る」と書くだけで、足さない。
- `expired` は消さない(過去の仮説として残す)。確定知識(`human_reviewed` 以上)と混ざらないのは、状態が違うから。**同じファイルに置くなら状態で分け、置き場を分けるなら `records/hypotheses/{draft,reviewed,expired}/` のように分ける(実装で決める)。**

### 11.5 3 種類目を 2 つに割る
- **初心者一般への提示**: 承認済みの表 M1〜M9 の文言(`actionCore`)と条件。**今の実例。**
- **このユーザーへの合わせ方**: 「p4 には M9 が当たり M4 は測れず」のような、**個人の照合の履歴**。これも同じ階段(`draft → human_reviewed`)に乗せる。**過学習の歯止め**: 1 人の履歴から表の行を変えない(N 人の再現が要る = 11.2)。

### 11.6 同意の線(concierge-prep/03 §B)
- 5 番「匿名の統計」の範囲は **(a) 他の方のレポートの比較対象の数、(b) 解析の物差しを確かめる統計**。記録そのものは外に出さない。
- したがって: **個人に紐づく仮説(`scope: this_user`)はその人の冊子と `records/` に留め、共有基盤へ入るのは `beginners_general` に昇格したもの(= 匿名の統計)だけ。** 昇格した知識にも `origin` に顧客の識別子を残さない(顧客の通し番号 `p4` は内部の記録だけ)。
- 6 番「次の 20 局との比べ」(任意、1 年)に同意しない顧客の仮説は、照合が来ないので `unmeasured` のまま。**同意が無くても 1 冊で成立**する(決定 4 の「何もなくレポートを頼む人」と同じ線)。
- 5 番を任意にするか必須にするかは人間(03 の未決)。任意なら、同意しない顧客の仮説は昇格の N に数えない。
