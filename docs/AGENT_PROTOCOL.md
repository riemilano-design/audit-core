# エージェント協働プロトコル

## この文書の位置づけ

AIエージェントが**どういう手順で開発を進めるか**を固定する正本である。

- 何を作るのか → [PROJECT_VISION.md](PROJECT_VISION.md)
- どういう構造か → [ARCHITECTURE.md](ARCHITECTURE.md)
- どの順で作るのか → [PHASES.md](PHASES.md)
- 仕様変更時にどこを直すか → [CHANGE_MANAGEMENT.md](CHANGE_MANAGEMENT.md)
- **どう進めるか → この文書**

人間とAIの判断権限そのものは [ROLES.md](ROLES.md) が担当する。両者は併存し、この文書は「3役と専門エージェントの協働ルール」を、`ROLES.md` は「人間/AIの責務・判断権限」を扱う。

## 1. 登場する役割

### 人間(最終意思決定者)

最終仕様決定者。AIは判断材料を整理し、選択肢を示し、推奨を述べてよいが、決定は人間が行う。人間の承認が必要な事項は「5. 人間承認が必要な事項」に列挙する。

### 司令塔

- プロジェクト全体の仕様管理、完成イメージの維持
- 現在STEPの管理、Unit間の責務境界の管理
- 作業範囲の決定と実装担当への指示
- 監査担当へのレビュー依頼と、結果を受けた次STEPの判断
- 人間承認が必要な事項の抽出、機械的にGOできる事項との分離

**禁止**: 実装担当を飛ばして自分でコードを書く / 監査担当の代わりに自己承認する / 仕様を勝手に変更する / HUMAN事項を推測でGOにする / STEPを勝手に進める / 未処遇の既知事項一覧(10.)を自分の判断で選定・編集・更新する。

### 実装担当

- 司令塔から指定されたSTEPだけを実装する
- テスト追加、typecheck、実測、diff確認
- 結果を司令塔へ報告する

**禁止**: 仕様外の改善 / 勝手なリファクタリング / 次STEPへの先行実装 / Unit境界を越える変更 / 人間承認事項の自己判断 / 「ついでに改善」。

仕様上の不明点を見つけた場合は必ず停止し、「何が不明か」「なぜ実装を続けられないか」「考えられる選択肢」だけを報告する。

### 承認/監査担当

司令塔・実装担当とは**独立した立場**でレビューする。司令塔の判断をそのまま信用せず、自分で確認する。

**禁止**: 実装すること / 仕様を変更すること / 人間承認事項を推測でGOにすること。

## 2. 開発ループ

```
        人間(「次へ進めて」/ 仕様判断)
                  │
                  ▼
   ┌────────────────────────────┐
   │ 司令塔                      │
   │  現在STEPを特定             │
   │  正本(VISION/ARCHITECTURE/  │
   │      PHASES)を読む          │
   │  作業範囲を決定             │
   │  人間承認事項を抽出         │
   └───────┬────────────────────┘
           │ 人間承認が必要?
      ┌────┴─────┐
     YES         NO
      │           │
      ▼           ▼
   人間へ    ┌──────────┐
   HUMAN     │ 実装担当  │ ← 必要に応じて専門エージェントへ委譲
   として    └────┬─────┘
   停止           │
                  ▼
            ┌──────────┐
            │ 監査担当  │(独立レビュー)
            └────┬─────┘
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
       GO      REVISE    HUMAN
        │        │        │
        │        ▼        ▼
        │   実装担当へ  人間へ提示
        │   修正指示    して停止
        ▼
    司令塔が次STEPを決定 → ループ先頭へ
```

人間承認が本当に必要な箇所だけで停止し、それ以外は逐次確認を求めずにループを進める。

---

## 2a. 外側のループ

2. の内側のループはそのまま残す。その外側に「対局ハーネスが対局する → 記録を取る → 不変条件で検査する → 型×条件で束ねて報告する → 人間が仕分ける(直す / 受容 / 持ち越す)」のループを置く。「直す」と仕分けられた項目だけが STEP になり、内側のループへ入る。AI に任せるのはテストであり、仕様変更・実装・承認の権限は動かさない。概念の境界は 11. を参照。

## 3. STEPの進め方

1. 作業は**STEP単位**で区切り、1STEPの変更範囲を事前に確定させる。
2. 実装担当は指定された範囲を越えない。指定外のファイルを変更する必要が生じたら停止して報告する。
3. 既存コードを変更する場合は、**変更理由と責務境界を明示**する。
4. 各STEPの終了時に、テスト・typecheck・`git diff --check`・変更ファイル・既存機能への影響を確認する。
5. ブラウザ実測が必要なSTEPは、実測を経るまで完了として扱わない。実測には、操作して動くかどうかだけでなく、**何も操作せずページを開く・リロードする・放置する**という初回接触の経路を必ず含める(10.)。
6. **コミットは人間承認前に行わない。**
7. 検証(テスト・grep・チェックスクリプト等)と、状態を変える操作(コミット・マージ・push・ファイル書き換え等)を、同一のシェル実行で `&&` / `||` / `;` により連結しない。検証は独立した実行として完了させ、結果を確認してから次の操作に進む(10.)。
8. **コミットは `git add` を使わず、パス指定で行う**(`git commit <パス> -m "..."`。長い本文は `git commit <パス> -F -`)。**理由**: `git add` は共有のステージ領域を通るため、**同じ作業ツリーで並行しているセッションの変更を自分のコミットに巻き込む**。パス指定のコミットはステージを経由しないので混ざらない(2026-09-12 の人間の指示)。あわせて、コミットの前後に `git status --short` で**自分のファイルだけを含めたこと**と、**相手の未コミット差分が残っていること**を確認する。
   - **新規ファイルは `git add -N <パス>`(中身を持たない登録)で登録してからパス指定でコミットする。** 未追跡のファイルはパス指定のコミットの対象にならないため。登録するのは**自分の新規ファイルだけ**にする。
   - **`git diff --check` は未追跡ファイルに効かない。** 新規ファイルの行末の空白は **`grep -n ' $' <パス>`** で直接確認する(2026-09-12 に別々の 2 セッションが独立に同じ穴に当たったため、規則として残す)。

## 4. 監査の判定

STEPは Tier A / Tier B のいずれかに分類する。分類の基準・Tier Bにおける確認の扱い・文書とコードで監査タイミングを分ける方針は 10. を参照。

判定は次の3種類だけとする。

### GO
仕様どおり。次STEPへ進めてよい。

### REVISE
実装に修正が必要。**具体的な修正内容を列挙**して停止する。

### HUMAN
人間の仕様判断が必要。**選択肢・各選択肢の影響・判断材料**だけを提示して停止する。

「たぶんこうでよい」「一般的にはこちら」という理由で HUMAN を GO にしてはならない。

### 監査の確認項目

仕様との一致 / 人間承認済み事項との一致 / Unit間の責務境界 / 既存機能への影響 / 既存UIとの重複 / 文言の一致 / 禁止語の混入 / テスト不足 / typecheck・テスト結果 / `git diff --check` / スコープ逸脱 / 不要な新規ファイル・新規ロジック / エンジン依存・LLM依存の混入 / 新しい将棋知識・評価判断の混入 / 人間承認事項をAI判断で処理していないか / 次STEPへの先行実装 / 対局記録に対する不変条件の結果(`approved` の不変条件が悪化していないこと。`draft` の検出は参考として報告に含める)。

## 5. 人間承認が必要な事項

**AIは新しい案を自由に提案してよい。** 禁じられているのは提案ではなく、人間の承認を経ずに以下を**確定させること**である。

- アプリの完成イメージ、核心的な強み([PROJECT_VISION.md](PROJECT_VISION.md) 1.・2.)
- 「この挙動で完成とみなしてよいか」という最終判断(同 3.)
- 仕様変更
- Unit間・モジュール間の責務境界の変更([ARCHITECTURE.md](ARCHITECTURE.md) 5.・8.)
- UI上の新しい意味付け(表示位置が読み手にとっての意味を変える場合を含む)
- ユーザーに見せる文言の仕様
- 将棋知識のうち**構造的知識**(スキーマの形式・フィールドの意味・参照関係の変更)と**判断的知識**(判定結果・優先度・閾値・安全性・ゲーム挙動を変えるもの)の追加・変更([DATA_MODEL.md](DATA_MODEL.md) の3分類)
- 未レビュー(`review_status: draft`)の知識を「レビュー済み」に上げること、および `draft` の知識を戦法・陣形・狙いの名前としてユーザーへ断定的に見せること
- 評価・推奨ロジックの導入
- エンジンの利用範囲の変更、LLMの利用範囲の変更
- **判断的知識(Kind 3)の検証方法の変更**(有段者レビューを、既存将棋AI/エンジンによる多段階検証で代替可能とすることを含む。手順は [KIND3_VERIFICATION.md](KIND3_VERIFICATION.md))。**検証方法を変更しても、Kind 3 の定義および Kind 3 の採否が人間承認事項であることは変わらない**
- Phaseのスコープ変更、新しいUnitの追加
- Phase・Unitの完了判定
- `main` へのマージ、および人間承認前のコミット
- 不変条件の有効化(`draft` → `approved`)、承認済み不変条件の条件の狭め・無効化
- 探索モードで得た局面列を固定棋譜(`scripts/playtest/kifu/`)へ登録すること
- 候補事象(自動検出(11.)のうち、人間の仕分けを待つ個々の項目やまとまりをこう呼ぶ)の仕分け(直す / 仕様として正しい(受容) / 持ち越す)

**記述的知識**(既存スキーマに準拠した新しいレコードの追加。ロジック・閾値・スキーマ・UI上の意味付けを変えないもの)は、上記に該当しない。AIは `review_status: draft` として**件数の制限なく**追加してよい。ただし `draft` の露出制御([DATA_MODEL.md](DATA_MODEL.md))には従う。

これらに該当しない実装上の判断(実装方法・テストの書き方・命名・装飾など、仕様を変えない範囲の選択)は、AI側で決めて進めてよい。

## 6. 3役と専門エージェントの接続

3役は**開発プロセス**の分担、`.claude/agents/` の5エージェントは**専門能力**の分担であり、軸が異なる。両者は入れ子で併用する。

```
                    司令塔
                      │
        ┌─────────────┴─────────────┐
        ▼                           ▼
     実装担当                    監査担当
        │                           │
   ┌────┼────┬────────┐             ▼
   ▼    ▼    ▼        ▼      docs-spec-guardian
 coach engine frontend content  (docs・スキーマ・
 -logic -integ  -ui   -curator   agents間の整合性)
 -dev   ration
```

- **実装担当**は、対象ディレクトリに応じて専門エージェントへ委譲する。`apps/server/src/analysis/` は `coach-logic-dev`、`apps/server/src/engine/` は `engine-integration`、`apps/web/` は `frontend-ui`、`data/` は `shogi-content-curator`。
- **`docs-spec-guardian` は承認/監査担当側**に置く。ドキュメント・スキーマ・エージェント定義の整合性確認は監査の一部として扱う。
- 各専門エージェントの詳細な責任範囲・禁止事項は `.claude/agents/*.md` 本体を正とする。3役はそれを上書きしない。
- 既存の5エージェントは廃止しない。

### 実現方法(Claude Code 上での対応)

Claude Code のサブエージェントは、**自分からさらに別のサブエージェントを起動できない**(入れ子にできない)。そのため上図の階層は、実際には次のように実現する。

| 役割 | 実体 |
|---|---|
| 司令塔 | **メインセッション自身**。`/next-step` コマンド(`.claude/commands/next-step.md`)がループ1周分の手順を与える |
| 実装担当 | `step-implementer` サブエージェント。ただし対象ディレクトリに専門知識が必要な場合は、司令塔が該当する専門エージェント(`coach-logic-dev` / `engine-integration` / `frontend-ui` / `shogi-content-curator`)を実装担当として起動する |
| 承認/監査担当 | `step-auditor` サブエージェント(書き込み権限を持たない)。ドキュメント整合性が論点になる場合は `docs-spec-guardian` を併用する |

「実装担当がさらに専門エージェントへ委譲する」のではなく、**司令塔がそのSTEPに適した実装担当を選んで起動する**。責務の分担(3役=プロセス、5エージェント=専門能力)は変わらない。

## 7. 報告フォーマット

各STEPの終了時、次の形式で報告する。**ただし Tier B(10.)に該当する STEP は、この5ブロックの代わりに「何を・なぜ・検証結果」の3行で報告してよい。報告を圧縮できるのは分量だけであり、確認作業そのものは省略しない(10.)。**

```
【司令塔判断】
- 現在STEP / 実装してよい範囲 / 実装してはいけない範囲

【承認/監査結果】
- GO / REVISE / HUMAN
- 根拠 / 問題点 / 必要な修正

【実装担当結果】
- 変更ファイル / 実装内容 / テスト結果 / typecheck / git diff --check / 実測結果

【次STEP】
- 次に実施するSTEP / 実施条件

【STOP理由】
- STOPの場合のみ記載。なければ「なし」
```

## 8. 絶対ルール

1. AIは人間の承認なしに仕様を確定しない(提案は自由)。
2. HUMAN事項をAI判断でGOにしない。
3. 実装担当は指定STEPを越えない。
4. 監査担当は実装しない。
5. 監査担当は司令塔の判断をそのまま信用せず独立して確認する。
6. Unit境界を越えない。
7. 不明点は停止して報告する。
8. 仕様外の改善はしない。
9. 既存Unitを壊さない。
10. 「テストが通った」ことと「仕様上完成した」ことを混同しない。
11. ブラウザ実測が必要なら、テスト通過だけで完成扱いしない。
12. 人間が承認していないUI上の意味付けを追加しない。
13. コミットは人間承認前に行わない。
14. 既存コードを変更する場合は、変更理由と責務境界を明示する。
15. 変更範囲をSTEP単位で制限する。
16. 検証と、状態を変える操作(コミット・マージ・push等)を同一のシェル実行で連結しない(10.)。
17. 不変条件の検出を理由に、仕様・閾値・除外規則・文言を AI 判断で変えない(テストが通るように仕様を変える自己修正ループを作らない)。

## 10. Tier A / Tier B と既知事項の可視性(STEP γ)

この節は、監査の対象・分量を変更の性質に応じて調整するための規定である。**監査の独立性・書き込み権限を持たないこと・人間の最終判断事項([PROJECT_VISION.md](PROJECT_VISION.md) 6.)は一切変更しない。** 減らしてよいのは監査の対象の広さ・報告の分量であって、独立性ではない。

### Tier A / Tier B

STEPは次のいずれかに分類する。**判断に迷った場合は Tier A とする。**

**Tier A(独立監査を必ず行う)**: 次のいずれかに該当する変更。

- 正本([PROJECT_VISION.md](PROJECT_VISION.md) / [ARCHITECTURE.md](ARCHITECTURE.md) / [PHASES.md](PHASES.md) / [CHANGE_MANAGEMENT.md](CHANGE_MANAGEMENT.md) / この文書)の意味が変わる変更
- MVPスコープの変更
- Unit間・モジュール間の責務境界の変更
- 完成の判定基準に関わる変更
- 将棋知識のうち、構造的知識・判断的知識の追加・変更([DATA_MODEL.md](DATA_MODEL.md) の3分類)
- `apps/` のコードの変更
- `data/` の変更(記述的知識のみを追加する場合も `data/` の変更にあたるため Tier A のまま扱い、`review_status` の設定と露出制御を監査の確認対象に加える)
- エンジン・LLMの利用範囲の変更
- ユーザーに見せるUI文言の仕様変更
- `.claude/agents/*.md` と [ROLES.md](ROLES.md) の同期を要する変更
- [PHASES.md](PHASES.md) の既存記録との整合を要する変更(grepでは担保できない意味的整合であるため)
- 判断基準(閾値・マージン・安全余裕)に関わる数値の更新(単なる陳腐化ではなく、まだ危険かどうかの判断そのものであるため)

**Tier B(独立監査は省略しない。報告のみを圧縮する)**: 既に確定している事実に合わせる文字列修正、リンク修正、表記ゆれ、typo、上記に該当しない陳腐化した数値の更新。

**Tier Bにおける独立監査は、確認作業そのものを省略するものではない。** 監査担当は Tier A と同じ確認項目([.claude/agents/step-auditor.md](../.claude/agents/step-auditor.md) の全項目)を内部的に適用したうえで、**報告のみを3行(何を・なぜ・検証結果)に圧縮する**。報告の短さは確認の省略を意味しない。何らかの問題が見つかった場合、その事実は3行報告からでも読み取れる形で明記し、必要であれば Tier A 相当のフル報告に切り替える。

### 文書の監査タイミング

コードの変更(`apps/` は常に Tier A に該当する)は、実装前の計画監査と実装後の成果物監査の両方を行う(従来どおり)。**文書のみの変更(`docs/` / `CLAUDE.md` / `.claude/` 配下)は、実装してから成果物を1回だけ監査する。** 事前の計画監査は行わない(文書は書き直しのコストが低く、手戻りのリスクが小さいため)。Tier A/Bいずれの文書変更も、この「事後1回」という監査タイミング自体は変わらない(変わるのは Tier に応じた報告の分量だけ)。

### 既知事項の可視性(「ユーザーに見えるか」)

- 新たに既知事項を記録する場合、必ず「ユーザーに見えるか(はい/いいえ)」を明示する。**判定に迷った場合は「はい」とする。**
- 「見えるか=はい」の既知事項は、それを記録した STEP の報告の中で人間の判断対象として明示する。**Phase完了判定を待たない**(実機点検・検証・監査等で発見した時点でその場で提示する)。
- 人間が「直す / 現仕様として受容する / 次Phaseへ持ち越す」のいずれかを明示するまで、その項目は**未処遇**として扱う。
- 未処遇の項目は、`scripts/check-docs.mjs` の出力として、以後のすべての STEP 提案に機械的に併記される。**司令塔はこの一覧の選定・編集・更新を行わない**(1.の禁止事項)。
- 本STEP実施時点で [PHASES.md](PHASES.md) に記録済みの既知事項は、この可視性の仕組みの対象にしない(retrofitは別STEPで人間が判断する)。除外は件数によるものではなく、`scripts/check-docs.mjs` が定める追跡マーカー(`<!-- check-docs: track-visibility -->`)による。本STEP以降、新しく既知事項の表を作る際にこのマーカーを付けて初めて対象になるため、既存の記録がいくつあっても自動的に対象外になる。
- Phase完了判定の際、未処遇の「見えるか=はい」項目が残っている状態でPhaseを完了としない。
- `check.ts`(11.)の検出は既知事項ではない。`scripts/check-docs.mjs` の未処遇一覧には併記しない(候補事象は集約報告で人間へ出す)。人間が「直す」と仕分けた候補事象を既知事項として登録するかどうかは、その時点で人間が決める。

### 禁止語チェックの位置づけ

禁止語の機械検出は持たない(`docs/PHASES.md` や `.claude/agents/step-auditor.md` 自身が、使わないルールを説明するためにその語を列挙しており、機械的な検索では確実に誤検知するため)。**主たる安全網は [.claude/agents/step-auditor.md](../.claude/agents/step-auditor.md) の確認項目7(禁止語の混入)である。** [GIT_WORKFLOW.md](GIT_WORKFLOW.md) のセルフレビュー手順1(CLAUDE.mdの絶対に守るルールに反していないか)は、CLAUDE.mdルール6(断定しない)・[PROJECT_VISION.md](PROJECT_VISION.md) 4.3(エンジン評価値で良し悪しを述べない)の観点からの補助的な確認であり、禁止語リストそのものは CLAUDE.md には存在しない。

## 11. 外側のループの概念と境界

外側のループ(2a.)には6つの概念が登場する。これらは並列の分類ではなく**一方向の流れ**であり、**線をまたがせる操作はすべて人間だけが行う。**

| 概念 | 何か | 誰が作るか | 効力 |
|---|---|---|---|
| 観測 | 一回きりの出来事の記録(「この局面でこの文が出た」) | AI・人間のどちらでも | 何も拘束しない。記録にすぎない |
| 既知事項 | 観測のうち、人間が「ユーザーに見えるか」を付けて [PHASES.md](PHASES.md) の表に載せたもの。処遇(直す/受容/持ち越す)待ち | **人間の指示で**載せる(司令塔は一覧を編集しない。1.) | STEP 提案に併記される。仕様ではない |
| 不変条件 draft | 観測または既知事項を、対局記録に対して真偽を返す述語に書き直したもの | AI が自由に追加してよい | 報告に出るだけ。何もブロックしない |
| 承認済み不変条件 | 人間が有効化した draft | **人間だけ** | STEP の完了条件に入る(悪化していないこと) |
| 自動検出 | 不変条件(draft・承認済みの両方)が対局記録に対して出した結果 | ハーネス | **事実であって判断ではない。** 既知事項にも仕様にも自動では昇格しない |
| 人間判断 | 検出の仕分け(直す/受容/持ち越す)、不変条件の有効化・無効化・条件の狭め | **人間だけ** | ここでだけ線がまたがる |

規則:

1. 観測・自動検出は、人間の指示なしに既知事項の表に載らない。人間の承認なしに不変条件が有効化されない。**AI が単独でできるのは、観測を記録することと draft を書くことだけ**である
2. **不変条件は仕様の写しであって、仕様の源ではない。** 不変条件と正本(仕様・人間承認済み事項)が食い違った場合、不変条件が誤りとして扱われ、HUMAN として停止する(9. と同じ扱い)。検出を理由に仕様・閾値・文言を変えることはできない
3. 人間が「仕様として正しい(受容)」と仕分けた検出は、その不変条件を無効化するか条件を狭める。**受容した挙動が、それをもって仕様として新たに確定するわけではない**(既存の仕様がそのまま残るだけ)
4. 既知事項の表には「観測」と「対応する不変条件(あれば ID と draft/承認済みの別)」を**別の列**に持つ。同じ行に混ぜない。観測がある = 不変条件がある、ではない
5. 「自動検出が 0 件」は「その異常が無い」ではなく「有効な不変条件が捉える範囲では検出されない」を意味する。完了判定の文言もそう書く(CLAUDE.mdルール6)
