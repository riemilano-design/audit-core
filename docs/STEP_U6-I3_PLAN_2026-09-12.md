## 4. 条件 (4)「LLM が書いた記録と後から区別できる」の具体案

**人間の指示: 欄を足さずに済む方法があるならそちらを先に検討すること**(スキーマに欄を足すのは構造的知識 = 人間の承認が要る)。

### 4.1 欄を足さない案(**こちらを推す**)

| 案 | 中身 | スキーマ変更 | 機械で検出できるか | 弱点 |
|---|---|---|---|---|
| **(a) `source` の接頭辞の規約** | `source` の**先頭**に定型句を必ず置く。例: **`【AI下書き / 出典は下記】`** | **不要**(`source` は自由記述の文字列) | **できる**(`source.startsWith(...)` の 1 行) | 人が後から書き換えれば消える。**規約であって保証ではない** |
| **(b) git の著者情報** | LLM が書いたコミットは `Co-Authored-By: Claude ...` を必ず持つ。`git log --follow <file>` で辿れる | **不要** | できる | **ファイルを人が後から編集すると混ざる**(どの行が誰かは分からない) |
| (c) `review_status` を使う | `draft` = LLM が書いた、とみなす | 不要 | できる | **不可**。`draft` は「未レビュー」であって「LLM が書いた」ではない。**人間が書いた `draft` もありうる。条件 (4) が条件 (1) と別に立っている理由がこれ** |

### 4.2 推す組み合わせと、その理由

> **(a) を主、(b) を従にする。**

- **(a) は `data/` の中で完結する。** レコードだけを見れば分かるので、`git` の履歴を辿らなくても、他のツール(`validate-data.mjs`・curator・将来の UI)から同じ判断ができる
- **(b) は改竄しにくいが、追跡に手間がかかり、部分編集に弱い。** (a) の裏取りとして使う
- **(c) は条件 (4) を満たさない。** ここを混同すると「`draft` を消したら区別も消える」ことになる

### 4.3 実際の作業手順に落とした形(案)

1. **書くとき**: `source` を **`【AI下書き / 出典は下記】`** で始め、続けて S-1〜S-5 を満たす本文を書く
2. **コミットするとき**: `Co-Authored-By:` を付ける(既に全コミットで実施済み)
3. **検査するとき**: `scripts/validate-data.mjs` に**警告(エラーではない)**を足す ― `review_status: "draft"` なのに `source` が定型句で始まらないレコードを一覧にする
4. **人間が承認して `human_reviewed` へ上げるとき**: **接頭辞は消さない。**「LLM が下書きし、人間が審査した」という履歴がレコード上に残る形にする(条件 (4) は「区別できる」であって「draft の間だけ区別できる」ではない)

> **3. を「警告」に留める理由**: **エラーにすると、何が有効なデータかの定義が変わる = 構造的知識の変更**にあたり、人間の承認が要る([CLAUDE.md](../CLAUDE.md) ルール4)。**まず規約として運用し、エラーに上げるかは人間が後で決める。**

### 4.4 既存の 5 件をどうするか(**人間の判断が要る**)

U6-I1・I2 で足した 5 件は、この規約より前に書いたため接頭辞が無い。ただし全件が `本アプリ自身の実測記録から起こした下書き。` で始まっており、**実質的には区別できる状態にある**。

- 案 1: 遡って接頭辞を付ける(`data/` の 5 ファイルを触る)
- 案 2: 付けず、規約はこれから書くものに適用する(**既存 5 件は git の `Co-Authored-By` で辿れる**)

**どちらにするかは人間が決める。**
