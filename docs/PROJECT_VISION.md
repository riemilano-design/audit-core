# プロジェクトの完成像

## この文書の位置づけ

このプロジェクトが**最終的に何を実現しようとしているのか**を固定する正本である。コードから読み取れる実装上の都合よりも、この文書に明示された内容を優先する。

この文書に書かれた内容は、**人間(プロジェクトの最終意思決定者)が決定したものだけ**である。AIエージェントはこの文書を根拠に判断してよく、**新しい案を自由に提案してよい**。ただし、この文書の内容を人間の承認なしに変更・確定してはならない。変更したほうがよいと考えた場合は、変更を実行せずに提案として提示し、人間の判断を仰ぐこと。

関連する正本: [LONG_TERM_VISION.md](LONG_TERM_VISION.md)(MVPの先にある長期構想。本文書の完成条件には含まれない)、[ARCHITECTURE.md](ARCHITECTURE.md)(構造と責務境界)、[PHASES.md](PHASES.md)(開発計画)、[CHANGE_MANAGEMENT.md](CHANGE_MANAGEMENT.md)(仕様変更の手順)、[AGENT_PROTOCOL.md](AGENT_PROTOCOL.md)(エージェントの協働ルール)。人間とAIの判断権限の線引きは [ROLES.md](ROLES.md) が担当する。

## 1. 核心的な強み

> **「次に指す手」を教えるのではなく、「次に何を考えるべきか」を教えることで、将棋の考え方そのものを身につけさせるAIコーチであること。**
> **局面ごとの答えではなく「目的 → 候補 → 理由」という思考の道筋を提示する。**

これがこのアプリの存在理由である。他の将棋ソフトとの違いはここにしかない。

この一文と矛盾する実装・データ・UI文言は、たとえ技術的に正しくても、たとえユーザーにとって便利に見えても採用しない。

## 2. MVPの完成イメージ

> **将棋初心者が対局中に、相手の意図・自分の目的・次に何を考えるべきかを理解し、その思考に沿って自分で候補手を選択できるAIコーチ。**

「自分で選択できる」ことが到達点である。アプリが手を選んであげることではない。

## 3. 完成の判定基準

> **将棋初心者が対象の対局を通して、相手の狙い・自分の目的・次に考えるべきことを理解し、その考え方に沿って自分で候補手を選択できる状態。**

**テストが通ったことは、完成したことを意味しない。** 自動テスト・型チェックがすべて通っていても、上記の状態に達しているかどうかは別の判断であり、その判定は人間が行う([ROLES.md](ROLES.md))。実際に人間が対局して確かめる必要がある場合、その確認を経ずに完成として扱わない。

## 4. この完成像から導かれる、変えない前提

以下は [../CLAUDE.md](../CLAUDE.md) および [DATA_MODEL.md](DATA_MODEL.md) で既に確定している事項であり、上記の完成像を支える土台である。人間の承認なしに変更しない。

### 4.1 「覚えさせる」のではなく「考え方を身につけさせる」

このプロジェクトは、「定跡を覚えさせるアプリ」ではなく **「将棋の考え方を対局中に身につけさせるAIコーチ」** である。**「最善手を教えるアプリ」ではない。**

迷ったら「これは"覚えさせる"設計になっていないか?」「これは"答えを教える"設計になっていないか?」を自問すること。

### 4.2 意味づけのパイプライン

単なる「局面 → 次の一手」の対応表ではなく、各局面に意味づけを持たせた9段階のパイプラインを中核に置く。

```
局面 → 戦型・形 → 相手の意図 → 相手の次の狙い → 自分の目的
     → 目指せる形 → 代表的な候補手 → その手の目的 → 初心者向け説明
```

各段階の詳細は [DATA_MODEL.md](DATA_MODEL.md)、実装上の責務分担は [ARCHITECTURE.md](ARCHITECTURE.md) を参照。

### 4.3 将棋エンジンの役割は「安全確認」であって「最善手」ではない

```
エンジン → 安全確認(悪手でないかのチェック)     ← これが本アプリの使い方
エンジン → 最善手の提示                        ← これは本アプリの使い方ではない
```

エンジンの評価値を根拠に「この手が良い/悪い」とユーザーへ述べない。一方で、安全確認を経ていない候補手をユーザーに見せてもいけない。

### 4.4 LLMに将棋の事実判断をさせない

「この形は何か」「相手の意図は何か」といった将棋の事実判断をLLMに行わせない。LLMを使う場合の役割は、既に確定した判断を自然な言い回しに整える「言い換え」に限定する。

### 4.5 説明は「目的 → 手 → 理由」の順で構成する

手だけを提示しない。将棋用語には必ず初心者向けの説明を添える(用語を知っている前提にしない)。断定できないことは断定せず、控えめな表現を既定とする。

### 4.6 将棋の知識データは人間のレビューを前提とする

定跡・形・意図データ(将棋の知識そのもの)を、人間のレビューなしに大量生成・確定しない。

### 4.7 MVPのスコープ

- 対局: 四間飛車(ユーザー)vs 居飛車(AI)
- 先後: ユーザー(四間飛車側)= 先手固定、相手(居飛車側)= 後手固定
- 目標形: 美濃囲い系(本美濃・高美濃・銀冠)
- プラットフォーム: Webブラウザ
- 想定ユーザー: プログラミング経験・将棋経験ともに前提としない初心者
- 実験機能: **指す前にユーザーが「この手は何のため」を申告する仕組み**(MVPの中心機能ではなく、最小の実験機能として含める。詳細は [LONG_TERM_VISION.md](LONG_TERM_VISION.md))

このスコープを広げる変更には人間の承認が必要である。

以下はMVPの完成条件に含めない。着手の判断は、MVPの完成を人間が確認したあとで別途行う。これらを含めた全体像は [LONG_TERM_VISION.md](LONG_TERM_VISION.md) にある。

## 6. AIが確定してはいけない事項

**AIは新しい案を自由に提案してよい。** 禁じられているのは提案そのものではなく、人間の承認を経ずに以下を**確定させること**である。

以下は人間の最終意思決定事項である。AIは判断材料を整理し、選択肢を提示し、推奨を述べてよいが、AIだけで「これで確定」と結論を出してはならない。

- アプリの完成イメージ(本文書 2.)
- アプリの核心的な強み(本文書 1.)
- 完成の判定基準、および「この挙動で完成とみなしてよいか」という判断(本文書 3.)
- UI上の新しい意味付け
- 仕様変更
- Unit間の責務境界の変更
- 新しい将棋知識の追加
- `main` ブランチへのマージ、および人間承認前のコミット

これらに該当する判断が必要になった場合、AIは推測で確定させず、選択肢・判断材料・推奨案を提示して停止する。逆に、これらに該当しない実装上の判断(実装方法・テストの書き方・命名・装飾など、仕様を変えない範囲の選択)は、AI側で決めて進めてよい。
