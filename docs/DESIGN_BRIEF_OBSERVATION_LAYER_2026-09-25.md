**書く席**: 司令塔(統括)。人間の決定を直接受け取った席が書く([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 5.2)。

## 0. 人間の決定(2026-09-25。4 人目 = 本人の 20 局の納品の後の議論で)

1. **対局後診断は最終目的ではなく、対局中コーチを作るための研究工程である。** 20 局の診断で得た観測と仮説を、対局中コーチの知識基盤へ戻す。**売り物(ココナラの 20 局診断)は変えない。** これは 2026-09-14 の「主役を対局後診断へ」の**目的の側**の読み替えであり、製品の側は動かさない。
2. **いま GO を出すのは「shapes を増やす」ことではなく、観測レイヤーそのものの設計思想である。** 形の語彙は、設計が「要る」と決めた桁として増やす(目的は LLM に将棋を教えることではなく、多角的分析と対局中コーチの**共通言語**を作ること)。
3. **LLM は判定者にしない。仮説生成器・批判者・整理者として使う。** 「複数の LLM が一致した」= 正しい、ではない。何を根拠にしたか・何を観測したか・どんな仮説か・反証を試したか・反証後も残ったか・次の 20 局で何が変わるはずか、まで記録する。
4. **ヒアリングは事前仮説を作るためだけに使う。** 20 局の各手に本人の説明を貼らない。ヒアリング無しでも成立する設計にする(何もなくレポートを頼む人がいる)。
5. **時間は症状であって原因ではない。** 「何を判断するために時間を使ったか → その判断に使える形・戦法・目的の知識があったか → 知識があれば判断コストは変わった可能性があるか」まで行く。
6. **知識は 3 種類に分けて蓄積する**(将棋そのものの知識 / 棋譜から発見した知識 / コーチング知識)。観測レイヤーと知識レイヤーは分ける。確定知識と過去の仮説が混ざらない形にする。
7. **今は実装しない。設計思想を確定する段階。** 設計を人間が GO してから実装に入る。

**根拠(この決定に至った実測)**: 4 人目の 20 局で、本人が数を見る前に書いた言葉と道具の数を封をして突き合わせた結果、当たり 2・半分 1・外れ 2・測れず 1(`out/kori/02-突き合わせ_2026-09-25.md`)。「序盤を早くすれば後半に残る」は反例が実物にあり(g02 序盤 18 秒で切れ負け、g06 序盤 60 秒で生き残り)、時間の側だけでは本人の仮説(形を知らないから闇雲に指す)を支持も反証もできなかった。**測れないものを「なぜ」として書かない規則は正しいが、仮説として立てて次の 20 局で検証する経路が無かった。**

## 1. 設計案に含めるもの(9 節 + 3 + 知識レイヤー)

タイトル: **「多角的 LLM 分析のための観測レイヤー設計案」**

1. **既存の観測項目**(いま道具が出している事実の一覧。まとめ・付録 1〜4・Failure Event・diagnosis-moment・条件式・時間・分かれ道・側)
2. **新しく足す観測項目**(形・囲い / 戦型 / 玉・飛車の位置 / 駒の展開 / 攻撃・守備の準備 / 相手への反応 / 手の目的候補 / 分岐点 / 評価値変化 / 時間 / その他)
3. **各観測項目がどの LLM レーンに供給されるか**
4. **LLM が推論してよい範囲**(禁止 = 断定「あなたは〜だからこの手を指した」/ 可能 = 「この局面では A・B・C の目的が成立し、実戦はどれとも対応しない手だった。同様の事例が 7 局中 5 局。『目的設定が弱い』仮説と整合するが、他の説明も残る」)。**CLAUDE.md 規則 5 の拡張案をここに同梱する(決めるのは人間。最重要コンセプトに触るため)**
5. **反証レーンの独立性**(反証担当には**事実と仮説だけ**を渡し、他レーンの推論を見せない。盲検)
6. **統合方法**(「一番もっともらしい説明を書け」ではなく「各仮説について、支持証拠・反証・未確認事項を整理し、現時点でどこまで言えるかを決めろ」。一致を強い証拠として数えない)
7. **仮説の記録形式**(**機械で検査できる契約 = JSON スキーマ**にする。Failure Event と同じ流儀。根拠の数が付録に実在するか・反証が試みられたか・予測が数で書かれているかを、人が読む前に機械が落とす)
8. **次の 20 局で検証可能にする方法**(各仮説に「次の 20 局で動くはずの数」を必ず付ける。今の冊子の「答え合わせの表」を仮説側に広げる。**予測は数で、測る前に書く**)
9. **将来の対局中コーチへの接続**(認識の ID を対局中と対局後の結合キーにする)

**司令塔が足す 3 点(本文に組み込む)**
- **A. 観測項目を 2 列に分ける**: 「知識なしで作れるもの(幾何: 玉の位置・飛車の筋・手の向き・相手への反応・駒の展開)」と「語彙が要るもの(形・囲い・戦型・手の目的候補)」。**どこまでを機械の事実として信じてよいかの線**を最初から引く。
- **B. 仮説の記録形式は契約(スキーマ)にする**(7 と同じ。F-1 の型 = 数は実在するが主張が支えられていない、が仮説層に移るのを防ぐ)。
- **C. 「最小の 1 周」を入れる**: 全レーンを作る前に、既にある 4 人分の事実で「観測 → 1 レーン + 反証 → 統合 → 予測 1 つ」を 1 周だけ回す設計。**設計の GO 条件は「人間が手順で監査できるか」**(根拠が辿れる・反証がある・予測が数である)。将棋の真偽の監査は前提にしない。

**知識レイヤーの節(1 つ足す)**
- [DATA_MODEL.md](DATA_MODEL.md) の 3 分類(記述的・構造的・判断的)× 知識 3 種類(将棋そのもの / 棋譜から発見 / コーチング)の対応表
- `review_status`(draft → human_reviewed → expert_verified)を 2・3 種類目にも敷く。昇格の条件は条件式で使った形(材料・試す・盲検を別の人にする。**N 人で再現するまで「一般」に上げない**)
- 2 種類目には**出どころ**(棋譜・顧客・レーン)と**範囲**(このユーザー / 初心者一般)を必ず持たせる
- **失効(降格)の状態を足す**(次の 20 局の予測が外れた知識は落とす)。スキーマ変更 = 構造的知識 = **人間の承認事項**として明記
- 3 種類目は「初心者一般への提示」と「このユーザーへの合わせ方」に割る。後者も同じ階段に乗せる(過学習の歯止め)。**承認済みの行動の表(M1〜M9)は 3 種類目の既存の実例**として位置づける
- **同意の線**: 顧客の棋譜から出た知識は、個人に紐づくものはその人の冊子に留め、一般化したものだけ共有基盤へ(concierge-prep/03 の同意は匿名の統計まで)
