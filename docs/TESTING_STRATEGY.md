# 自動テスト戦略

## 現状

`apps/`(本実装)向けのNode.js環境はまだ構築されていない(Phase 0本体の作業)。一方、Phase 0着手前の技術検証(`spike/`)・プロトタイプ検証(`prototypes/`)・共通ユーティリティ(`scripts/lib/`)では、それぞれ独立したNode.js環境([node:test](https://nodejs.org/api/test.html)使用)でテストが既に存在し実行できる(例: `scripts/lib/usi-coordinates.test.mjs`、`prototypes/shape-matcher/*.test.mjs`)。これらは検証用途のテストであり、`apps/` 本実装向けのテスト基盤ではない。ここでは方針とテストの種類を先に決めておき、Phase 0本体(`apps/` の作成)以降で本実装向けのテスト基盤として順次有効化する。

## テストの種類

### 1. データスキーマ検証(最優先・最も軽量)

`data/`配下の全JSONファイルが、対応する `data/schemas/*.schema.json` に準拠しているかを機械的に検証する。

- 実行方法: `scripts/validate-data.mjs`(Node.js標準機能のみで書かれた軽量バリデータ。外部ライブラリのインストールを待たずに、Node.jsさえ入っていれば動く)
- 検証内容: 必須フィールドの有無、型の一致、IDの相互参照(`intents.opening_id`が実在する`openings.id`を指しているか等、[DATA_MODEL.md](DATA_MODEL.md)の「IDの参照関係」を参照)
- 実行タイミング: `.claude/settings.json` のフックにより、`data/`配下のファイルをWrite/Editした直後に自動実行(Node未インストール時は安全にスキップされる。[CHANGE_MANAGEMENT.md](CHANGE_MANAGEMENT.md) 参照)

### 2. ロジック単体テスト

形判定・意図推定・経路計画などのロジックは、SFEN(局面)を入力として受け取り、判定結果を返す**純粋関数**として実装する方針にする(副作用を持たせない)。これにより、以下のようなテストが書きやすくなる。

```
入力: SFEN文字列(既知の局面)
期待値: 判定されるべき形・意図
```

- 使用ツール: Vitest(Phase 0でセットアップ)
- 置き場所: 各モジュールと同じ階層に `*.test.ts`

### 3. ゴールデン局面回帰テスト

Phase 1で作った定跡データに対応する代表的な局面(SFEN)を10〜20個ほど選び、「この局面ではこの形・この意図と判定されるはず」という期待値をテストデータとして固定する。ロジックやデータを変更した際に、意図せず判定結果が変わっていないかを検知する。

- 位置づけ: 単体テストより「実際の対局でどう見えるか」に近い、回帰検知のための仕組み
- 作成タイミング: Phase 1でデータが揃った時点

### 4. エンジン疎通スモークテスト

やねうら王プロセスが起動し、`usi`→`usiok`→`isready`→`readyok`の応答が一定時間内に返ることだけを確認する軽量なテスト。CIやローカル環境の差異(エンジンのパスなど)で失敗しやすい部分を早期に切り分けるため、他のテストと分離しておく。

### 5. UI・E2Eテスト

MVPでは自動化しない。[PHASES.md](PHASES.md) のPhase 5で人間による通しプレイテストのみ行う。将来必要になれば、Playwrightなどの導入を別途検討する(今回は決めない)。

## CIについて

現時点ではCI(継続的インテグレーション、コミットのたびに自動でテストを走らせる仕組み)は導入しない。ソロ開発で規模も小さいため、ローカルでのフック実行と `main` マージ前のセルフレビュー([GIT_WORKFLOW.md](GIT_WORKFLOW.md))で当面代替する。必要性が高まったら(例: 複数エージェントの並行作業が常態化したら)改めて検討する。
