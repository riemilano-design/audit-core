# 自動テスト戦略

## 現状

`apps/`(本実装)向けのNode.js環境はまだ構築されていない(Phase 0本体の作業)。一方、Phase 0着手前の技術検証(`spike/`)・プロトタイプ検証(`prototypes/`)・共通ユーティリティ(`scripts/lib/`)では、それぞれ独立したNode.js環境([node:test](https://nodejs.org/api/test.html)使用)でテストが既に存在し実行できる(例: `scripts/lib/usi-coordinates.test.mjs`、`prototypes/shape-matcher/*.test.mjs`)。これらは検証用途のテストであり、`apps/` 本実装向けのテスト基盤ではない。ここでは方針とテストの種類を先に決めておき、Phase 0本体(`apps/` の作成)以降で本実装向けのテスト基盤として順次有効化する。

## テストの種類

### 1. データスキーマ検証(最優先・最も軽量)

`data/`配下の全JSONファイルが、対応する `data/schemas/*.schema.json` に準拠しているかを機械的に検証する。

- 実行方法: `scripts/validate-data.mjs`(Node.js標準機能のみで書かれた軽量バリデータ。外部ライブラリのインストールを待たずに、Node.jsさえ入っていれば動く)
- 検証内容: 必須フィールドの有無、型の一致、IDの相互参照(`intents.opening_id`が実在する`openings.id`を指しているか等、[DATA_MODEL.md](DATA_MODEL.md)の「IDの参照関係」を参照)
- 実行タイミング: `.claude/settings.json` のフックにより、`data/`配下のファイルをWrite/Editした直後に自動実行(Node未インストール時は安全にスキップされる。[CHANGE_MANAGEMENT.md](CHANGE_MANAGEMENT.md) 参照)

### 2. ロジック単体テスト

形判定・意図推定・経路計画などのロジックは、SFEN(局面)を入力として受け取り、判定結果を返す**純粋関数**として実装する方針にする(副作用を持たせない)。これにより、以下のようなテストが書きやすくなる。

```
入力: SFEN文字列(既知の局面)
期待値: 判定されるべき形・意図
```

- 使用ツール: Vitest(Phase 0でセットアップ)
- 置き場所: 各モジュールと同じ階層に `*.test.ts`

### 3. ゴールデン局面回帰テスト

Phase 1で作った定跡データに対応する代表的な局面(SFEN)を10〜20個ほど選び、「この局面ではこの形・この意図と判定されるはず」という期待値をテストデータとして固定する。ロジックやデータを変更した際に、意図せず判定結果が変わっていないかを検知する。

- 位置づけ: 単体テストより「実際の対局でどう見えるか」に近い、回帰検知のための仕組み
- 作成タイミング: Phase 1でデータが揃った時点

### 4. エンジン疎通スモークテスト

やねうら王プロセスが起動し、`usi`→`usiok`→`isready`→`readyok`の応答が一定時間内に返ることだけを確認する軽量なテスト。CIやローカル環境の差異(エンジンのパスなど)で失敗しやすい部分を早期に切り分けるため、他のテストと分離しておく。

### 5. UI・E2Eテスト

ブラウザ操作の自動化(Playwright 等)は導入しない。人間による通しプレイテストは引き続き行う。ただし、対局そのものを入力とする回帰検査は下記 6. で自動化する(ブラウザを経由せず、web が受け取る API レスポンスを検査する)。

### 6. 対局回帰(対局ハーネスと不変条件)

対局そのものを統合テストの入力にする。置き場所は `scripts/playtest/`(開発補助。本番導線に含めない)。

- **対局ハーネス**: 本番関数(`apps/server/src` の `buildStateResponseWithPlan` など)を import し、server.ts と同じ順序・引数で呼んで、一手ごとに web が受け取るのと同じ API レスポンスを JSONL に保存する。本番関数を複製しない
- **二つの実行モード**: **固定棋譜**(記録済みの自分側・相手側の手を再生する。回帰用。数値の比較に使う)と **探索**(相手は本番と同じ素のエンジン、自分側は台本・浅い読み・乱択で新しい局面列を作る。発見用。数値の比較には使わない)
- **不変条件**: JSONL に対して真偽を返す決定的な関数。LLM を使わない。`draft`(AI が自由に追加してよい。報告に出るだけで何もブロックしない)と `approved`(人間が有効化したもの。STEP の完了条件に入る)を分ける。`approved` にする操作は人間承認事項([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 5.)
- **集約報告**(`check.ts`): 検出を「型(沈黙・矛盾・断定・未説明用語・盤との不一致・陳腐化)× 発生条件」で束ね、件数・代表例・再現位置を出す。常に exit 0。「0件」は「有効な不変条件が捉える範囲では検出されない」を意味し、「異常なし」を意味しない
- **位置づけ**: 探索の出力は観測、検出は候補事象であり、既知事項・仕様・固定棋譜への登録には自動で進まない(境界は [AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 11.)
- 実行方法・出力形式は `scripts/playtest/README.md` を正とする

固定棋譜モードでも、候補手の説明の件数が実行ごとに揺れる場合がある(2026-09-11 に ply 20 で1件/2件の揺れを実測。原因は未確定)。比較に使うのは候補手の**状態**(ready / not_ready と notReadyReason)を基本とし、件数の差は単独では異常と扱わない。

## CIについて

現時点ではCI(継続的インテグレーション、コミットのたびに自動でテストを走らせる仕組み)は導入しない。ソロ開発で規模も小さいため、ローカルでのフック実行と `main` マージ前のセルフレビュー([GIT_WORKFLOW.md](GIT_WORKFLOW.md))で当面代替する。必要性が高まったら(例: 複数エージェントの並行作業が常態化したら)改めて検討する。

## 変異は両向きに回す ― **落ちたことは、門が仕事をしている証拠ではない**(2026-09-28)

**規則**

> **材料を変異させて試験が落ちても、門の各行が仕事をしている証拠にはならない。**
> **2 つの行が同じ変異で鳴るとき、片方を消しても試験は落ちない。**
> 門を測るなら **2 つの向き**を回す。
> **向き 1(材料 → 門)**: 落とすべき材料を 1 つずつ作り、**落ちるか**。
> **向き 2(門 → 試験)**: 門の「落とす行」を 1 本ずつ黙らせ(`pass` に置き換え)、**その行を消したら落ちなくなる試験があるか**。
> **向き 2 で落ちなくなる試験が無い行は、覆われていない** ― その行は消しても誰も気づかない。

**向き 2 の一覧は、手で並べない。AST で機械に数えさせる。**

> 手で並べた一覧は「**代表 1 本**」になる。**同じ関数の中に落とす行が 4 本並んでいると、目は先頭 1 本だけを拾う。**
> 2026-09-28 の実測: 手で並べた一覧は 15 本、**AST で数えたら 19 本**で、**落としていた 5 本は 1 本も覆われていなかった**
> (5 本すべてが「同じ関数の中の 2 本目以降」だった)。

**実測(`report-pdf/check_structure.py` と `check_structure_test.py`。STEP CUSTOMER-EXIT ④)**

向き 1 を 7 本(司令塔が指定)通した時点では **7 本とも落ちた**。向き 2 を回して、**2 行が「消しても試験が落ちない」**と出た:

| 覆われていなかった行 | なぜ隠れていたか |
|---|---|
| 本人用と見本用の**ページ数の差** | 変異「対応表を落とす/残す」が**対応表の在り処の行も同時に鳴らす**ので、差の行を消しても試験は落ち続けた |
| **`pos` の件数**(正本は 2 件) | 変異「盤を 1 つ抜く」が**宣言と差し込みの不一致の行も同時に鳴らす**ので同じ |

**切り分けの作り方**: **落としたい行だけが鳴る材料**を作る(差だけを崩す = ページ数の差を 2 にしつつ対応表の在り処は正しいまま /
件数だけを崩す = 盤を 3 つ宣言し索引の差し込み回数も 3 に揃える)。
**それが作れないときは、`assertIn` でその行の文言を名指しする** ― 他の行が同時に鳴っても、
**その行を黙らせれば文言が消えるので試験は落ちる**(例: 見本用のページ数の上限は、本人用の上限と同時にしか鳴らせない)。

**最終(2026-09-28)**: 対象 **23 本**(`problems.append` 22 本 + 空白落とし 1 本)・**覆われていない対象 0 本**・試験 27 本・1.57 秒。
校正の道具は `scratchpad/calibrate.py`(門のファイルは `finally` で戻し、**sha256 で照合**する)。

## python の変異試験とバイトコード ― Apple python の `pycache_prefix`(2026-09-29)

**観測(P-122)**: 変異試験の道具が「この変異は誰も捕まえない」という**偽の緑**を 1 回返した(別の道具で同じ変異を回すと 14 本が赤)。その回で何が起きたかは**測れなかった**(証拠は `scratchpad/pyc_evidence/`、変異前のソースに対応する pyc しか残っていなかった)。

**機構(司令塔・自動化レーンがそれぞれ再現)**: この Mac の `python3`(`/Library/Developer/CommandLineTools/usr/bin/python3` 3.9.6)は `sys.pycache_prefix = ~/Library/Caches/com.apple.python` で、**pyc をソースの隣の `__pycache__` ではなくそこへ絶対パスごと書く**。だから `find -name __pycache__` は常に 0 件で、「キャッシュは無い」に見える。pyc の有効性は既定で**ソースの mtime(秒)と長さ**だけで判定されるので、**同じ長さ・同じ mtime の変異は古い pyc に隠れる**。`-B` は書くのを止めるだけで**読むのは止めない**。

```
printf 'X=1\n' > m.py; python3 -c 'import m; print(m.X)'        # 1
cp -p m.py m.bak; printf 'X=2\n' > m.py; touch -r m.bak m.py    # 同じ長さ・同じ mtime に変異
python3 -c 'import m; print(m.X)'                                # 1 ← 隠れる
python3 -B -c 'import m; print(m.X)'                             # 1 ← -B でも隠れる
python3 -X pycache_prefix=$(mktemp -d) -c 'import m; print(m.X)' # 2 ← 効く
```

当たりやすい変異: `!=`→`==`、`>=`→`> `、数字 1 桁の差し替え、同じ文字数の日本語(「形勢の流れ」→「知らない節」は 5 文字・15 バイトで同じ)。写しを `cp -p`・`rsync -a`・`shutil.copytree` で作ると mtime が保たれるので特に危ない。

**規則**
1. **主**: 変異の一本目は**陽性対照**(捕まると分かっている変異)。鳴らなければ、その回の変異の結果は**全部捨てる**。原因が何であっても効く。
2. **副**: 変異の写しは `python3 -X pycache_prefix=<その回だけの新しい dir>`(または `PYTHONPYCACHEPREFIX`)で走らせる。`__pycache__` を消すのと `-B` では効かない。
3. 「変異なしで rc=0」の校正はこの穴を**捕まえない**(古い pyc でも同じ内容なら緑)。
4. **「見つからなかった」を「無い」と読まない**(探した場所を書く)。
