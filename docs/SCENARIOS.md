# 対局シナリオ(将来設計・未実装)

## 目的

現在のMVPは「AI(居飛車側)がどう指してくるか」を制御していない。しかし将来的には、練習したいテーマに応じて AI の序盤の指し方を選べるようにしたい。

例:

- 標準的な居飛車
- 棒銀
- 斜め棒銀
- 早仕掛け

これらを「対局シナリオ」として選択・制御できるようにすることで、「今日は棒銀対策を練習する」といった目的別の練習対局が可能になる。

## 現段階での方針

似ているが別物の2つを分けて扱う。**片方は行う方針へ変更され、もう片方は引き続き見送り中である。**

| | 内容 | 現在の方針 |
|---|---|---|
| **相手AIが狙いを持って指す** | 相手側が複数の戦法・狙いから毎局1つを選んで指す。**選んだものはユーザーに開示しない**(ユーザーは対局の経過から認識しにいく) | 人間の判断により**行う方針へ変更された**([PHASES.md](PHASES.md) の Phase 4「その後の変更」)。**MVPで相手AIが選択候補として使う範囲**は、STEP δ で司令塔が提案し人間が追認した解釈により `data/intents/` の居飛車系3件(棒銀・斜め棒銀・早仕掛け)に限定するが、これは相手AIの選択範囲についてのものであり、記述的知識の追加や将来の戦法追加を禁じるものではない([DATA_MODEL.md](DATA_MODEL.md) の Kind 1)。選択方法(毎局ランダムか固定か)と非開示の具体的な扱いは、今後のSTEPで確定する |
| **ユーザーが練習テーマとして相手の作戦を選ぶ** | 「今日は棒銀対策を練習する」のような目的別の練習対局(本文書「目的」の想定) | **引き続き見送り中である。** |

実装する場合の見通しを立てるために、データ構造の受け皿だけを `data/schemas/openings.schema.json` の `scenario` フィールドとして用意してある。[PHASES.md](PHASES.md) の Phase 4 で「見送り・別途仕様確定後に改めて検討する」と判断し、`data/openings/*.json` の `scenario` フィールドは `null` のまま維持している。この受け皿の扱いは、上記の方針変更によっては変えない。

## 想定する設計の方向性

### 認識用データと制御用データを分ける

似ているが目的が違う2種類のデータを混同しないこと。

| | 目的 | 使う場面 | 対応スキーマ |
|---|---|---|---|
| **認識(recognition)** | 相手の指し手から「今何をしているか」を判定する | 対局中、常に動く | `intents.schema.json` の `recognition_pattern` |
| **制御(control)** | AI自身に特定の作戦を指させる | 練習シナリオを選んだとき | `openings.schema.json` の `scenario`(将来) |

同じ「棒銀」でも、認識用データ(棒銀を検知する手がかり)と制御用データ(AIに棒銀を指させる手順)は別物として管理する。片方を変えてももう片方が壊れない設計にする。**この設計方針は、相手AIに狙いを持たせる方針へ変更されたあとも維持する。**

なお認識側は、戦型・狙い・陣形を「現時点での仮説」として扱う([DATA_MODEL.md](DATA_MODEL.md))。相手AIがどの狙いを選んでいるかを認識側の入力にしない(選んだものをユーザーに開示しないため、認識は指し手の観測だけから行う)。

**`recognition_pattern` の検証時利用**: `recognition_pattern` は、制御データの検証時に**テスト・オラクル**(制御手順が意図した狙いを盤上に実現できたかの照合基準)としてのみ使用してよい。**実行時のAI制御手順の生成・選択には絶対に使用しない。** 手順は [KIND3_VERIFICATION.md](KIND3_VERIFICATION.md) Phase A-3。

### 制御方式の候補(未決定)

- 序盤の数手を `scenario` に定義した手順で強制進行させ、そこから先はエンジンに自由に指させる
- エンジンの候補手の中から、シナリオの傾向に近い手を優先的に選ばせる(エンジンの読み自体は変えない)

どちらを採るか、あるいは組み合わせるかは、本実装に着手する判断が出た時点で改めて検討する。ここで先に決め打ちしない。

### 見送りの背景(Phase 4 判断時点)

- MVPの「四間飛車 vs 居飛車」がそもそもまだ動いていない段階で、複数シナリオの制御を作ると検証すべき組み合わせが増えすぎる
- シナリオデータも将棋知識の一種であり、[../CLAUDE.md](../CLAUDE.md) のルール4番(大量生成の禁止)に抵触しやすい
- Phase 1〜3 を通じて「相手が定跡から外れたときにどう振る舞うべきか」の知見が溜まってから設計した方が、手戻りが少ない
