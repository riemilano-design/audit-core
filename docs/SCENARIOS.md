# 対局シナリオ(開発・検証専用の機構)

## 目的(当初の構想。**Phase 7 の再定義により、本番機能としては撤回された**)

当初はこう構想していた ―「現在のMVPは『AI(居飛車側)がどう指してくるか』を制御していない。しかし将来的には、練習したいテーマに応じて AI の序盤の指し方を選べるようにしたい。」

**この構想は本番機能としては採らない。** 練習テーマとして相手の作戦を選ばせることは、[../CLAUDE.md](../CLAUDE.md) の「絶対的な上位原則」が禁じる「戦型に合わせてユーザーを誘導する」に当たる。以下は当初の構想の記述であり、**開発・検証用の制御機構がどういう発想から生まれたかの履歴**として残す。

例:

- 標準的な居飛車
- 棒銀
- 斜め棒銀
- 早仕掛け

これらを「対局シナリオ」として選択・制御できるようにすることで、「今日は棒銀対策を練習する」といった目的別の練習対局が可能になる。**(← 当初の構想。本番機能としては採らない)**

## 現段階での方針

> **【最重要】この文書が扱う「対局シナリオ」は、開発・検証専用の機構である。本番の基本体験には使わない。**
>
> [../CLAUDE.md](../CLAUDE.md) の「絶対的な上位原則」により、本番の対局は**何もない初期局面から始め、戦型を事前に決めない**。固定された狙い・手順を相手AIに最初から与えることは、本番では行わない。既存の制御機構(`data/openings` の `scenario`・`?scenario=`・`BOH_GIN_SCRIPT`・`HAYAJIKAKE_SCRIPT`)は**開発・検証専用として残すが、本番の基本設計として拡張しない**。
>
> 以下の記述は、この位置づけの下で読むこと。**変更前の記述は履歴として残す。**

似ていたが別物の2つを分けて扱ってきた。**現在はいずれも本番の基本体験としては行わない。**

| | 内容 | 現在の方針 |
|---|---|---|
| **相手AIが狙いを持って指す** | 相手側が複数の戦法・狙いから毎局1つを選んで指す。**選んだものはユーザーに開示しない**(ユーザーは対局の経過から認識しにいく) | **本番では行わない**(上記の最重要注記)。開発・検証用の機構としてのみ残す。以下は変更前の記述の履歴である。かつては人間の判断により**行う方針へ変更された**([PHASES.md](PHASES.md) の Phase 4「その後の変更」)。**MVPで相手AIが選択候補として使う範囲**は、STEP δ で司令塔が提案し人間が追認した解釈により `data/intents/` の居飛車系3件(棒銀・斜め棒銀・早仕掛け)に限定するが、これは相手AIの選択範囲についてのものであり、記述的知識の追加や将来の戦法追加を禁じるものではない([DATA_MODEL.md](DATA_MODEL.md) の Kind 1)。**選択方法・非開示の具体的な扱いは STEP ζ-4c-1 で確定した**: 毎局 seed 付きランダムで、承認済み(`verification_status: human_approved`)variant から重み付けなしに均等に1件を選ぶ。seed と選択結果は公開しない(非開示は [ARCHITECTURE.md](ARCHITECTURE.md) 6. の公開境界と `?scenario=` の開発モード限定で実現する) |
| **ユーザーが練習テーマとして相手の作戦を選ぶ** | 「今日は棒銀対策を練習する」のような目的別の練習対局(本文書「目的」の想定) | **引き続き見送り中であり、新方針では復活させない。** 戦型に合わせてユーザーを誘導する構造にあたるため |

実装する場合の見通しを立てるために、データ構造の受け皿だけを `data/schemas/openings.schema.json` の `scenario` フィールドとして用意してある。[PHASES.md](PHASES.md) の Phase 4 で「見送り・別途仕様確定後に改めて検討する」と判断し、`data/openings/*.json` の `scenario` フィールドは `null` のまま維持している。この受け皿の扱いは、上記の方針変更によっては変えない。その後、この受け皿の構造は人間の承認を経て正式に定義された([DATA_MODEL.md](DATA_MODEL.md))。ただし `data/openings/*.json` の `scenario` は引き続き `null` のままであり、値の投入は [KIND3_VERIFICATION.md](KIND3_VERIFICATION.md) の検証と Phase F の人間による最終採用判断を経てから行う。

## 想定する設計の方向性

### 認識用データと制御用データを分ける

似ているが目的が違う2種類のデータを混同しないこと。

| | 目的 | 使う場面 | 対応スキーマ |
|---|---|---|---|
| **認識(recognition)** | 相手の指し手から「今何をしているか」を判定する | 対局中、常に動く | `intents.schema.json` の `recognition_pattern` |
| **制御(control)** | AI自身に特定の作戦を指させる | **開発・検証時のみ**(本番では使わない) | `openings.schema.json` の `scenario`(**スキーマは STEP ζ-4b で定義済み**。値の投入は未了で `null` のまま) |

同じ「棒銀」でも、認識用データ(棒銀を検知する手がかり)と制御用データ(AIに棒銀を指させる手順)は別物として管理する。片方を変えてももう片方が壊れない設計にする。**この設計方針は、Phase 7 の再定義(本番では相手AIに固定の狙いを与えない)のあとも維持する。** 認識用データは本番で使い続け、制御用データは開発・検証専用になる。分離しているからこそ、この位置づけの違いを保てる。

なお認識側は、戦型・狙い・陣形を「現時点での仮説」として扱う([DATA_MODEL.md](DATA_MODEL.md))。**開発・検証用のシナリオモードを使ったときも**、相手AIがどの狙いを選んでいるかを認識側の入力にしない(認識は指し手の観測だけから行う)。**本番では相手AIが固定の狙いを持たないため、そもそも入力になり得るものが存在しない。**

**`recognition_pattern` の検証時利用**: `recognition_pattern` は、制御データの検証時に**テスト・オラクル**(制御手順が意図した狙いを盤上に実現できたかの照合基準)としてのみ使用してよい。**実行時のAI制御手順の生成・選択には絶対に使用しない。** 手順は [KIND3_VERIFICATION.md](KIND3_VERIFICATION.md) Phase A-3。

### 制御方式(人間の判断により確定)

- 序盤の数手を `scenario` に定義した手順で強制進行させ、そこから先はエンジンに自由に指させる
- エンジンの候補手の中から、シナリオの傾向に近い手を優先的に選ばせる(エンジンの読み自体は変えない)

**人間の判断により、上の1つ目(序盤の数手を `scenario` に定義した手順で強制進行させ、そこから先はエンジンに自由に指させる)を採ることが確定した。** 2つ目は採らない(候補としての記述は履歴として残す)。`scenario` のスキーマ構造は [DATA_MODEL.md](DATA_MODEL.md) と `data/schemas/openings.schema.json` に定義済みである。**毎局の選択方法・ランダム性の有無も STEP ζ-4c-1 で確定した**(毎局 seed 付きランダムで、承認済み variant から重み付けなしに均等に1件を選ぶ。seed と選択結果は非公開)。**手順そのものの内容(具体的な `moves`)は、引き続き未確定である**(今後のSTEPで人間の承認を経て決める)。

### 見送りの背景(Phase 4 判断時点)

- MVPの「四間飛車 vs 居飛車」がそもそもまだ動いていない段階で、複数シナリオの制御を作ると検証すべき組み合わせが増えすぎる
- シナリオデータも将棋知識の一種であり、[../CLAUDE.md](../CLAUDE.md) のルール4番(大量生成の禁止)に抵触しやすい
- Phase 1〜3 を通じて「相手が定跡から外れたときにどう振る舞うべきか」の知見が溜まってから設計した方が、手戻りが少ない
