## 3. 唯一の変更: member 付き context を `population` の値として読む

変更を 2 種類に分け、**結果でも別々に数える**。

### 3.1 A. 構造の規則(会社に依存しない。Adapter の本体)

1. context の `explicitMember` を読み、Claim の `population` 修飾の値として扱う(2 本目は member 付き context を一律に外していた。ここだけを変える)。
2. 文の母集団(どの事業の数か)の決め方:
   - 文の中に登録簿の事業名が**ちょうど 1 つ**含まれる → その事業の member。
   - 文の中に無い → **同じ段落の中で、さかのぼって 5 文以内**に「事業名がちょうど 1 つ含まれる文」があれば、その事業の member を引き継ぐ(`member_source: carried`)。段落は凍結した文の切り方で改行になる境界。段落をまたいで引き継がない。
   - 文の中に 2 つ以上の事業名 → 文自身では決めず、引き継ぎもしない。その文の Claim は `ambiguous(member)` で**未束縛**にする(連結の総額と比べない)。
   - 事業名が文にも引き継ぎ元にも無い → 2 本目と同じ(member 無しの context だけ。**挙動は byte 一致**)。
3. member が決まった Claim は、**その member を持つ context の fact だけ**を候補にする(member 無しの context と**合わせない**。候補の母集団を置き換える)。要素の選び方(完全一致 → 部分一致)・期間の選び方・丸め・符号・比の式は凍結のまま。
4. 派生(前期比)の Claim は、当期と前期の**両方**の context が同じ member を持つことを要求する。片方しか無ければ未束縛(`no_prior_member_context`)。
5. 主語なしの Claim(`value_only`)で member が決まっている場合も、候補は member の fact だけ。member が決まっていなければ 2 本目と同じ。

### 3.2 B. 対応の登録(会社ごと。Adapter の登録簿)

事業名 ↔ member 要素名の対応。**出どころを計器にする。**

- **Run L(主。封じた予測はこちらに掛かる)**: ZIP に入っている会社拡張の label linkbase(`*_lab.xml`)から member の日本語ラベルを機械で引き、NFKC 正規化したラベルが MD&A の文の中に現れる member だけを登録簿に入れる。**人は 1 行も書かない。**
- **Run R(従。探索)**: Run L で当たらなかった member に人が対応を書き足して回す。Run B と同じく予測の検証には使わない。Run L との差が「登録簿の手書きが要る分」。

**分母の定義(結果を見て変えない)**: 「member 候補として実際に評価対象となった member 数」= 当期または前期の連結の Duration context に現れる `explicitMember` の**異なり数**(全社・調整額・消去などの member も含む)。

## 4. 誤りの増加経路(先に固定する仮説)

member を束縛に入れると、Claim ごとの候補の fact が変わる。2 本目の GROUNDED 26 件のうち **5 件が `value_only`**(主語なしで値だけが一意に当たった: **N052・N065・N073・N080・N081**)。

仮説(事前に固定):
- member の引き継ぎ(§3.1 の 2)が広すぎると、連結の総額を述べた文の Claim に member が付き、連結の fact と比べられなくなる → 新しい VALUE_MISMATCH または未束縛が**増える**経路。
- `value_only` は主語が無いので、候補の母集団が変わると「別の fact に偶然一致する」「一意でなくなる(ambiguous 化)」が起きうる。

**false pass の定義**: 「2 本目では `value_only` 等により GROUNDED だった Claim が、member 束縛後の正準の証拠(要素名・期間・member の 3 つ揃い)との再照合によって、実際には誤って GROUNDED だったと判明するケース」。

結果側の約束: **member 導入によって新たに GROUNDED になった全件**と、**`value_only` 5 件の変化**を、1 件ずつ人が読んで表にする(ID・文・束縛先 context・member・値)。

## 5. byte freeze gate(実装後・計測前の必須の門)

- `xbrl_probe3.py` を**別ファイル**として作る。`xbrl_probe.py` は変更しない。
- member 束縛を **OFF** にした状態(環境変数 `PROBE_MEMBER=0`)で 2 本目の JSON(sha256 `73f413f228f62ec9528e42bd866cfd162e4336c94206a9e93f9d48f412752c20`)を **byte 一致**で再現する。`shasum -a 256` の一致を結果文書に貼る。
- **byte 一致しなければ 3 本目の計測を開始してはいけない。** 一致するまで差分を縮める。縮められなければ 3 本目は無効と記録し、人間の判断を仰ぐ。
- 2 本目との差分を次に限定する:
  - context の選別(§3.1)
  - member 対応表の読み込み(§3.2。label linkbase の読み、Run R の登録簿ファイルの読み)
  - 切替の配管(`PROBE_MEMBER`・出力先 `probe3L_S100Z4B6.json` / `probe3R_S100Z4B6.json`・保管済み ZIP のローカル読み)。配管が OFF 時の出力を変えないことは byte 一致の門で示す
- 次は**絶対に変更しない**: P-1〜P-7 / 語彙 73 / 正規表現 / 既存の Claim 抽出規則 / Core / 2 本目の `xbrl_probe.py`。

## 7. 外れたときの読み方

- セグメントの GROUNDED が司令塔の下限 5 を下回る: 要素名が連結と違う(`…SegmentInformation` 系)か、前期の member context が無いか、ラベルが文の事業名と一致しない。どれかを XP3 に書く。**語彙を足して直さない**(足したくなったら 4 本目の予測へ)。
- 人間の予測(9〜15 / 18)と司令塔の予測(5〜10 / 20)のどちらが近いか: セグメント利益 10 件の読みの差。司令塔が外れて 10 件が GROUNDED になるなら、主語の取り方が予測と違う(要調査)。
- セグメント以外の 12 件が動く: 引き継ぎの規則が連結の文に漏れた。構造の規則の欠陥として記録し、規則を狭める変更は 4 本目へ。
- false pass が 2 件以上: `value_only` を GROUNDED に数える設計自体を v0.2 の論点に戻す。
- ラベルだけで当たる member が半分未満: 対応表は語彙と同じ「会社ごとに育つ登録簿」。半分以上: データ自身が持つ鍵で、会社をまたいで移る部分がある。
- 層・form・modifier・scheme のどれかが増える: 増えたものを Core に入れずに記録する(2 本目と同じ)。
