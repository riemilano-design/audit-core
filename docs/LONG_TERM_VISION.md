# 長期構想

## この文書の位置づけ

このプロジェクトが**最終的にどういうシステムになろうとしているのか**を記録する文書である。人間(プロジェクトの最終意思決定者)が決定したものだけを書く。

**この文書に書かれた内容は、MVPの完成条件ではない。** MVPの完成イメージと完成の判定基準は [PROJECT_VISION.md](PROJECT_VISION.md) が正本であり、両者が食い違った場合は [PROJECT_VISION.md](PROJECT_VISION.md) を優先する。本文書に書かれていることを理由に、MVPのスコープを先回りして広げてはならない([PROJECT_VISION.md](PROJECT_VISION.md) 5. と同じ原則)。

**本文書は未検証の仮説を含む。** 「7. 検証したいこと」に挙げた項目は、実際のユーザーで確かめるまで正しさが確定していない。仮説が否定された場合、この文書を書き換えるのが正しい対応である。

AIエージェントはこの文書を根拠に判断してよく、新しい案を自由に提案してよい。ただし、この文書の内容を人間の承認なしに変更・確定してはならない([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 5.)。

---

## 1. 中心的な賭け

> **将棋エンジンは「正解」を知っているが、人間が「なぜその手を選んだのか」は知らない。**
> **エンジンの「正解を出す能力」と、LLMの「説明する能力」の間に、独自の「人間の将棋判断を構造化する層」を作る。**

既存のAI棋譜解析の典型的な流れは次のとおりである。

```
棋譜 → エンジン → 勝率・悪手 → 解説
```

このプロジェクトが目指すのは次の流れである。

```
棋譜 → 局面構造(Shape) → 目的(Intent) → 判断のズレ → 個人傾向 → コーチング → 練習 → 改善
```

「AIで棋譜を分析する」という土俵では勝負しない。狙うのは **「そのユーザーが何を考えてその手を選んだのかを、局面構造と行動履歴から構造化する」** という領域である。

これは [PROJECT_VISION.md](PROJECT_VISION.md) 1.(核心的な強み)と矛盾しない。同文書が「次に何を考えるべきかを教える」と述べているものを、より長い時間軸へ延長したものである。

## 2. 7つの層

| 層 | 問い | 現状 |
|---|---|---|
| ① Shape | 今どんな形なのか | 実装済み(Phase 1・2) |
| ② 経路 | その形を作るには何をすればよいか | 実装済み(Phase 6 Unit 1) |
| ③ Intent | この手は何のためか | **相手の意図**は実装済み(Phase 1)。**ユーザー自身の目的**は未実装 |
| ④ 判断 | その目的は、この局面で適切か | 未実装 |
| ⑤ 結果 | 判断の結果、局面・形はどう変わったか | 実装済み(Phase 6 Unit 2・3) |
| ⑥ 蓄積 | 同じことを何度繰り返しているか | 未実装。MVPに含めない |
| ⑦ コーチング | 次に練習すべきことは何か | 未実装。MVPに含めない |

LLMが登場するのは⑦だけである。①〜⑥はすべて決定的なロジックとデータで組み立て、LLMには**確定した事実の言い換え**だけをさせる([CLAUDE.md](../CLAUDE.md) ルール5)。この分業は長期構想でも変えない。

## 3. Intentは「推定」せず「宣言」してもらう

### なぜ推定しないのか

▲5九銀という一手は、「囲いを進めたい」「相手の攻めが怖い」「他に思いつかなかった」の**どれとも整合する**。一手からその人の意図は決まらない。手からユーザーの心の状態を言い当てる設計は、[CLAUDE.md](../CLAUDE.md) ルール6(断定できないことは断定しない)に正面から反する。

そこで、**指す前に本人に目的を選んでもらう**。

```
この手は何のため?
  ○ 囲いを進める
  ○ 相手の攻めに備える
  ○ 攻める
  ○ 分からない
```

これにより「あなたは守りたかったのでしょう」という心理推測が消え、**本人がそう申告したという事実**だけが残る。

なお、ここで主軸から外すのは「**ユーザー自身の目的を手から推定すること**」である。**相手の意図の推定**(教育用データパイプラインの③④、`intentDetector.ts`)は従来どおり継続する。

### 宣言を「真の意図」とみなさない

人間は自分の思考を正確に説明できるとは限らない。したがって宣言をそのまま真実として扱わず、次の要素を並べて保持する。

| 要素 | 内容 | 取得元 |
|---|---|---|
| `DeclaredIntent` | 本人が申告した目的 | ユーザーの選択 |
| `ObservedAction` | 実際に指した手 | 指し手そのもの |
| `PositionRequirement` | 局面から観測できる事実 | 既存の判定ロジック(下記 4. の制約に従う) |
| `EngineOutcome` | 結果 | エンジンの参考評価(安全確認の範囲内) |
| `Consistency` | 上記4つの整合度 | 上記から機械的に算出する。**何をもって「整合」とするかは未確定**(下記 8.) |

この構造の要点は、**「攻める」と宣言したのに実際には守りの手を指した**というズレを、心理を推測せずに**思考と行動の乖離という事実**として扱えることである。

### 「分からない」を失敗として扱わない

「分からない」は選択肢として必ず残す。これを失敗扱いすると、ユーザーは正解らしい選択肢を選ぶようになり、蓄積されるデータが濁る。

「分からない」が選ばれた局面そのものが重要な情報である。将来、どの種類の局面で目的を決められないのかを見る材料になる。

## 4. `PositionRequirement` に課す制約

④「判断」を成立させるには「この局面が何を要求しているか」が要る。しかしその作り方には制約がある。

- **エンジンの評価値を根拠に「攻めた方が有利」とは述べない。** [PROJECT_VISION.md](PROJECT_VISION.md) 4.3 が禁じている
- 「この局面は攻めるべき」を新しいルールとして作ることは、**新しい将棋知識の追加**にあたり、人間のレビューが必須である([CLAUDE.md](../CLAUDE.md) ルール4)

したがって `PositionRequirement` は「要求」ではなく **観測可能な事実の束**に留める、というのが上記の制約から導かれる方向である(**本セッションでの提案であり、確定した設計ではない**。正式な確定は実装着手時に人間の確認を経る)。

> 「あなたは『相手の攻めに備える』と宣言しました。この局面では、相手の攻めの形はまだ判定できていません(棒銀・斜め棒銀・早仕掛けのいずれにも一致していません)。」

この案では、断定せず、エンジン評価も使わず、既存の判定結果をそのまま並べる。**ズレを判定するのはアプリではなくユーザー自身**である。これは [PROJECT_VISION.md](PROJECT_VISION.md) 1.「答えではなく考え方」に忠実な形でもある。

## 5. 目的を聞く頻度

1局は60〜100手ある。毎手聞けばユーザーは適当に選ぶようになり、宣言データがノイズになる。したがって**毎手は聞かない**。

一方、**どの局面で聞くか・1局あたり何回聞くかは未確定である**(下記 8.)。本セッションでは次の案が出ているが、**これは提案であって確定した設計ではない**。実装に着手する時点で人間の確認を経る。

> 新しい判定ロジックを作らず、既存モジュールが「分岐点」を検出したときだけ聞く。
>
> - `planChangeDetector.ts` / `planChangeReason.ts` — 計画が変わった
> - `moveOutcomeDetector.ts` の `route_lost` / `preparation_required` — 道のりが続かなくなった
> - `nextConsiderationDetector.ts` — 指せる道のりが複数ある
>
> 目安は1局あたり5〜10回。

## 6. MVPに含めるもの・含めないもの

| 機能 | MVP |
|---|---|
| 対局(四間飛車 vs 居飛車) | 含める |
| Shape(形の判定) | 含める |
| 形への経路と候補手 | 含める |
| 相手の意図の推定(パイプライン③④) | 含める(実装済み) |
| **指す前のIntent申告(最小の実験機能)** | **含める** |
| ユーザー自身のIntentを手から推定する | 含めない |
| 毎手のLLM解説 | 含めない |
| 複数局を横断した個人傾向の分析 | 含めない |
| 個人の弱点モデル | 含めない |
| 個人専用の練習局面の自動生成 | 含めない |

**「指す前のIntent申告」はMVPの中心機能ではなく、最小の実験機能として入れる。** 中心はあくまで [PROJECT_VISION.md](PROJECT_VISION.md) 2.・3. が定める「対局中に理解し、自分で候補手を選択できる」ことである。

⑥⑦(蓄積・コーチング)を含めないことには実務上の意味がある。中核仮説(下記 7.)は、ユーザーモデルも永続化もLLM層も作らずに検証できる。ここを曖昧にすると、検証のために先に基盤を作ることになり、順序が逆になる。

## 7. 検証したいこと

MVPで確かめたいのは「Intent推定の精度」ではない。**指す前に目的を意識させること自体が、将棋学習として成立するか**である。

1. 面倒ではないか
2. 目的を考えることで指し手が変わるか
3. 目的と実際の手にズレが生じるか
4. ユーザー自身が「これは役に立つ」と感じるか

「最初は面倒だったが、目的を考えてから指す癖がついた」と言われれば、それはこのプロジェクトの思想そのものが機能したということである。「毎回聞かれるのが鬱陶しい」なら、設計を変える。

ここで手応えが出た場合に限り、③④の層を本格的に育てる。

## 8. まだ決まっていないこと

- Intentの選択肢の具体的な文言と数(4択でよいか、局面によって変えるか)
- **目的を聞く局面と頻度**(5. の分岐点案は本セッションでの提案にとどまる)
- **`Consistency` の算出方法**(何をもって「整合」とするか)。あわせて、それが [AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 5. の「評価・推奨ロジックの導入」にあたらないかの確認
- 「指す前のIntent申告」をどのPhaseで実装するか(Phase の割り当ては未確定)
- `PositionRequirement` の具体的な作り方(4. の制約を満たす範囲で何をどこまで出すか)
- 宣言データの保存先と保存期間(MVPでは1局内で完結するため、永続化の要否そのものが未決)
- 検証の規模と進め方(まず3〜5人で体験だけを確かめ、手応えがあれば人数を増やす、という順序が案として出ている)
