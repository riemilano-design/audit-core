## 1. 最終目的(人間の提示)

これは「将棋アプリを作ってユーザーから月額課金するプロジェクト」ではない。

> **将棋棋譜から、プレイヤー固有の判断・失敗パターンを抽出できる解析エンジンを開発し、それを企業へ API・OEM・ライセンス・技術提供などの形で提供する。**

Web アプリは商品そのものではなく、**解析エンジンの Reference Implementation(実証用・デモ用 UI)**と位置づける。

**既存の将棋 AI との違い**: 既存は「この局面で何を指すべきか」。本エンジンは「このプレイヤーは、どのような状況で、どのような失敗を繰り返しているか」。商品価値の中心は「最善手を当てる能力」ではなく**「個人の繰り返しパターンを発見する能力」**。

```
従来型:   棋譜 → エンジン解析 → 悪手 → 最善手
本エンジン: 棋譜 → エンジン解析 → 盤上の事実 → 物理的な変化 → Failure Candidate
          → 複数局で集約 → Personal Pattern → 説明・練習
```

## 2. 核心となる階層(人間の提示。既存の 3 層との対応は司令塔)

| 階層 | 内容 | 例 | 既存の設計との対応 |
|---|---|---|---|
| Observation | 計算機が観測した事実 | 評価値・王手・詰み・捕獲・利き・退路・形・PV | A 層(`replay.ts` の JSONL、`rules/`・`analysis/`) |
| Physical Event | 盤上で実際に起きた変化 | 優勢だった局面から自玉周辺の安全性が低下した | B 層の下位(急落候補・窓の中の王手) |
| Failure Candidate | それが失敗パターンである可能性 | 優勢局面における自玉危険化 | B 層の Failure Event(死因①、draft) |
| Personal Pattern | 複数棋譜で繰り返し確認されたパターン | 30 局中 6 局で、優勢時に自玉の安全性が低下した後、短手数で王手 | ロードマップ D3・D4(集計、発症条件別) |
| Interpretation | 人間・AI による意味づけ | 攻めを継続することを優先している可能性 | C 層(急がない。LLM は言い換えだけ) |
| Prescription | 次にどう考えるか | 優勢になったら、攻めを続ける前に自玉の安全性を確認する | D5(練習問題・③へ戻す) |

**この階層が B2B で重要な理由(人間の提示)**: 「AI が勝手に診断している」状態を避けられる。「あなたは攻め急ぎ型です」と言わせるだけなら LLM で足りるので、企業は「ChatGPT に棋譜を渡せばいいのでは」と言う。**確定事実 → 物理イベント → 失敗候補 → 統計的反復 → 解釈**と分けることで、**どの結論がどのデータから導かれたのかを追跡できる**。これは B2B の品質特性である。**事実を LLM に決めさせない**(CLAUDE.md ルール 5)という設計思想は、そのまま売り物の一部になる。

## 3. 企業側から突かれる 3 つの問題(人間の提示)と、対応

| 問題 | 対応 |
|---|---|
| **① 解析コスト**(「1 万局でいくら」) | **二段階解析**を検証する: 第 1 段 Light Scan(評価変化などから候補局面を抽出)→ 第 2 段 Deep Analysis(候補局面だけ PV・詳細)。**1 局あたりの解析時間・CPU コスト・1,000 局と 10,000 局の処理能力を実測**し、「安いはず」ではなく数字で説明できる状態にする(司令塔: ロードマップの **D-COST**。エンジンと道具は揃っているので今すぐ安くできる) |
| **② 戦型の違いによる統計ノイズ** | 「5八金を指した」のような駒配置ではなく、**戦型が変わっても成立する状況の構造**(自玉の退路・玉への攻撃・大駒の可動域・攻めと受けの均衡・評価値・相手の反撃可能性)で定義する。**司令塔の注意**: 特徴 1 つが判断的知識で人間承認を要する(ルール 4)。**まず死因① 1 種類で通し、特徴を増やすのは実棋譜で誤検出を見てから** |
| **③ 「内製できるのでは」** | 売るのはコードではなく、**将棋ルール処理 + エンジン解析 + 盤面物理イベント + Failure Candidate モデル + Personal Pattern 集約 + 説明可能な Evidence + テスト/Invariant + 実データによる検証**というパイプライン全体。**「1,000 件テスト済み」はまだ売り文句にしない**(人間の提示 8.)。本当の防壁は「実装 → テスト → 実棋譜 → 誤検出データ → 改善 → Failure Pattern 知識 → さらに実棋譜」の循環が形成されたとき |

## 4. 司令塔の評価と、構想に足した点(2026-09-15)

賛成する。既存の技術構想(3 層、Failure Event、先に書いた「面白い」基準、D0〜D5、B2C 基盤を触らない判断)と矛盾せず、Gate 1〜3 は D0〜D4 とほぼ一対一である。そのうえで次を足した(人間が「反映して」で承認)。

1. **最初の買い手はプラットフォームでなく教育側**。国内の買い手候補は多く見て 5〜10 社。将棋ウォーズの HEROZ は自社が AI 企業で、③「内製」の壁が最も高い。先に検証する相手は**将棋教室・指導者・通信講座・講師系の発信者**: 内製する力が無い / 生徒ごとの弱点診断という直接の需要がある / 商品形態を**「コーチが解釈するための支援ツール」**にでき、「AI が診断する」と言わずに済む(ルール 5 と整合)。
2. **堀は実データの検証資産**。誤検出を人が確かめた実棋譜の蓄積と、人間承認済みの失敗パターン知識が、唯一真似しにくいもの。それを集める最も安い経路は**「棋譜ファイルを上げると診断が返るページ」(同意つき)**であり、Web は単なるデモでなくデータ取得の入口。**ただし作るのは Gate 3 の後**。
3. **プラットフォーム提携はデータ権利の問題を解く手段でもある**。将棋ウォーズ規約 6 条(棋譜の著作権は運営)・81Dojo 6.2(営利は事前承認)は個人向けでは壁だが、提携なら相手が権利を持つ([STEP_D0-KIFU_PLAN_2026-09-14.md](STEP_D0-KIFU_PLAN_2026-09-14.md) 5.)。営業の文面に入れる。
4. **Gate 0 を足す: 棋譜と目利きの調達**。人間は将棋を指さないので、実棋譜も目利きも手元に無い。必要なのは、**自分の棋譜を公式機能で書き出してくれる愛好者 1〜3 人(将棋ウォーズ 1〜3 級〜初段前後)と、結果を読める有段者 1 人**。目利きは最初の顧客候補(指導者)を兼ねられる。**ここが実務上いちばん詰まりやすく、人間にしかできない。**
5. **Gate 3・4 は既にある基準に一本化する**。「実在の 1 人の 20 局以上で、同じ発症条件の死因が 3 件以上、将棋の分かる人が『本人は気づいていなさそう』と言える」([DIAGNOSIS_CONCEPT_2026-09-14.md](DIAGNOSIS_CONCEPT_2026-09-14.md) 7.2)。**基準を後から増やさない。**
6. **今すぐ安くできる 2 つ**: 二段階解析のコスト実測(D-COST)と、Failure Event JSON を版付きの契約にする(JSON スキーマ v0。`diagnose.ts --events` の形を固定して版番号を付ける)。
7. **「技術そのものの売却」は出口の 1 つとして残すが、買い手の数から見て期待値は小さい**と書いておく。

## 5. Gate(段階的な GO/REVISE。人間の提示 11. に Gate 0 を足した)

| Gate | 通る条件 | 対応する STEP・記録 |
|---|---|---|
| **Gate 0 調達**(司令塔が追加) | 本人が公式機能で書き出した実棋譜 20〜50 局を合法に得られる / 結果を読める有段者が 1 人いる | 人間の作業。棋譜は `~/Desktop/kifu-samples/` |
| **Gate 1 技術成立** | 実棋譜を取り込める / NNUE 解析できる / 再現性がある / 解析時間を測定できる | D0-KIFU(`731f19d`)・D0-NNUE(`f64ae13`)で通過。再現の単位は保存した棋譜 JSON と `records/`。解析時間は D-COST |
| **Gate 2 イベント検出** | Failure Candidate が抽出できる / Evidence が説明できる / 誤検出を確認できる | D1(`3267abd`)で道具は通過。誤検出の確認は D3(仮想人間 20 局)と D4 |
| **Gate 3 個人パターン** | 20〜50 局で繰り返しが出る / 戦型をまたいでも意味がある / 悪手ランキングとの差がある | D4。**7.2 の基準で判定** |
| **Gate 4 ユーザー価値** | 将棋に詳しい人が「自分の弱点を理解するのに役立つ」と判断 | 7.2 の「本人は気づいていなさそう」と一本化。目利きは Gate 0 で調達 |
| **Gate 5 企業価値** | 企業側が「自社サービスに組み込む意味がある」と判断 | PoC・ヒアリング(外部公開の判断は人間) |
| **Gate 6 商業成立** | API 化可能 / コストが説明可能 / 導入方法が明確 / データ・ライセンス条件を整理可能 | D-COST・JSON スキーマ・規約の記録が材料 |

**最初の GO/REVISE ポイント**(人間の提示 18.): 実在棋譜 20〜50 局 → NNUE 解析 → Failure Candidate → Evidence → 複数局集約 → Personal Pattern 候補 → JSON。**この結果を将棋に詳しい人間が見て「単なる悪手ランキングでは得られない」と判断できるか。**ここを通過して初めて、API 仕様・PoC 資料・価格・ライセンス条件・営業先の具体化に進む。

**今後のすべての開発を判定する質問**: **「これは売れる解析エンジンの証明につながるか?」**

## 6. 売る相手と商品形態(人間の提示。順は司令塔が変えた)

| 順 | 相手 | 形 | 注意 |
|---|---|---|---|
| 1 | 将棋教育サービス(教室・指導者・通信講座・講師系の発信者) | 棋譜 → 弱点発見 → 練習問題 → 学習。**コーチが解釈する支援ツール** | 最初の検証相手。目利き(Gate 0)と重なる |
| 2 | 将棋プラットフォーム | 既存サービスに「あなた自身の弱点分析」を追加(API/OEM) | 「内製」の壁が最も高い。提携はデータ権利を解く |
| 3 | メディア・出版・ゲーム関連 | OEM として組み込む | — |

商品形態は **API / OEM / ライセンス / 技術提供 / 技術そのものの売却** の複数の出口を持ち、**B2C SaaS 一本に賭けない**。**「この企業が必ず欲しがる」とはまだ言わない**(PoC・ヒアリングで検証)。

## 7. やらないこと・やること(人間の提示 15.・16.)

**売却仮説を検証するまで優先度を下げる**: Web UI の装飾 / 認証 / 課金 / DB / マイページ / 大規模なスマホ対応 / 不必要な画面機能 / 大量の Failure Candidate。**今のアーキテクチャ(DB なし・認証なし・課金なし・1 ゲーム中心)は、B2B の解析エンジンとして見るとステートレスな解析コアに発展させやすく、都合がいい。**

**優先する**: 技術(NNUE・KIF/CSA 入力・実在棋譜・軽量スキャン・深掘り解析・解析コスト測定)/ 解析(Failure Candidate 1 種類・Evidence・物理イベント・複数棋譜集約・Personal Pattern 候補)/ 品質(再現性・Invariant・誤検出調査・固定棋譜による回帰テスト)/ 出力(構造化 JSON、将来の API 化を意識したデータ構造)。

## 8. 最終的な営業メッセージ(人間の提示。Gate 5 の後に使う)

> 将棋 AI は、局面ごとの最善手を提示することには強い。しかし、プレイヤーが複数の対局を通じて、どのような状況で同じ失敗を繰り返しているかを構造的に分析することは別の問題です。私たちは棋譜をエンジン評価だけで終わらせず、盤上で起きた物理的イベント、失敗候補、複数局にまたがる個人パターンへ変換する解析基盤を開発しています。既存サービスの UI や棋譜データ基盤を活かしたまま、API/OEM として組み込めることを目指しています。

**一言で**: 「将棋 AI を作る」のではなく、**「将棋 AI・盤面解析・複数棋譜の統計を組み合わせて、プレイヤー自身も気づいていない“繰り返す失敗パターン”を発見する解析エンジンを作り、それを企業の既存サービスに組み込める技術として売る」**。
