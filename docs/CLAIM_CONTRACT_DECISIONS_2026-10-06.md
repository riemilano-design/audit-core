# Claim Contract ― Q-1〜Q-6 の決定と v0.2 の方向(2026-10-06、人間の決定「それで進めて」)

[CLAIM_CONTRACT_SPEC_v0.1.md](CLAIM_CONTRACT_SPEC_v0.1.md) §11.2 の持ち越し 6 件を、人間が同日の雑談で決めた。司令塔の精密化 2 点(Q-1 の「0 との比較」・Q-5 の「minN で落ちた UNVERIFIABLE」)を含めて人間が「それで進めて」と確定した。**v0.1 の本文は測った時点の記録として書き換えない。** v0.2 はこの文書に従って書く。コードは触らない。

## 1. 決定

| Q | 決定 | 精密な定義 | 含意(やること) |
|---|---|---|---|
| **Q-1 比較子** | 比較子は Claim の修飾にしない。**線の登録簿に値・比較子・承認を束ねて置き、ポインタで取る** | **構造上の 0 に対する比較**(存在する・空でない・等しい)は承認なしで許す。**人が選んだ数に対する比較**(0.7・2 倍・minN)は承認を要求する。0 は判断ではなく「在る」の定義 | C-02・C-04・C-10 の「> 0」は A のまま。同じ形(threshold)でも比較子は線ごとに違う(C-09 `<`、C-30 `>=`)ので、LLM は比較子を主張できず、線の id だけを書く |
| **Q-2 線 0.7 の承認** | `approval_record` を特別な欄にしない。**「線 t は承認済みである」は source が登録簿の direct_value の主張**で、ポインタが解決しなければ UNVERIFIABLE | 承認を担えるのは**承認状態を持つ scheme だけ**(`registry:`)。`code:` の定数が解決できても承認にはならない(でなければ code の定数が全部「承認済み」になる) | **送付済みの c5 の線 0.7 と「2 つぶん」は、この決定を適用すると POINTER_NOT_FOUND で止まる**(F-5。`ANSWER_MENU` に 0.7 は無い)。→ **人間の判断待ち(§3)**: 線 2 本を承認して登録簿に載せるか、冊子に線を印字するのをやめるか |
| **Q-3 顧客向け予測** | PREDICTIVE を自動で付けない。**成立条件を契約に書き、満たすものだけ PREDICTIVE**。満たさない表は「測る数の登録」(descriptive)として残す | 新しい欄の一覧を作らない。**H-4 の欄(metric・comparator・value・window・writtenAt)+ 封じたコミットの時刻 + 事象時刻との順序検査**が PREDICTIVE の契約 | c5 の答え合わせの表(C-32)は比較子が無いので descriptive。2 冊目で比較子を出すかは customer-comprehension-first と合わせて別途 |
| **Q-4 packet の外** | Evidence Pointer の **scheme** として正式に許す。`packet:` / `aggregate:` / `registry:` / `code:` / `files:` / `document:` | scheme は出どころだけでなく**信頼の段**を持つ。契約が形ごとに許す scheme を列挙する(顧客向けのデータの主張を `code:` や `files:` で根拠づけない) | XBRL で足してよい scheme は **`xbrl:` と `filing:` の 2 つまで**、と繋ぐ前に書く(§4) |
| **Q-5 INCONCLUSIVE** | 内部の状態を増やさない(4 語のまま)。顧客向けは固定文「**今回の数からは、明確な差は確認できませんでした。**」(2026-09-30 接続設計案 H-7 で人間が承認済み。`NEXTGEN_CONNECTION_DESIGN_2026-09-30.md` 176・231 行) | INCONCLUSIVE は主張の検証状態ではなく**予測台帳の結果**。「次の 25 局で差が動いたか」は結果の主張で、契約に minN がある。標本が届かなければ**結果の主張が minN で落ちた UNVERIFIABLE**。既存の機構だけで出る | v0.1 §10 の「`INCONCLUSIVE` の語が要る」を取り下げる。契約の版上げは要らない |
| **Q-6 両立しない主張** | 新しい状態(CONTRADICTED)を足さない。**両方を保持し個別に検証**。正準データが片方を支持すれば他方は VALUE_MISMATCH。正準データ自体が決められなければ UNVERIFIABLE | c5 の実例(C-17 / C-36c)は値どうしの矛盾ではなく「材料が無い」と「その材料について出やすかった」の組。片方は形の外、片方は UNVERIFIABLE で、**矛盾は結果からは見えない** | 状態の代わりに**表示の規則**: 人の確認の表(v0.1 §9)で同じ subject の主張を隣に並べる |

## 2. v0.2 の層(修飾は 3 のまま。v0.1 §7.1 の「修飾 +3」は取り下げ)

v0.1 で実測から足した 3 つは、どれも修飾ではなかった。

| v0.1 で足したもの | v0.2 での置き場 | 理由 |
|---|---|---|
| `source_kind` | **Evidence Pointer の scheme** | 主張の性質ではなく、どこから取るか |
| `join` | **検証レシピの操作**(母集団を packet から復元する手順) | 主張の性質ではなく、証拠を組み立てる操作 |
| `verification_depth` | **契約が要求する深さ / 結果が到達した深さ**の 2 つ | 主張の性質ではなく、検証の結果 |

```
Claim          form(4)+ modifiers(population / time_range / normalization)
Evidence Ptr   scheme + locator + 結合の手順
Contract       必須欄・許容幅・要求する深さ・線の id(登録簿を指す)・許す scheme
Result         状態(4 語)+ 到達した深さ + 出所
```

**承認も比較子も線も、登録簿へのポインタ解決に畳まれた**(Q-1・Q-2)。Core は「データについての主張」と「自分の線についての主張」を同じ機構で検証する。

## 3. 人間の判断(H-A は 2026-10-06 に確定。H-B は 2 冊目の前)

| # | 判断 | 決定 |
|---|---|---|
| H-A | 線 0.7(M4)と 2 倍(M5)を登録簿に載せるか | **B: 載せない(人間の確定 2026-10-06)。** 送付済みの c5 冊子は変更せず、歴史記録として残す。理由: 送付済みを救うために登録簿を作ると、監査の結果を成果物に合わせることになる。0.7 と 2 倍は記録上も「道具の仮置き」で、承認された事実が無い |
| H-B | 2 冊目の答え合わせの表に比較子と向きを出すか | 2 冊目の前に決める(Q-3・F-6) |

### 3.1 H-A の精密な中身(司令塔の精密化を人間が確定)

| 項目 | 決定 |
|---|---|
| 落ちる主張 | **「線を下回った(上回った)ので行動にしました」という採用の主張**(本編 32・34 行の後半)。承認済みの線を要求するので POINTER_NOT_FOUND |
| 落ちない主張 | **「道具の仮置きの線は 0.7 です」「線は 22 / 531 の 2 つぶんです」という道具の定数の記述**。承認済みとは言っておらず、`code:check_answer.MENU_THRESHOLDS.*` で解決する → GROUNDED(Q-4 の scheme。信頼の段は「道具についての主張」) |
| 採用のうち残るもの | minN(分母の下限)は承認済みの表(`DELIVER_GATES` §2.4・`ANSWER_MENU`)にある → その部分は GROUNDED |
| 規則 | **「承認されていない線で行動を採用しない」**。「線を印字しない」ではない ― 線の印字は仮置きを隠さないための人間の判断(2026-09-29)で、やめると問題が見えなくなるだけ |
| v0.2 の記録 | 旧冊子について 2 行: 線の記述 = GROUNDED(code)、採用 = POINTER_NOT_FOUND。失敗ではなく「人が選んだ線は承認の証拠が無ければ検証可能な線として扱わない」契約を実データで確かめた例 |
| 次に戻ってくる判断 | **2 冊目の前に 1 件**: M4・M5 の採用はこの 2 本の線で決まるので、同じ行動を出すなら線を判断的知識として承認するか、行動を出さないかを決める。過去の救済ではなく将来の採用の判断なので B と矛盾しない |

これで**現時点の人間の判断待ちは 0 件**。次は v0.2 → XBRL の予測の封(§4)。
