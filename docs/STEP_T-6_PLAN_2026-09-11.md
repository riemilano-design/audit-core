## 2. 実装してよい範囲

### A. 回帰モードのエンジン条件(設問 1 = (b) + Threads=1)

**A-1(`apps/server/src/engine/usiEngine.ts`。engine-integration)**: `GoOptions` に `nodes?: number` を追加。`go()`・`goMultiPv()` は `nodes` が与えられたとき `go nodes ${nodes}` を送り(`movetime` は送らない)、タイムアウトは定数 `NODES_GO_TIMEOUT_MS = 60_000`。`nodes` が無ければ従来どおり `go movetime`(既定 2000)。`setThreads(threads: number)` を `setMultiPv` と同じ形で追加(`setoption name Threads value N` を送るだけ)。**本番の既定値・呼び出し(server.ts、candidateMoveSafetyCheck、playOpponentMove)は変えない。** `usiEngine.test.ts` に「nodes 指定で `go nodes N` を送る」「未指定で `go movetime 2000`」「setThreads の送信文字列」を追加。`prioritizedEngine.ts` は変更不要(options を転送するだけ。F-5)。

**A-2(`scripts/playtest/lib/fixedSearchEngine.ts`(新規)+ test。step-implementer)**: `LowPriorityEngine` を包み、`goMultiPv(options)` を `{ ...options, nodes }` で下へ渡す薄いアダプタ(`position`・`setMultiPv` は素通し)。本番関数の複製はしない。

**A-3(`scripts/playtest/replay.ts`)**: CLI に `--nodes <N>`(既定 **4,000,000**。本番の Threads=1・2秒に近い到達ノード数。F-2)と `--threads <N>`(既定 **1**)を追加。ハンドシェイク後に `rawEngine.setThreads(threads)` を送り、`engine.asLowPriority()` を A-2 のアダプタで包んで recorder へ渡す。`meta` 行に `searchMode: "nodes"`・`nodes`・`threads` を追加(`MetaLine` に optional で追加。`compare.ts` の正規化ではこれらを**除かない** = 条件が違う記録は一致しない)。**`explore.ts` は変えない**(探索モードは本番条件のまま)。`--nodes 0` を「本番条件(movetime)のまま」の逃げ道として残す(比較実験用。既定ではない)。
- 既定値 4,000,000 は**ハーネスの引数であって、将棋の判断・本番の閾値ではない**。README にその旨と、変えた場合は記録の `meta` で区別できることを書く。

**A-4(`check.ts`)**: 入力の `meta.searchMode`/`nodes`/`threads` が混在する場合に「入力の探索条件が混在」の警告1行(gitHead 混在の警告と同じ形)。

### B. I-6(draft)と型「結果」(設問 2 = 最小案)

**B-1(型)**: `InvariantType` に `"結果"` を追加。`check.ts` の `ALL_TYPES`・`typeCounts`、`lib/denominators.ts` に同型があれば同期(F-10)。

**B-2(`adviceSource` の判定。記録の変更なし)**(計画レビュー1回目の REVISE を受けて改訂): 提案書 4.3 は「`recorder.ts` に1項目足す」としているが、S1 の選択規則は直前の ready 行の既存フィールドだけで決まる(F-9)ため、**記録には足さず、不変条件側で直前の ready 行から導く**: `senteMove(t)` が直前 ready 行(ply t−2)の `candidateMove.explanations[].move` に含まれる(かつ `status === "ready"`)なら `candidate`、そうでなく `candidateMoveLabels` のキーに含まれるなら `route`、それ以外は `none`。JSONL の形式を変えない。この判定は `lib/adviceSource.ts`(純粋関数)+ test に置く。

**意味の範囲(監査案 (b) を採用)**: この値が意味するのは「その手が、直前に画面へ出ていた助言(候補手または道のりの一手)と**一致した**」ことであり、「助言に**従った**」ことではない。従ったと言えるのは、選択規則がその助言を参照している S1(および S2・S3 が S1 規則へフォールバックした手)だけで、E・R の手は助言を参照せずに決まるため一致は偶然でありうる。固定棋譜(人間の対局。C-1 の事故を含む)は選択の由来が記録に無いため「一致」として扱う。この区別を (1) `lib/adviceSource.ts` と `i6-advice-then-loss.ts` の冒頭コメント、(2) I-6 の `detail` 文(「直前に表示していた候補手/道のりの一手と一致する手」と書き、「従った」と書かない)、(3) README(B-4)に明示する。あわせて `check.ts` の「## 入力」の各行に `profile`(meta にあれば。固定棋譜は「固定」)を出し、検出例の kifuId(探索は末尾にプロファイルを含む)と合わせて由来を読めるようにする。全プロファイルへ適用するが、集計・解釈のときは S1 と他を分けて読む前提で、その旨を README に書く。

**B-3(`invariants/i6-advice-then-loss.ts` + test。status `draft`、type `結果`)**: 各 ready 行 t(`senteMove`・`goteMove` あり、直前 ready 行あり)について、`adviceSource ∈ {candidate, route}` のとき、本番関数 `detectBoardEvents(prev.sfen, senteMove, goteMove)` を呼び、`kind === "captured_by_opponent"` で `square !== null` の事象があれば、その `square` を移動先とする手が `response.legalMoves` に**1つも無い**場合に検出する(最小案)。移動先の取り出しは **`moveUsi.slice(2, 4)`**(固定位置。`7g7f` → `7f`、`P*5e` → `5e`、成り `3d3c+` → `3c`。`scripts/playtest/lib/players.ts` の `toSquareOf` と同じ考え方で、同関数を export して共用する。「末尾2文字」は成りで壊れるため使わない)。将棋の知識を使わない。`condition` は `adviceSource`(`candidate` / `route`)。`detail` に取られた駒(`piece`)とマスを含める。`index.ts` に登録。取り返し以外の損得(単純案)は扱わない。
- 「取り返す手が無い」の判定は合法手の移動先だけを見る(取り返した結果の損得は見ない)。人間の最小案の文言どおり。

**B-4(README)**: 回帰モードのエンジン条件(`--nodes`・`--threads`、既定値、meta への記録、探索モードは本番条件のまま)、型「結果」と I-6 の説明、`adviceSource` を記録ではなく事後判定で得る理由と、「一致」であって「従った」ではないこと(S1 とその他を分けて読む)。
