## 1. 先に決めること: 短い読み筋の扱い(**司令塔の指示により、実装前に決めて書く**)

### 1.1 何が問題か

`multipv 2` が `lowerbound` で **1 手だけの読み筋**を返すことがある(設計書 1.4)。通常は 10〜15 手。

このとき素直に材料を数えると、**「駒を取る手は無い」「王手は無い」「角交換は無い」がすべて成立してしまう。**
しかしこれは局面についての事実ではなく、**エンジンの出力が途中で切れているという事実**である。

**材料が「無い」と言うとき、それが「読み筋を最後まで見て無かった」なのか「読み筋が短くて見えなかった」なのかが区別できないと、誤認をそのまま文にする。**
これは既知事項 P-23 / P-26 の扱い(**「測っていないから言わない」と「急がないから言わない」を混ぜない**)と同じ問題である。

### 1.2 決めたこと(2 つある。**片方だけでは足りない**)

**(1) 門番: 使える手数が `minPlies` 未満なら、材料を 1 つも立てない。**

```
usablePlies < minPlies  →  { kind: "insufficient", usablePlies, reason: "pv_too_short" }
```

**提案値 `minPlies = 4`。** 理由:

- 取り合いは「取る → 取り返す」で最低 2 手かかる。相手の応手まで見ないと、材料 1(最初に取るのはどちらか)が取り合いの始まりなのか一方的な取りなのかが分からない
- 実際に壊れる形は**長さ 1**(`lowerbound`)であり、正常な読み筋は 10〜15 手。**4 は壊れた線だけを弾き、正常な線は 1 本も弾かない**位置にある
- 3 以下だと長さ 2〜3 の中途半端な線を通してしまい、5 以上にする根拠が今は無い

**`minPlies` は閾値なので判断的知識である**([CLAUDE.md](../CLAUDE.md) ルール 4)。**既定値を勝手に確定させない。** 呼び出し側が渡せるようにし、提案値は承認事項に上げる(7. の H-1)。

**(2) 門番を通った後も、「無い」を素のブール値で表さない。**

門番は長さ 1 の病的な線を弾くだけで、**長さ 4 の線と長さ 15 の線の違いは消えない。**
`minPlies` を通ったからといって `false` が「無かった」を意味するようにはならない。

**そこで、出来事の材料は「起きた ply」か `null`(この読み筋の中では起きなかった)で表す。** ブール値にしない。

```ts
firstCapture: { ply: 3, byUs: false, role: "pawn" } | null
```

戻り値は常に `usablePlies` を持つ。**`null` + `usablePlies` を両方見なければ「無い」と言えない**形にする。
**`null` を「無い」と読み替えるのは、文を組み立てる段(設計案 (え))の責任であり、この STEP では行わない。**

### 1.3 読み筋が途中で非合法になったとき

エンジンの読み筋は古い局面のものが混ざることがある。

**決定: 例外を投げない。`isLegalMove` が false を返した手の**直前**までを使い、`usablePlies` にその長さを入れ、`truncatedAtPly` に切れた位置を入れる。**
`replayMoveHistory` は非合法手で例外を投げる仕様だが、あれは**ユーザーが実際に指した履歴**を扱うものなので正しい。**読み筋はエンジンの予想にすぎず、同じ扱いにはしない。** そのため `replayMoveHistory` は使わず、本モジュール内で `applyMove` を直接回す(既存モジュールを 1 行も変えないため)。

## 2. 材料 1〜12 の定義

★ = **判断的知識。定義を確定させない**(規則として選べる形にし、既定値を置かない)。

| # | 材料 | 提案する定義 | 型 |
|---|---|---|---|
| 1 | 最初に駒を取るのはどちらか | 着手前の局面で移動先に相手の駒がある最初の手(打つ手は除く)。成駒は `normalizeRole` で正規化 ― **既存 `captureSummary.ts` と同じ基準** | `{ ply, byUs, role } \| null` |

| 12 ★ | 利きが通るか | **飛・角・香(成含む)の `attacks` の升数の合計**の、root と末端の差 | `{ us: number, opponent: number }` |

### 2.1 ★ を「規則」にする書き方

司令塔の指示どおり、`IntentPickRule` / `DirectionRule` と同じ形にする。**既定値を置かず、呼び出し側が必ず選ぶ。**

```ts
export interface PvMaterialRules {
  /** 材料 2「ぶつかる」の定義。既定値なし。 */
  contact: "capture_available" | "mutual_attack";
  /** 材料 5「玉の周り」の定義。既定値なし。 */
  kingNeighborhood: "eight_neighbors";
  /** 材料 11「上がる/下がる」の定義。既定値なし。 */
  advance: "rank_delta";
  /** 材料 12「利き」の定義。既定値なし。 */
  reach: "sliding_attack_count";
}
```

**`PvMaterialRules` は必須引数にする(`?` を付けない)。** そうすれば「既定値を置かなかった」ことを型が強制し、後から誰かが暗黙の既定で呼ぶことができない。

**選択肢を 2 つ実装したのは `contact` だけである**(`capture_available` / `mutual_attack`)。
残る 3 つは今のところ選択肢が 1 つしかないが、**既定値を作らないために欄を残してある。**
計画時は `kingNeighborhood` に `castle_zone` を併記していたが、**囲いの範囲の定義そのものが
判断的知識であり、測る材料が無いまま実装すると確定させてしまう**ため、足していない。

### 2.2 攻め / 受けの定義(設計書 4.1)は**この STEP では作らない**

> 読み筋の中で最初に駒を取ったのがどちらか。こちらなら「仕掛ける」、相手なら「攻めてくる」。

**材料 1 を計算するところまでで止める。** 材料 1 の値から「仕掛ける/攻めてくる/まだぶつからない」へ写す関数は**書かない**(司令塔の指示)。
写像は文を組み立てる段(設計案 (え))の仕事であり、そこで承認を通す。

## 3. 型と関数の形

```ts
export type PvMaterialsResult =
  | { kind: "insufficient"; pvLength: number; usablePlies: number; reason: "pv_too_short" }
  | { kind: "measured"; pvLength: number; usablePlies: number;
      truncatedAtPly: number | null; materials: PvMaterials };

export function computePvMaterials(
  rootSfen: string,
  pv: string[],
  rules: PvMaterialRules,   // 必須。既定値なし
  minPlies: number,         // 必須。既定値なし(1.2 の (1))
): PvMaterialsResult;
```

- **決定的な純粋関数。** 同じ入力には常に同じ出力。状態を持たない
- エンジンにも LLM にも依存しない(引数は SFEN と文字列配列だけ)
- `us` = **root 局面の手番**(`pv[0]` を指す側)。先手/後手ではなく「読み筋を始める側」で揃える

### 3.1 読み筋の同一性 ― **関数の中でエンジンを呼ばない**(2026-09-13 の観測による追加)

司令塔から観測が来た。同じ局面・同じ 4,000,000 ノードで、**記録に載った `engineReference` と③が使った `engineReference` が別物になる**行が 3 行出た。うち 1 行(`claude-3` ply 22)は `afterPass` の最善手そのものが違った(`dropCp` 98 対 300 超、名指すマス `9i` 対 `8e`)。**別々の探索だからである。**

> **探索の内部状態の違いは、境目の数 cp ではなく読み筋そのものを変えうる。**

**この STEP の関数は「どの読み筋を渡されたか」だけに依存させる。** 関数の中で探索を起こさない。読み筋は引数で受け取る。

そうすると**同一性の問題はこの STEP の外(読み筋を記録に載せる U6-L 側)に閉じ込められる。** この関数は、同じ `(rootSfen, pv, rules, minPlies)` に対して常に同じ結果を返すことだけを保証し、**その `pv` がどの探索から来たかには関与しない。**

3. の型が既にこの形になっている(引数は SFEN と文字列配列と規則だけで、エンジンへの参照を持たない)。**追加の変更は不要だが、契約として明記する。**
テストでも守る: **`pvMaterials.ts` が `engine/` 配下を import していないことを確かめる**(5.1 の「依存」の行)。

どちらも **shogiops の `attacks()` が盤の外(内部表現 16×16)の升を返す**という同じ罠への対処であり、**中身は同じ**である。

本 STEP が重複を作ったのは、**既存ファイルを 1 行も変えない**という方針(4.)のためである。あちらは `export` されていない module-local なので、共有するには既存ファイルに触る必要があった。

#### なぜ直すか

> **同じものが 2 箇所にあると、片方だけ直る状態を作る。**

いまは中身が同じだが、**片方だけが将来の shogiops の変更に追随する**、あるいは**片方だけに升が足される**ことがありうる。そのとき、どちらが正しいのかを判定する手段が無い。

#### 提案する範囲

- `BOARD_SQUARES` を 1 箇所(`rules/` 配下が自然。`squareAttack.ts` と同じ層)へ移し、両方がそれを import する
- **値は 1 升も変えない。** 移すだけである
- 移した先に、罠の説明(`attacks()` が盤外を返すこと、線で利く駒だけでなく玉も隅で返すこと)をまとめる

#### 確かめ方

- **移動の前後で `size()` が 81 であること**を試験に書く
- **既存テストが 1 件も動かないこと**(`routePlanner` の経路探索は本番導線なので、ここが動いたら移し方を間違えている)
- 片方だけを壊すと両方の利用箇所で鳴ることを確かめる

#### この STEP でやらないこと

- 盤の範囲の定義を変えること
- `countKingNeighbors` の冗長な交差を外すこと(**12.3 のとおり、いまは冗長だが、空き升を数える形に変えたときに効き始める**。外すかどうかは別の判断)
