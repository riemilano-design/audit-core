## 2. 何を測るか

### 2.1 回す条件(7 局 × 4 条件。**全部 Threads 1**)

| 条件 | `--nodes` | `--reference-nodes` | 役割 |
|---|---|---|---|
| **L100k** | 100,000 | 100,000 | 軽い走査(4,000,000 の 1/40) |
| **L400k** | 400,000 | 400,000 | 軽い走査(4,000,000 の 1/10) |
| **C4M** | 4,000,000 | 4,000,000 | **対照**: 深い走査を、この STEP の実行と同じ機械の状態でもう 1 回。**`records/d0-nnue` との差が、深い走査どうしの揺れ(P-33)の床になる** |
| (既存)**D4M** | 4,000,000 | 4,000,000 | `records/d0-nnue`(`0cce0c3`)。深い走査の基準 |

**100,000 と 400,000 を選んだ理由**:
- 4,000,000 の **1/40 と 1/10**。探索 1 本はノード数にほぼ比例して短くなると読めば(C-g の nps で 100,000 ≈ 0.17 秒・400,000 ≈ 0.7 秒・4,000,000 ≈ 6.9 秒)、**「1 桁安い」と「2 桁近く安い」の 2 点**で、安さと取りこぼしの関係の曲がり方が見える
- **それより小さい値(例 10,000)は選ばない**: 探索 1 本が 0.02 秒ほどになり、エンジンとのやりとり・JS の処理など探索以外の時間が支配的になると読む(**読みであり、測っていない**)。探索以外の時間は 4. で測るので、測った後に足すかを決める(Q-1)
- **`--nodes` と `--reference-nodes` を同じにする理由**: 今の `replay.ts` では導線の探索を省けない(C-a・C-b)。**「今の道具で 1 局を軽く回すと何秒か」を測る。**診断に要る `engineReference` だけの所要は、4. の分解で読む(**上限としての値**。8. の L-4)

**D3 の 20 局(`records/d3-nnue`)**: D3 が記録をコミットした後、**L100k・L400k だけ**を同じ形で足す(深い走査は D3 のものを使う。C4M は 7 局だけ)。

### 2.2 比べるもの(**規則 11.6 の 3 種の「無い」で分ける**)

**単位は「組」**: (棋譜の id, 直前の ready 行の ply, 直後の ready 行の ply)。深い記録と軽い記録で、**同じ組を突き合わせる。**

深い走査で**急落候補**(`cpDrop` か `mateDrop`)だった組について、軽い走査の同じ組を次の 4 つに分ける:

| 区分 | 軽い走査の同じ組 | 意味 |
|---|---|---|
| **拾えた** | 急落候補(種類が違っても拾えたに入れ、**種類の食い違いは別に数える**) | |
| **取りこぼし** | 比べた(差を取った・直後が mate)が、急落候補にならなかった | 軽くしたことで見えなくなった |
| **比べられなかった** | 組が「比べられなかった組」(王手中・終局・測れなかった・評価値でない のどれか。理由を並べる) | **取りこぼしに入れない**(軽い走査が見て外したのではない) |
| **測っていない** | 軽い記録にその組が無い(再生が途中で止まった等) | **取りこぼしに入れない** |

逆向き(軽い走査で急落候補だった組)も同じ 4 つに分け、「深い走査で比べて急落でなかった」を **余計に拾った** と呼ぶ。

**率は分母を書いて出す**: 取りこぼし率 = 取りこぼし ÷(拾えた + 取りこぼし)。**比べられなかった・測っていないは分母に入れず、件数を隣に並べる。**余計に拾った率 = 余計 ÷(軽い走査の急落候補のうち、深い走査で比べられた組)。

**あわせて出すもの(判断はしない)**:
- 拾えた組の `diffCp` の、深い走査との差の分布(中央値・最大)
- 深い走査の差が閾値の近く(−400 ± 100)にある組の数(取りこぼしが閾値の近くに集まるかを見る材料)
- `matedIfPass`(パスすると詰まされる読み)は急落候補と別に、同じ 4 区分で数える
- **死因①(draft)の候補**は、軽い走査・深い走査それぞれの件数を並べるだけにする(7 局では 0 件のはず。D1 §10.10)

**3 つの比べ**: (1) L100k 対 D4M、(2) L400k 対 D4M、(3) **C4M 対 D4M(揺れの床)**。あわせて (1′) L100k 対 C4M・(2′) L400k 対 C4M も出す(同じ日・同じ機械の状態の深い走査と比べた値)。

## 3. 二段目(深掘り)の形 ― **案として書く。実装は別 STEP**

**二段目 = 軽い走査の急落候補の組だけを、nodes 4,000,000 で測り直す。**組 (b−1, b+1)(b は分岐点の手)の 2 行が対象(発症条件の写しは b−1 の行から取るので、2 行で足りる)。

`replay.ts` に「**対象の ply を絞る**」引数を足す 2 案(**どちらも本番の挙動は変えない**。ハーネスの引数):

| 案 | 形 | 良い点 | 足りない点・決めること |
|---|---|---|---|
| **(i) 対象外の ready 行を作らない** | `--target-plies <ply,…>`: 対象外の手番では immediate 行だけを書き、ready 行(導線の探索と `engineReference`)を作らない | 対象外の探索が 0 本になり、最も安い | **記録の形が変わる**(ready 行が欠ける)。`diagnose.ts` は欠けた行を「**測らないと決めた(対象外)**」として、「測っていない」と分けて数える必要がある(規則 11.6)。そのために meta に対象の一覧を残す。`check.ts` の不変条件が ready 行の欠けを許すかは、その STEP で確かめる |
| **(ii) 全行を軽く回し、対象の行だけ参考評価を深くする** | `--reference-plies <ply,…>` と `--reference-nodes-deep 4000000`: 全行の導線と `engineReference` は軽いノード数、対象の行だけ `engineReference` を深いノード数で測る | 記録の形が変わらない(各行の `engineReference.nodes` に測ったノード数が残る ― C-e) | 導線の探索は全行ぶん残る。**ノード数の違う行どうしの組**(対象の行とその隣の行)ができるので、`diagnose.ts` か比べの道具が「**両方同じノード数の組だけを比べる**」必要がある |

**決定(Q-5): まず (ii)**(記録の形を変えないので、既存の不変条件と `diagnose.ts` への波及が小さい)。安さは (i) に劣るので、**(ii) で取りこぼしと所要を測った後に (i) を別 STEP で足すか決める。どちらもこの STEP では実装しない。**

**二段目のコストの式**(5. の記号):
- 案 (ii): T₂段 = t_boot + R × t_row(軽) + K × 2 × (t_ref(4M) − t_ref(軽))
- 案 (i): T₂段 = t_boot + R × t_imm + K × 2 × t_row(4M)

## 4. 所要の測り方(**規則 12 番。時間に依存する計測は一度に 1 セッション**)

1. **始める前に宣言する**(他のセッションはエンジンを使う作業を止める)。**`ps -A -o pid=,comm=` を取り、エンジンの本数はシェルの外(スクリプトの中)で末尾一致で数える。0 本でなければ始めない**
2. **機械の状態を記録する**: `uname -a`、`sysctl -n machdep.cpu.brand_string hw.ncpu hw.perflevel0.physicalcpu hw.perflevel1.physicalcpu hw.memsize`、`pmset -g batt`(電源が AC か)、実行ファイルと `nn.bin` の sha256(P-43 の手当て)。**そのとき動いていた他のセッションの有無を、ListAgents の busy / idle で 1 行残す**(load average の説明のため。司令塔の決定、2026-09-15)。**他のセッションが待機している時間帯に回す**
3. **1 局ごとに**: 直前と直後の `sysctl -n vm.loadavg`(**load が 2.0 を超えていたら、その局の前後で ListAgents の busy / idle をもう一度残す**)、`/usr/bin/time -l` の実時間と最大 RSS、`replay.ts` の `summary` 行(`totalMs`・`readyMsPerPly`)。**エンジンの起動の時間 t_boot ≈ 実時間 − `totalMs`**(Node の起動も含む。分けない)
4. **順序**: **L100k → L400k → C4M → L400k → L100k**(軽い 2 条件を前後に 2 回ずつ)。**ファンの無い Air は長く回すと熱で遅くなりうる**ので、同じ条件の 1 回目と 2 回目の差で、時間の漂いを見る(2 回目の記録は比べ(2.2)には使わず、所要にだけ使う)
5. **終わったら「解放した」と宣言する**

**根拠にする値の条件(Q-3 で決定。2.0 は仮置き)**: 1 局の直前と直後の load average(1 分)が **どちらも 2.0 以下**の局の値だけを「根拠」とし、それ以外は「参考」と印を付けて並べる。**D0-NNUE と同じく、load が高いときの値は根拠にしない。**

**時間の分解(読み。根拠は 1 つ目の式だけ)**:
- t_row(条件) = その条件の `readyMsPerPly` の中央値(と分布)
- t_ref(条件)(`engineReference` の 2 本ぶん)は、**行ごとの `elapsedMs` を「その行の③と候補手の探索の本数」(`searchPvs` の本数)に当てた切片**で読む(C-g と同じやり方)。**切片は読みであり、`engineReference` の時間を直接測ったものではない**(8. の L-4)

## 5. 見積もりの式(**式と記号だけを先に決める。数字は測った後に入れる**)

| 記号 | 意味 | 出どころ |
|---|---|---|
| t_boot | 1 局ぶんのエンジンと Node の起動 | 4. の 3 |
| t_row(条件) | ready 行 1 行の所要(導線 + `engineReference`) | `readyMsPerPly` |
| t_ref(条件) | `engineReference` の 2 本ぶん(読み) | 4. の分解 |
| R | 1 局の ready 行の数 = ⌊手数 / 2⌋ + 1 | 棋譜 |
| K | 1 局の、軽い走査の急落候補の数 | 2.2 の結果 |
| p | 同時に回すプロセスの数 | **この STEP では p = 1 だけを測る** |
| e(p) | p 本同時に回したときの効率(1 本あたりの速さの比) | **測らない**(Q-6) |

- **1 局(1 段)**: T_局(条件) = t_boot + R × t_row(条件)
- **N 局(1 プロセス)**: T_N = N × T_局。**1,000 局・10,000 局の値はこの式で出す**
- **N 局(p 本同時)**: T_N(p) = N × T_局 ÷ (p × e(p))。**e(p) は測っていないので、p > 1 の値は「上限の目安」と書き、根拠にしない。**性能コアは 4 つ、効率コアは 4 つで、同じ速さではない(C-i)
- **二段**: 3. の式
- **実棋譜への持ち込み**: この 7 局は 20〜30 手の短い局である。**R は棋譜の手数で決まるので、実棋譜の手数の分布(Gate 0 で得る)を入れて計算し直す。**仮の値を置く場合は「仮に 120 手なら R = 61」のように仮と書く
- **円への換算はしない**(機械の値段・電気代・クラウドの料金は外の数字であり、この STEP の範囲外)
