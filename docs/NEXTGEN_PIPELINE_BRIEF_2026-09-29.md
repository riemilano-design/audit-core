# 次世代パイプラインの指示書 ― 分析の自動化と器への自動配置を一体に(2026-09-29 夜。司令塔が書き、人間が 4 点直して方向を固めた)

## 0. 最上位の原則と 5 つの層

**冊子を作りながら分析しない。** 工程は ① Observation → ② Analysis → ③ Verification → ④ Integration → ⑤ Answer selection → ⑥ Slot filling → ⑦ Rendering → ⑧ Audit → ⑨ Human release の順に、不可逆に近い形で分ける。冊子の見た目を直していたら分析結果まで変わる、を起こさない。

| 層 | 役目 |
|---|---|
| エンジン・機械認識 | **事実を作る** |
| LLM 群(GPT / Gemini / Claude) | **意味を探す** |
| 機械 | **事実と整合性を検証する** |
| 器 | **顧客の問いに合わせて配置する** |
| 人間 | **送るか決める** |

> **LLM の出力は事実層ではない。LLM は意味探索層であり、LLM の一致・多数決・もっともらしさは、それ自体では証拠にならない。**(人間の言葉、2026-09-29)

## 1. 流れ(人間の最終整理)

```
                    顧客の問い(分析の入力条件)
                             ↓
棋譜・エンジン・機械認識 → Observation Packet(数の唯一の基準点)
                             ↓
              GPT 席 ・ Gemini 席 ・ Claude 席(自由分析・仮説・発見)
                             ↓
                    統合(LLM の整理役)
                             ↓
          機械検証(数・分母・局面・母集団・仮説か事実か)
                             ↓
                    回答候補・行動候補(検証済み ≠ 採用)
                    ↓                        ↓
        顧客の問いへの回答 → スロット     行動候補 → 承認済みの表(人間が足す)
                             ↓
                  自動組版 → 機械監査 → 「答えの場所」の確認 → 最終実物確認 → 人間が送る
```

## 2. 人間の 4 つの直し(2026-09-29 夜)

1. **Observation Packet は「単なる束」ではなく正式な中間成果物。** 分析・検証・編集の全工程が参照する**唯一の事実入力**。LLM が勝手に事実を作った・途中の編集で数字が変わった、を追跡できる形にする。
2. **LLM の自由分析はかなり外してよい(二層構造)。** 内部分析では、手の目的の推測・仮説・「○○を狙っていたのでは」・行動候補・顧客の問いへの回答候補・答えられない理由、を出してよい。顧客出力は、機械で確認できた数と手だけ・承認済みの行動だけ・確認できた名前だけ・断定しない。分析段階の制約は「出力形式・安全性・事実と仮説の区別」に限る(禁止事項を無くすのではない)。
3. **「統合」は LLM、「採用」は別物。** LLM 分析 → 統合 → 機械検証 → **採用可能な候補** → 顧客の問いとの適合 → 承認済み行動表 → 冊子。検証済み = 採用ではない。LLM の行動候補は人間に上げ、人間が表に足したものだけが冊子に出る。
4. **顧客の問いは分析の入力条件。** 編集段階で初めて出るものではない。ただし「問いがあるから都合のいい分析をする」にはしない ― 「この問いに対して packet に在る事実から何が答えられるか」を探し、**「答えられない」も正式な結果**にする。

読者席(F)は必須工程から外す。品質保証装置ではなく、最後の人間的な読み手による違和感検出装置として残す。

### 2.5 追加の 2 点(2026-09-30 未明、人間)

5. **顧客の問いは packet に混ぜない(schema 上で分離)。** packet = 事実層、顧客の問い = 分析・編集の条件。「顧客がこう聞いたから事実の作り方を変えた」を防ぐ。

```
packet                      request
├── facts                   ├── customer_questions
│   ├── games               └── requested_scope
│   ├── moves
│   ├── engine
│   ├── time
│   ├── branches
│   ├── collapse
│   └── recognition
├── aggregates
└── provenance
```

   両方が LLM 分析の入力になる(packet → 事実、request → 条件)。

6. **packet の全部の値に provenance(出どころ)を持たせる。** 数値: `source: {type: engine, engine_version, pipeline_version, generated_at}`。局面: `source: {game_id, ply, sfen}`。集計: `derived_from: [game_id…]`。最終冊子の数から packet まで戻れることが、「LLM が事実を作った・途中の編集で数字が変わった」を追跡できる形の実体。

   **読み替え(2026-09-30、司令塔。計画 `PLAN_OBSERVATION_PACKET_2026-09-30.md` §4・§10)**: 値ごとに埋め込むと provenance だけで約 3.6 MB になるので、**参照方式**にする ― 行が `src` の符号を持ち、`provenance.sources` が engine_version・pipeline_version・材料の path と sha256・generated_at を持つ。行の中で出どころが違う数値だけ `src_<欄名>`。集計の行は `derived_from` を必ず持つ。遡れることは失われない。加えて `population` は機械が読める 3 欄(`from`・`where`・`unit`)にし、集計の値を facts から数え直せる形にする。packet に実名は入れない(`customer_ref` の符号だけ)。

## 4. 変えない線

- LLM に数えさせない(数はエンジンと集計)。
- 顧客に出る文は CLAUDE.md 規則 5 の (1)〜(4)。規則 8 の (2)(一致を証拠にしない)と (4)(名前は data/ の認識だけ)は残す。(3)(手の目的を列挙しない)は**内部の分析では緩め、顧客に出る文では禁じる** ― CLAUDE.md の書き換えは人間の承認の後。
- 実名を冊子に出さない。本人に聞かない。送るかは人間。
