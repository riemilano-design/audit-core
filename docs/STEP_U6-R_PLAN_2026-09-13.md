#### 変える挙動 ―`compare.ts`(2026-09-13。再監査 2 回目の必須 4。**司令塔の決定**)

**`meta` 行に `dirty` / `dirtyPaths` / `dirtyCount` が入ったことで、`compare.ts` の結果が変わる。** 汚れの 3 欄だけが違う 2 本は、これまで「完全一致」だったが、**「差があった行: dirty, dirtyCount, dirtyPaths[0]」と出るようになる**(再監査が実測)。**計画の当初はこの変化を「変えるもの」にも「変えないもの」にも書いていなかった。**

**決定: 汚れの 3 欄は比べる**(条件として扱う。`compare.ts` の `META_EXCLUDED_KEYS` には足さない)。理由: `compare.ts` が除いているのは「**実行のたびに変わる値**」(`startedAt` 等)であり、汚れはそうではない ―**`gitHead` が同じでも結果を変える条件**である(8.3 で沈黙率が 64% → 100% に動いた)。**汚れた 1 本ときれいな 1 本を「完全一致」と黙って並べることは、この STEP が防ぎたいことそのものである。** `compare.test.ts` に 1 件置いた。

**変えない非対称(既知事項の候補。番号未定)**: `compare.ts` は `gitHead` を除外しているので、**コミットの違う 2 本は「完全一致」と出る。** 汚れは比べるのにコミットは比べない、という非対称が残る。**これは T-5 の決定であり、U6-R では変えない。**

#### パスの読み方 ―`git status --porcelain -z`(2026-09-13。再監査 2 回目の非必須 b。**実測した**)

**`-z` なしでは、空白を含むパスは `core.quotepath=false` でも引用符で囲まれる**(一時リポジトリで実測: `R  apps/old.ts -> "apps/new name.ts"`、`?? "data/新規 形.json"`)。引用符で始まるパスは `apps/`・`data/`・`scripts/` に一致しないので、**汚れとして数えられなかった。** **`-z` では引用符もエスケープも付かない**(`R  apps/new name.ts\0apps/old.ts\0?? data/新規 形.json\0`)。

**したがって `-z` を採り、`core.quotepath` の指定はやめた**(`-z` の下では効果が無い)。リネームは `-z` では「新しい PATH」の項目のあとに「元の PATH」が別の項目として続くので、両方を数える。**git に渡す引数(`-z` と `--untracked-files=normal`)は、一時リポジトリで本物の git を呼ぶ試験で見張る**(差し替えの runner は引数を見ないため)。

### 何を「汚れ」と数えるか

**`git status --porcelain` の出力のうち、`apps/`・`data/`・`scripts/` に掛かる行だけ**を数える。**`docs/` の編集は結果に影響しないため数えない**(数えると常に汚れることになり、警告が意味を失う)。**未追跡ファイル(`??`)も数える** ― `data/` に未追跡の形や狙いがあると**結果が変わる**ため(U6-A・U6-I で実際に起きた)。

**`dirtyPaths` は最大 20 件までにし、超えたら件数だけを書く**(記録が肥大しないため)。

#### 除外: `node_modules`(**計画レビュー 1 回目の指摘。実測で確認した**)

**パスに `node_modules` を含む行は、追跡・未追跡・シンボリックリンクの別を問わず数えない。**

理由は仮定ではなく実測である。**worktree では `node_modules` を共有ツリーからシンボリックリンクで貼っており、`.gitignore` の `node_modules/`(末尾スラッシュ付き)はシンボリックリンクにマッチしない。** 2026-09-13 に `wt-u6j` で実測した:

```
$ git status --porcelain --untracked-files=normal   # worktree 内
 M apps/server/src/analysis/shapeFormationAnalyzer.ts
 M scripts/playtest/replay.ts
?? apps/server/node_modules
?? apps/web/node_modules
?? node_modules

$ git check-ignore -v node_modules apps/server/node_modules apps/web/node_modules
(出力なし。exit 1 = 除外されていない)

$ ls -ld apps/server/node_modules
lrwxr-xr-x ... apps/server/node_modules -> /Users/midoriko/Desktop/sgogi-coach/apps/server/node_modules
```

**共有ツリーでは同じ 3 つが実ディレクトリなので `git check-ignore` は exit 0 を返し、正しく無視される。つまりこれは worktree でだけ起きる。**

**除外しないとどうなるか**: `apps/server/node_modules` と `apps/web/node_modules` は `apps/` に掛かるので、**編集の有無に関わらず worktree では常に `dirty: true` になる。** **常に鳴る警告は見なくなる** ― この STEP が防ごうとしているものを、この STEP 自身が作ることになる。**worktree は本プロジェクトの標準の並行作業手段である**([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 3.)から、これは例外的な場面ではなく既定の場面である。

## 3. 「不明」を「きれい」と読ませない(**この STEP の要点**)

**古い記録には `dirty` の欄が無い。** ここで **`dirty ?? false` と書くと、欄が無い記録がすべて「きれい」に化ける。** **今日 8 回踏んだ「何も無いことを、問題が無いことと読む」型そのものである。**

**したがって 3 値で扱う**:

| 値 | 意味 | `check.ts` の表示 |
|---|---|---|
| `true` | 測ったとき汚れていた | **「汚れ: あり(n 件)」** |
| `false` | 測ったとききれいだった | 「汚れ: なし」 |
| 欄が無い | **この記録は汚れを記録していない** | **「汚れ: 不明(この記録は汚れを記録していない)」** |

**「不明」は警告の対象に含める。** 理由: **不明な記録と汚れた記録を混ぜて比べたときに、それが分かる必要がある**ため。

**実装レビューへの申し送り**: `check.ts` の該当箇所が **`=== true` / `=== false` / それ以外**の明示分岐になっており、**`?? false` のような省略記法を使っていないこと**を、実装レビューで必ず目で確かめる。**この 1 行の書き方だけが 予-R3 の成否を決める。**

## 7. この STEP で分からないこと

- **`dirty` が `true` だったときに、その差分が結果に影響したかどうかは分からない。** 分かるのは「**影響しうる編集があった**」ことだけである。**警告の文言もそう書く。**
- **worktree で測っても、`node_modules` は共有ツリーからリンクしている。** 依存の版が変わっていた場合はこの指標では捕まらない。**2. で `node_modules` を汚れから外したので、なおさら捕まらない。** これは承知のうえの取り引きである ― **リンクの存在を毎回鳴らすことと、依存の版の変化を捕まえることは別の話であり、前者を鳴らしても後者は捕まらない。**
- **`report.json`(`check.ts --json`)には汚れの欄が無い。範囲外とする**(再監査 2 回目の非必須 a。司令塔の決定)。**json を読むものが出た時点で足す**(既知事項の候補。番号未定)。
- **`buildMetaLine` へ移した後の `replay.ts` は、実物では回していない**(9.9 以降の直しはすべてエンジン不要の範囲で行った)。3 回目の再監査が `explore.ts` を実物で 1 局回して予測が的中したが、**`explore.ts` を回したことで `replay.ts` も担保したことにはしない**(再監査の書き方のとおり)。確かめたのは試験・変異・バイト比較だけである。
- **`dirty: true` なのに `dirtyCount` も `dirtyPaths` も無い `meta` は「汚れ: あり(0 件)」と出る**(再監査 2 回目の非必須 d)。**`buildMetaLine` は 3 欄を必ず一緒に書くので、壊れた記録でしか起きない。限界として明記する。**
- **配線の見張りはソース照合である。照合は片側にしか壊れない** ― 整形を変えると壊れていなくても落ち(安全側)、**照合する文字列を残したまま意味を変える書き換えは捕まらない。** `check.ts` を子プロセスで丸ごと走らせて出力を確かめる形なら文字列に依らないが、playtest の試験に子プロセスを起こすものが無く、**4 度目の範囲拡大の上限に掛かるので採らなかった。**
  - **実例(3 回目の再監査が測った。4 件とも vitest 0/176・tsc rc=0。9.10 の直しの後に担当が同じアンカーで当て直しても 4 件とも 0/178・tsc rc=0)**:

    | # | 照合の文字列を残したまま意味を変える書き換え |
    |---|---|
    | Y08 | `check.ts`: `readDirtyState(meta)` の行は残し、戻り値の `dirtyState` を `"clean"` に差し替える |
    | Y09 | `check.ts`: 読む直前に `meta.dirty` を `false` に書き換える |
    | Y10 | `replay.ts`: `buildMetaLine` の後、書き出す直前に文字列で `"dirty":true` を `"dirty":false` にする |
    | Y10b | `explore.ts`: 同上 |

  - **塞がない**(司令塔の決定)。**書いた JSONL を読んで確かめる端から端までの試験は、上で採らなかった子プロセス方式と同じコストで、範囲の上限に掛かる。** 限界は数字付きで測ってあるので、「測っていないものは承認しない」には当たらない。

### 8.3 **校正の副産物 ― この STEP が要る理由が、校正の中で実演された**

**校正 1 番と 2 番の 2 本は、`gitHead` が同一(`a061019`)・同じ棋譜・同じノード数・同じ探索条件である。** それでも 6 列がこうなった。

**沈黙率が 64% から 100% へ動いた。** 原因は `data/shapes/` に置いた**未追跡の 1 ファイル**である。**「未追跡ファイルも数える」という 2. の判断が、そのまま実例になった**(U6-A・U6-I で起きたことの再現でもある)。

### 8.4 実装中に見つけた、自分のコードの穴(**この STEP と同じ型**)
