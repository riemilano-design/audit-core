## 2. 実装してよい範囲

### サーバー(`apps/server`。既存判定の別表現。新しい判定・閾値なし)

**S-1(当たりのマス)**: `PieceThreatMessage` に `square: string`(当たっている自分の駒のマス。USI)と `attackerSquares: string[]`(当てている相手の駒のマス。USI。既存の攻め駒の並び順のまま)を足す(`explainPieceThreats` が `fact` から写すだけ)。`partitionUrgentMessages` の型(`UrgentMessage` の union)はそのまま通る。王手・詰みの行にはマスを足さない。
**S-2(④のマス)**: `TargetShapeProgress` に `matchedSquares: string[]`・`missingSquares: string[]`(USI。既存のラベル配列と同じ順)を足す(`toTargetShapeProgress` が `shapeResult` から写すだけ)。
**S-3(②の根拠のマス)**: `StageResult` に `evidenceSquares?: string[]` を足し、`buildOpponentIntentFormingStage`・matched の段階で `best.matchedSignatures.map((s) => s.to)`(重複除去。`recognition_pattern` 順)を入れる。`generateCoachExplanations` が `CoachExplanation` に `evidenceSquares?: string[]`(**`status` と同じくスキーマ外の API 用フィールド。`Explanation` 自体には足さない**。F-5)として写す。unclassified・`draft` で unclassified に落ちる場合は付けない(名前も根拠も出さない = 露出制御に従う)。
**S-4(テスト)**: S-1〜S-3 それぞれに、既存テストの材料で「マスが写っていること」「並び順が既存と同じこと」「unclassified に無いこと」を検証。`explanations.schema.json` の必須フィールド検査(既存テスト 320 行付近)は `Explanation` 対象のまま。

### web(`apps/web`)

**W-1(色)**: `.piece-gote` の色を `#222` に(回転はそのまま)。持ち駒欄は触らない(色指定が元々無く、決定 2 の 3 の対象外)。赤は当たり・王手の印と帯にだけ使う。既存の青枠(直前の手)・黄(選択中)・緑(移動先)は変えない。
**W-2(事実の印。常時)**: `renderCandidateArrows` を「盤の印をまとめて描く」関数(例 `renderBoardMarks(plan, coach)`)に広げ、同じ SVG オーバーレイに次を描く。当たっている自分の駒 = 実線の赤い輪(F-9 の寸法をマス幅比で描く)、当てている相手の駒 = 細い赤枠。マスは S-1 の `square`・`attackerSquares` から取る(web で利きを判定しない)。同じマスが直前の手の青枠と重なっても両方描く(青枠は `td` の内側、赤枠は SVG。優先順位の規約(`style.css` 163 行のコメント)に「赤い輪・赤枠は事実の印として常時、青枠と重なってよい」を追記)。候補手の矢印は既存のまま。
**W-3(凡例。固定 3 語)**: 凡例を「当たり / 直前の手 / 次の一歩」の 3 項目(各項目に印のミニ図形: 赤い輪+赤枠 / 青枠 / 破線矢印)で**常時**出す(印の有無で項目を増減しない。「(今は無し)」等の注記は付けない。F-9 の未承認文言は使わない)。凡例の語は承認済みの 3 語だけ。
**W-4(当たり 4 駒以上)**: 盤には D の順(= `urgentMessages` の並び)で上位 3 件だけ赤い輪を描き、その 3 件の攻め駒に赤枠。帯は上位 3 件の行を既存の文のまま出し、4 件目以降の行は出さず、代わりに 1 行「ほか N 駒」(N = 件数 − 3。承認済み文言)を置く(追加の決定の文どおり。計画レビュー 1 回目で「承認済み文から一意に読める」と確認)。純粋関数 `partitionPieceThreatsForBoard(messages)` → `{ drawn, othersCount }` を `gameApi.ts` に置きテストする。
**W-5(開いたときだけの印と説明 2 行)**: ②の根拠のマス(淡い青灰の塗り。`coach` の `opponent_intent` の `evidenceSquares`)と、④のできているマス(淡い緑の塗り。`targetShapeProgress.matchedSquares`)・これから作るマス(破線の輪。`missingSquares`)を描く関数と、承認済みの説明 2 行(②「盤の淡い青灰の塗り＝この見立ての根拠になった相手の駒」、④「盤の淡い緑の塗り＝できているマス、破線の輪＝これから作るマス」)を各ブロックの本文の末尾に置く。塗りは `td` の背景(選択中・移動先の背景と重なるときは既存の `!important` が勝つ = 操作中の見え方を優先)、破線の輪は SVG。**いつ描くか(②④に開閉が無い 5-4 時点の扱い)は 5. の H-1 の人間判断に従う**(推奨: 5-4 では②④が常に開いている扱いで、根拠があるときは常に描き、説明行も常に出す。5-3 が開閉と排他を付けた時点で「開いたときだけ」になる)。
**W-6(テスト)**: `gameApi.ts` の純粋関数(W-4 の分割、印の入力を API から取り出す関数)にテスト。既存テスト 58 は変更しない。
