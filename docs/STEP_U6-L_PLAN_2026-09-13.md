## 1. 司令塔が「実装前に決めること」とした 3 点への回答

### 1.1 決定 1 ― 記録する読み筋と、③⑤を作った読み筋が同一であること

**同一の探索結果を、同じ関数の戻り値として運ぶ。**再探索は行わない。

| 対象 | ③⑤を作る探索 | 読み筋の運び方 | 同一か |
|---|---|---|---|
| ③(focusText) | `computeFocusText` → `measureEngineReference(current.sfen, focusEngine)` | その `MultiPvGoResult` から `pv` を取り出し、`computeReachablePlan` の戻り値に同梱 | **同一(同じオブジェクト)** |
| ⑤(candidateMove) | `checkCandidateMovesSafety(...)` の `baselineMultiPv` / `evaluations[].multiPv` | 同じ `safetyCheck` から取り出し、同じ戻り値に同梱 | **同一(同じオブジェクト)** |
| 記録の `engineReference`(行頭の欄) | **ハーネスが独自に測る別の探索**(`recorder.ts` の `referenceEngine`) | ここには読み筋を足さない | **別物。足さない** |

**「同じ設定で呼べば同じ結果」を前提にしない**という指示に、**突き合わせではなく構造で**答える。値をコピーして運ぶので、ずれようがない。

3 行目が重要である。2026-09-12 に 3 行やられたのは、**記録の `engineReference` と③が使った `engineReference` が別々の探索だった**ためである(`claude-3` ply 22 は `afterPass` の最善手そのものが別の手だった)。**同じ穴を読み筋で作らないために、行頭の `engineReference` には読み筋を足さない。**足すと「記録に読み筋がある」という事実だけが残り、それが③の見た読み筋かどうかを後から誰も区別できなくなる。

**この決定の副作用(重要)**: ③が使った `EngineReference` そのものは、いまも記録に載っていない。**載せるべきだが、本 STEP のスコープではない。**L-2 として分離し、司令塔の判断を仰ぐ(7.1)。

### 1.2 決定 2 ― 短い読み筋の扱い

**2 つの別々のことを分ける。**

**(a) 記録の規則(本 STEP で決める。実装上の判断)**

> **長さで捨てない。0 手・1 手を含め、返ってきた読み筋をそのまま記録する。**
> 併せて **`lowerbound` / `upperbound` だったか**を記録する。

理由: 記録の時点で捨てると、**捨てた件数が分布から消える。**「1 手しか返らなかった探索が何件あったか」は、U6-M の `minPlies` を決めるための**数えたい当の量**である。門番は使う側(U6-M)に置き、記録側には置かない。

**(b) 「読み筋として使わない」門番(2026-09-13、測定後に司令塔が確定)**

**計画の時点では「提案値 4 手。本 STEP では確定しない」と書いていた。**測定(11.2)で、長さが連続せず 2 つの塊に分かれることが分かったので、**門番の立て方そのものが変わった。**

> **1. 第一の門番 ― `lowerbound || upperbound` が付いた探索は、読み筋として使わない。**
> **2. 控えの門番 ― 長さ 3 手未満(2 手以下)を弾く。**

**理由(私の実測と、司令塔の決定)**

- 標識が付いた 112 本は**すべてちょうど 2 手**。標識が付かなかった 136 本のうち**4 手未満は 1 本だけ**
- したがって**標識を第一にすれば、控えを 3 にしても 1 本も余計に捨てない。**4 にすると**使える読み筋を 1 本捨てる**
- **長さ 2 は「2 手先までしか読めなかった」ではなく、「この探索は打ち切られた」という事実の副作用である。**長さを見るのは症状を見ることで、標識を見るのは原因を見ることにあたる

**判断的知識だが、実測があるので確定した**([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 5.1 の委任条件 3 を満たす)。**確定の条件として、限界を一緒に書く。**

> **これは `go nodes 4,000,000` の実測である。本番は `go movetime 2000` であり、そちらでも 45% が標識付きになるかは測っていない。**

**計画時点の提案値 4 が U6-M の提案値と一致していたことは、根拠にしていない。**どちらも同じ理屈から出た提案であって、測定ではなかった。**実際、測ってみたら値も立て方も変わった。**

## 2. 実装前に測って分かったこと

### 2.1 【最重要】本番は MultiPV = 1 でしか読んでいない

設計書 1.4 と司令塔の指示は「MultiPV の読み筋は既に計算されていて `checkCandidateMovesSafety` が捨てている」としている。**`pv` を捨てているのは事実である。**しかし**本数は 1 本である。**

根拠(すべてコードを読んで確かめた。推測ではない):

| # | file:line | 事実 |
|---|---|---|
| 1 | `apps/server/src/engine/prioritizedEngine.ts:140` | `asLowPriority()` の `pendingMultiPv` の**初期値は 1** |

| 5 | `apps/server/src/analysis/engineReference.ts:129,134` | ③は**明示的に `setMultiPv(1)`** |

**これを 1 より大きくすることは本番の挙動の変更である。**`apps/server/src/analysis/candidateMoveReferenceFilter.ts:104` が `evaluation.multiPv[0]?.score` を読んで候補手を除外しており、MultiPV を上げると探索の枝刈りが変わって `multipv 1` の評価値自体が変わりうる。**除外される候補手が変わる = 画面が変わる。**

> **結論: U6-L は MultiPV = 1 のまま行う。3〜5 本を得るのは (お) の仕事であり、本番の挙動を変える判断である。**

### 2.2 `goMultiPv` の「最後に観測された行を採用する」規則が、読み筋を空で上書きしうる

`apps/server/src/engine/usiEngine.ts:222-227`:

```ts

  const parsed = parseInfoLine(line);
  if (!parsed) continue;
  linesByMultipv.set(parsed.multipv, { multipv: parsed.multipv, score: parsed.score, pv: parsed.pv });

```

`parseInfoLine`(`usiInfoParser.ts:64-79`)は **`info` で始まる行をすべて返す**。`multipv` が無ければ 1、`pv` が無ければ `[]`、`score` が無ければ `undefined` を既定にする。したがって `info string ...` のような **`pv` を持たない info 行が後から来ると、それまでの読み筋を空配列で上書きする。**

**実際に起きているか(既存の記録からの観測)**

| 観測 | 値 |
|---|---|
| 記録済みの探索(`out/i11` の ready 59 行 × baseline/afterPass) | **118 本** |
| `lines[0]` の score が欠測だった探索 | **0 本** |

**これは「score が空でなかった」の観測であって、「pv が空でなかった」の観測ではない。**score と pv は同じ info 行に出るのが通例なので pv も残っていた可能性は高いが、**pv は記録されていないので確かめられない。**U6-L が記録を始めて初めて確かめられる。

**本 STEP では `goMultiPv` の規則を変えない。**変えると `score` の採用も変わり、候補手の除外が変わる(= 本番の挙動)。**空の読み筋が何件出たかを数えて報告する**にとどめ、直すかどうかは数が出てから決める。

**既知事項の行(番号未定)**

> **`goMultiPv` は info 行を後勝ちで採用するため、`pv` を持たない info 行(`info string` 等)が後に来ると読み筋も評価値も空で上書きされる。**記録済みの 118 探索では評価値の欠測は 0 件だが、読み筋については未測定である。対局記録に出るかどうかは U6-L の測定で分かる。

## 3. 設計

### 3.1 新しい型(本番。`apps/server/src/analysis/searchPv.ts` を新設)

```ts
/** STEP U6-L。本番が既に行った探索の読み筋を、記録のためだけに持ち回る観測。
 *  画面にも HTTP 応答にも出さない(server.ts は backgroundPlan へ写さない)。 */
export interface SearchPvObservation {
  /** どの探索か。③の 2 本と、候補手の baseline / 各候補手。 */
  source: "focus_baseline" | "focus_after_pass" | "candidate_baseline" | "candidate_after_move";
  /** 実際に探索した局面(SFEN)。source と合わせて、後から再現できるようにする。 */
  sfen: string;
  /** source === "candidate_after_move" のときだけ、その候補手(USI)。他は null。 */
  moveUsi: string | null;
  /** MultiPV 番号(本 STEP の時点では常に 1 のはず。2 以上が出たら 2.1 の読みが誤り)。 */
  multipv: number;
  scoreCp: number | null;
  mate: number | null;
  /** 読み筋(USI)。取れなかった場合は空配列(長さ 0 も記録する。1.2(a))。 */
  pv: string[];
  /** その info 行が lowerbound / upperbound だったか。 */
  lowerbound: boolean;
  upperbound: boolean;
}
```

`pv.length` を別欄に持たない ― **同じ事実を 2 つの欄に持つと、片方だけ更新される穴ができる**(2026-09-12 の「一つの値に二つの意味を持たせない」の裏返し)。長さは読む側が数える。

### 3.2 `lowerbound` を取れるようにする(本番。挙動は変えない)

- `usiInfoParser.ts` の `UsiInfoLine` に `lowerbound: boolean; upperbound: boolean` を**必須で**足し、`parseInfoLine` が `\blowerbound\b` / `\bupperbound\b` を見て埋める。
- `usiEngine.ts` の `MultiPvLine` にも**必須で**足し、`goMultiPv` が写す。

**必須にする理由**: optional にすると、次に `MultiPvLine` を作る人が黙って落とせる。[measure-dont-grep-impact-scope] の原則どおり、**必須にして tsc に数えさせる。**

**直す件数の見積もり**: `multipv:` を含む行は 9 ファイル 64 行。**ただしこれは grep の数であり、実際に直す箇所ではない。**2026-09-12 に「18 ファイル 69 箇所」と書いて撤回した(実数は 14)のと同じ数え方である。**確定値は必須化して tsc を回したときの件数で置き換える。**

### 3.3 本番の戻り値に足す(1 欄・必須)

`computeReachablePlan` / `safeComputeReachablePlan` の戻り値に `searchPvs: SearchPvObservation[]` を**必須で**足す。入口は 2 箇所(1.3)。

- `measureEngineReference` が `EngineReference` に `pv` を持って返すよう変える(baseline / afterPass それぞれ)。`EngineReferenceSide` に足す ― **ここは既存フィールド(`scoreCp` / `mate` / `bestmove`)と同じ探索の産物なので、同じ構造体に入れるのが正しい。**
- `computeFocusText` が `{ text, searchPvs }` を返すように変える。
- `computeReachablePlan` が `safetyCheck` から候補手側の読み筋を組み立てる。

**HTTP 応答(`StateResponseBodyWithPlan`)には足さない。**`ReachablePlanBody` は触らない。これが「本番の挙動を変えない」の具体的な中身である。

### 3.4 記録へ写す(ハーネス)

`buildRecordLine` の引数を `phase` で判別する直和型にする。

```ts
type RecordLineParams =
  | { phase: "immediate"; ply: number; sfen: string; senteMove: string | null;
      goteMove: string | null; elapsedMs: number; response: StateResponseBodyWithPlan }
  | { phase: "ready";     ply: number; sfen: string; senteMove: string | null;
      goteMove: string | null; elapsedMs: number; response: StateResponseBodyWithPlan;
      engineReference: EngineReference | null;     // 既存の optional をやめる
      searchPvs: SearchPvObservation[] };          // 新設・必須
```

JSONL の形は変えない(`immediate` 行は `JSON.stringify` がキーごと落とす既存の挙動をそのまま使う)。

`invariants/types.ts` の `RecordLine` では **`searchPvs?:` を optional にする。**理由は書き手が忘れうるからではなく、**過去の記録ファイルにこの欄が無いから**である。**ready 行には必ず(空配列でも)出力する**ので、読む側は `undefined` = 古い記録 / `[]` = 読み筋が 1 本も取れなかった、と**区別できる。**この区別を型のコメントに明記する(`focusTextState` で「一つの値に二つの意味を持たせない」と決めたのと同じ理由)。

### 3.5 分布の報告(`check.ts`)

[DESIGN_REVIEW_2026-09-13.md](DESIGN_REVIEW_2026-09-13.md) 8.1 の 4 つ目「読み筋の長さの分布(`lowerbound` で 1 手しか返らない件数を含む)」を出す。

**判断はしない。**数えるだけ([AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 11.「不変条件は仕様の写しであって仕様の源ではない」、`denominators.ts` と同じ立て方)。

### 3.6 U6-M へ材料を渡すための追加の測定(M-2。司令塔の判断を仰ぐ)

**4. の P5 のとおり、MultiPV = 1 では `lowerbound` は 0 件になると予測する。**予測どおりなら、**U6-L の分布は U6-M の `minPlies` を決める材料にならない。**

材料を出すには、**MultiPV = 5 の探索を別に回すしかない。**

- 回帰セットの 59 局面の SFEN に対し、**ハーネス専用のスクリプト**で `setMultiPv(5)` の探索を 1 回ずつ行い、5 本それぞれの長さと `lowerbound` を数える
- **本番のコードは通さない。本番の挙動も変えない**(設計書の「新しい探索は要らない」は本番の話であって、測定の話ではない)
- **エンジンを 59 局面 × 1 本回す。**枠が空いてから宣言して行う

**これを U6-L に含めるか、別 STEP にするかは司令塔の判断を仰ぐ**(7.1)。
