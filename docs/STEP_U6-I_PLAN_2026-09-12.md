## 1. なぜ狙いなのか(人間の読みと、その確認)

縛った初心者の 2 局目は、16 手すべてで画面が何も言えなかった([BASELINE_2026-09-12.md](BASELINE_2026-09-12.md) 2.)。この局は**玉も金銀も一度も動いていない**ため、形(`data/shapes/`)をどれだけ増やしても一致しない(3 件 → 8 件で 16/16 のまま、という実測がある)。

狙いは構造が違う。`apps/server/src/analysis/intentDetector.ts` は**後手の指し手だけ**を見て、`data/intents/*.json` の `recognition_pattern` の署名(駒種 + 移動先)が順不同で観測されたかを機械的に突き合わせる。**こちらの陣形を見ない**。これが 2 局目を動かしうる唯一の経路である。

## 2. 着手前に確かめたこと(3 点。人間の指示による)

### 2.1 (1) 検出結果は coach 要素になるか → **なる**

経路は次のとおり(コードを読んで確認)。

```
detectIntents()                                   intentDetector.ts:detectIntentsFromEvents
  → IntentDetectionResult[](matchScore 降順・同点は intentId 昇順で安定ソート)
  → buildOpponentIntentStage() / buildOpponentNextAimStage()   explanationGenerator.ts:273, 349
  → generateCoachExplanations()                                explanationGenerator.ts:413
  → CoachExplanation[](stage と status を持つ)
  → stateResponse.ts:1378 coach: safeExplainPosition(...)
```

`CoachExplanation.status` に入る値は `buildStages` の分岐から次のとおり。

| 状態 | `[2] opponent_intent` の status | `[3] opponent_next_aim` の status |
|---|---|---|
| `matchScore === 0`(該当なし) | `none` | `none` |
| `forming`(署名が一部だけ観測) | **`forming`** | **`forming`** |
| `matched` かつ `review_status !== "draft"` | **`matched`** | **`matched`** |
| `matched` かつ `review_status === "draft"` | `none`(露出制御で unclassified へ) | **`matched`** |

**確認済み(実測)**: 固定棋譜 2 局目 + 現行 3 件で 16 行すべて `none/none`。これは記録済みの 16/16 沈黙と一致する(この一致をもって、以降の机上計算の校正とした。[tsx の使い捨て確認は型検査が走らないため、必ず既知の正解で校正する])。

### 2.2 (2) 「認識あり」はその status を数えるか → **数える**

`scripts/playtest/lib/denominators.ts:19`

```ts
const RECOGNIZED_STATUSES = new Set(["forming", "matched", "completed"]);
...
const hasRecognition = coach !== undefined && coach.some((c) => RECOGNIZED_STATUSES.has(c.status));
```

`coach` の**どの要素でもよい**(stage を問わない)。したがって `[2]` か `[3]` のどちらかが `forming` / `matched` になれば「認識あり」になる。狙いの stage は `filterCoachForTargetShape`(`stateResponse.ts:1447`、`current_shape` かつ `forming` だけを落とす)の対象外であり、終局(`status.isEnd`)以外で落ちる経路は無い。

### 2.3 (3) 「一つに絞る」処理を通るか → **通らない。形で起きた失敗は再演しない**

**結論: 起きない。** 形のときの沈黙悪化(42.4% → 61.0%)は `resolveRecognizedDirection`(`stateResponse.ts:593`)が **`shapes` だけ**を受け取り、forming が複数あって系統の根を決められないと `reason: "ambiguous"` を返し、`resolvedTargetShapeId` が決まらず道のり・候補手が消える、という経路だった。狙いはこの関数に**一切入らない**(引数は `shapeResults` のみ)。

狙い側の「絞り込み」は `pickBest`(`explanationGenerator.ts:84`)だけで、性質が違う。

- ソート済み配列の先頭を取り、`matchScore > 0` なら返す。**同点は intentId 昇順で決定的に決まる**
- **`ambiguous` に相当する戻り値が無い。** 候補が何件あっても必ず 1 件に決まり、stage が配列から落ちることも無い

したがって次が成り立つ(構造上の単調性)。

> **狙いによる「認識あり」⇔ `matchScore > 0` の狙いが 1 件以上ある ⇔ 後手の指し手のどこかに署名が 1 つでも観測された。**
> 狙いを**足すことで `matchScore` の最大値は上がるか変わらないかのどちらか**であり、**下がらない**。ゆえに**足して「認識あり」が消えることはない**。

**確認済み(実測)**: 同時に 6 件が forming になる合成データを 2 局目に当てたところ、16 行のうち 15 行が `forming/forming`、`ambiguous` に相当する挙動・stage の欠落は 0 件だった(1 行目は後手の手がまだ無いため `none`)。

### 2.4 確認の途中で見つかった、人間に報告すべき 2 点

いずれも**既存の構造**であり(現行 3 件はすべて `human_reviewed` のため表に出ていなかった)、**draft を足すと初めて表に出る**。番号は**未定(人間が採る)**。

- **[番号未定 ①] draft の狙いが `matched` に達すると、`[2]` が「まだ分かりません」に落ちる一方で、`[3]` は `next_aim_explanation` を `matched` として出す。**
  `nameExposure`(露出制御)は `buildOpponentIntentStage` にしか掛かっておらず、`buildOpponentNextAimStage`(`explanationGenerator.ts:349`)には掛かっていない。実測で確認済み(draft の狙いを全署名一致まで進めると `[2]=none / [3]=matched`)。
  **本 STEP での扱い**: 判定・文言(判断的知識)は人間承認なしに変えない([CLAUDE.md](../CLAUDE.md) ルール4)。代わりに、**追加する `next_aim_explanation` には戦法名を一切書かず、ルール6の控えめな語尾で書く**ことで、断定露出を実データ側で避ける。構造の是非は人間の判断。

- **[番号未定 ②] `pickBest` は `matchScore`(一致した署名の割合)だけで選ぶため、署名数の少ない draft の狙いが、署名数の多い `human_reviewed` の狙いを押しのける。**
  実測(後述 4.2)では、1 局目の 20〜30 手目で `boh_gin`(human_reviewed・2/3 一致・`forming` の事実文)が、追加する 3 署名の draft(3/3 一致)に置き換わり、`[2]` が事実文から「まだ分かりません」へ**後退する**。
  **本 STEP での扱い**: 選び方(優先度)は判断的知識のため変えない。**予測に書き、実測して報告する**。

### 2.5 併せて確認した制約(人間の判断が要る)

### 8.6 推奨(**決めるのは人間**)

**案2「出せる文が先、同点は審査済み」を推す。** 理由は 3 つ。

1. **案1 と同じく「分かりません」を 0 にする**(11 → 0)
2. **一致度が並んだときだけ審査済みを採る。** 審査済みを一致度より上に置かないので、人間が警告した「よく当たっている下書きが永久に出ない」は構造上起きない(案3 で実際に起きることが 8.2 で確認できた)

## 9. 「測れるようにする」と「本番で効くようにする」の区別(**2026-09-12 追記**)

> 別セッションの成果監査が、`directionRule`(U6-F)と `suppressTargetShapeProgress`(U6-H)は **計測用にしか存在せず、本番の HTTP からは到達しない**ことを確かめた([STEP_UNIT6_PLAN_2026-09-12.md](STEP_UNIT6_PLAN_2026-09-12.md) 13.12 (4c))。`apps/server/src/server.ts` の 4 箇所(`:310`・`:361`・`:397`・`:432`)はいずれも `buildStateResponseWithPlan(..., {}, ...)` を渡しており、リクエストから `StateResponseOptions` を組み立てる処理が無い。
> **人間の規則**: この型のオプションを足すときは、2 つが別の作業であることを計画の時点で分けて書く。

**本 STEP の `IntentPickRule` は、その 2 つが**混ざった**形になっている。読み分けを書いておく。**

| 入り口 | 本番に効くか | 位置づけ |
|---|---|---|
| **`DEFAULT_INTENT_PICK_RULE`(モジュール直下の定数)** | **効く** | `server.ts` が `{}` を渡すため `options.intentPickRule` は `undefined` になり、`generateCoachExplanations` の既定引数としてこの定数が使われる(`explanationGenerator.ts:555` → 既定引数)。**この 1 行を変えると本番の画面が変わる** |
| `options.intentPickRule`(呼び出しごとの上書き) | **効かない** | `directionRule` と同じ。HTTP からは到達しない。テストと計測だけが使う |

**したがって Q-7(既定をどれにするか)は、「測れるようにする」ではなく「本番で効くようにする」側の決定である。** 既定を変えた瞬間に本番の `[2][3]` が変わる。**だから人間が決めるまで `"current"` のまま置いてある。**

**この読みは実測でも裏づけられている**: `scripts/playtest/replay.ts` は `intentPickRule` を 1 箇所も渡していない(`grep -c` = 0)。それでも worktree で**定数 1 行だけ**を倒したところ、`buildStateResponseWithPlan`(= `server.ts` が呼ぶのと同じ関数)の出力が変わり、②が「分かりません」の行数が 11 → 0 になった(8.2)。**定数が本番経路を通ることが、読みではなく出力で確かめられている。**

**U6-F・U6-H との違いはここだけである**(あちらは定数ではなく引数の既定値で、本番に効く入り口が無かった)。

## 10. 人間の決定(2026-09-12。Q-2・Q-6・Q-7)

### 10.1 Q-7: **既定を案2 にする**(決定)

`DEFAULT_INTENT_PICK_RULE` を `"current"` → **`"speakable_then_reviewed"`** に変更した。9. のとおり**この定数は本番の画面に効く**ため、これは「本番で効くようにする」側の変更である。

採用理由(人間が採った):案1 と同じく②が「分かりません」を 0 にでき、**一致度が並んだときだけ**審査済みを採るので、よく当たっている下書きが永久に出なくなることは構造上起きない。

### 10.2 「`[2]` が直る代わりに `[3]` が痩せる」の読み方(**人間の決定**)

**むしろ正しい向きである**と読む。理由は 2 つ。

1. **`[3]` は③として別セッションがいまエンジンで埋めつつある**(STEP 5-F)。したがって `[3]` が汎用文になっても穴にならない
2. **痩せる中身は P-19 が本来止めるはずのもの**(`draft` の `next_aim_explanation` の素通し)である。**U6-G 後の画面へ一歩近づいた**、という読みを採る

### 10.3 「弱い観測を語る」は順位の問題ではない(**人間の決定。重要**)

8.4 で挙げた「2局目 22手目以降、`[2]` が 3筋(1/2一致)を根拠にし、実際の大きな出来事だった 8筋の歩交換を語らない」件について。

> **現行でも 8筋 は語れていない ―「分かりません」だからである。** 根は並べ方ではなく、**8筋 の狙い(`hishasaki_fugokan`)が `draft` のままで、`matched` に達しても名乗れない**ことにある。[CLAUDE.md](../CLAUDE.md) ルール4のとおりで、**露出制御は正しく働いている。**

**したがって直し方は順位付けではなく、下書きを審査して `human_reviewed` に上げることである**([KIND3_VERIFICATION.md](KIND3_VERIFICATION.md) の多段階検証にあたる工程)。

> **これは順位の問題ではなく、審査が追いついていない問題である。順位付けでこれを解こうとしないこと。**(2026-09-12 の人間の決定)

### 10.4 Q-6: 別 STEP にする。ただし食い違いの行数だけ数えた(**数えるだけ。直していない**)

`selectTargetPurpose`(内部の `selectBestIntent`)は今回**触っていない**。その規則は「`matchScore` 降順 → `intentId` 昇順」で、**変更前の `pickBest("current")` と同一**である。したがって食い違いは「案2 の選択 ≠ current の選択」の行と一致する。

**結果: 59 行中 18 行で食い違う。ただし画面に出る材料になっているのは 0 行である。**
