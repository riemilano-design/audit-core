## 4. 読み

- **replay.ts と rescreen.ts のエンジンの使い方**:
  - 共通: どちらもエンジン 1 本を handshake → isready → Threads 1 で起こし、同じプロセスで最後まで回す。`usinewgame`・ハッシュの消去・`USI_Hash` の設定は、`apps/server/src/engine`・`scripts/playtest/lib` に無い。置換表と履歴はプロセスの中で持ち越される
  - replay.ts: ready 行ごとに、候補手の探索と③の探索(どちらも固定ノード)を同じ局面で先に走らせ、その直後に `measureEngineReference` を呼ぶ(`lib/recorder.ts` の `buildReadyRecord`)
  - rescreen.ts: 読み直す行を ply の昇順に、`measureEngineReference` だけを続けて呼ぶ(`lib/rescreen.ts`)
- **差の仕組み(P-33 の実測)**: 参考評価は、その前に同じプロセスで何を読んだかに依存する
  - 4M 一律は、同じ局面を先に読んだ置換表から始まる。床は、1 つ前の読み直した行の置換表から始まる
  - 段 2 は床と読み直す行の集まりが違うので、また別の履歴になる
  - 各道具・各並びの中では再現する(床 2 回で 836/836 行一致、P-48)。エンジンの揺れではなく系統的な差
  - 同じ 4M でも、境の近くの差の値が 48〜370 cp 動いて境をまたぐ(床 8+7 件、段 2 の深い組 10 件)
  - **どちらの値が良いかは測っていない**
- **段 2 に固有の損失**: 400k の値に由来する取りこぼしは選び方の 1 件だけ。残りの 10 件は、4M で読み直しても履歴で境をまたいだもの
- **「ノード数」の区分は、この作りでは切り分けられない**: 段 2 の深い値 257 行のうち、床の深い値とのバイト一致は 41、4M 一律の値とは 40(両方と一致 38。多くは値が null の行)
- **ノード数だけの差を測るには、履歴を揃える必要がある**(道具を足す判断で、この STEP の範囲外。案だけ):
  - (i) 行ごとに新しいエンジンのプロセスで測る
  - (ii) 同じ並びの行を、400k と 4M で同じ順に読む
